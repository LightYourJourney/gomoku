# 最终性能报告（Phase 10E）

**日期**：2026-10-21
**范围**：Phase 10B–10D 的搜索优化、增量评估接入、真实浏览器与构建产物性能
**原则**：只报能重跑出来的数字；毫秒数标注环境与负载；跨会话绝对值不作比较

## 1. 环境

| 项 | 值 |
| --- | --- |
| 硬件 | Apple M3 / 8 核 / 16 GB |
| 系统 | macOS 26.6.2（Darwin 25.6.0） |
| Node / Yarn | v26.12.0 / 1.22.22 |
| 引擎 | `search-1`，Negamax + Alpha-Beta + 迭代加深 + Zobrist TT + 杀手着法 + VCF |
| 审计时负载 | 5.9–24.5（共享机器，1 分钟均值） |

## 2. 引擎速度：固定深度

协议：两边独立打包；12 轮严格交替；每轮每边取最快一次；depth 4；同一会话。
这套协议在字节相同的两份包上对照过，比值 0.978×（噪声内），因此低于 ±3% 不当作证据。

| 项 | 结果 |
| --- | --- |
| 旧版（10C 前基线包） | 268.6 ms |
| 新版（当前源码包） | 117.6 ms |
| 合计比值 | **2.28×** |
| 历史三次运行 | 2.27 / 2.28 / 2.30× |
| 行为差异 | 16 个局面的着法、节点、ttHits、深度全部一致 |

分局面典型值（旧 → 新）：开局 30.8–33.6 → 10.9–12.6 ms；中盘约 24 → 11 ms；
endgame-eight-holes 3.1 → 2.5 ms（1.25×）、nearly-full 3.4 → 2.9 ms（1.20×）；
两者约 265 节点，固定初始化成本占比高。

## 3. 引擎速度：真实预算

### 3.1 固定局面（hard，1600 ms，同会话 3 轮取中位）

| 局面 | 旧版 | 新版 | 比值 | 节点 / 深度 / reason |
| --- | --- | --- | --- | --- |
| opening-adjacent | 310.3 ms | 132.3 ms | 2.35× | 10,177 / 6 / search |
| bench-midgame | 188.5 ms | 97.7 ms | 1.93× | 7,202 / 6 / search |
| bench-double-three | 815.3 ms | 331.7 ms | 2.46× | 19,289 / 6 / search |

两边都在预算内走满深度 6，节点数逐位相同。真实预算的比值低于固定深度的 2.28×，
因为 VCF（最多 35% 预算）与候选生成没有在 10C 优化，占比被放大。

### 3.2 真实对局（hard，2 开局 × 换色，4 局）

- 107 个配对手：节点、深度、ttHits、原因**逐手相同**。
- 配对总耗时：新版 20,259 ms，旧版 30,843 ms，**1.52×**（负载 24.46）。
- 10C 归档的低负载运行是 **1.64×**（20,145 ms vs 33,129 ms）。
- 2 局以 `move-limit` 结束（78 手）；新旧两边同样结束，未当成和棋。

这说明优化减少的是**同样的搜索树的计算时间**，没有改变棋谱。

## 4. 浏览器与交互

### 4.1 五档应手（生产构建，真实 Chrome，单步）

| 档位 | 墙钟（含 UI） | 面板深度 | 节点 |
| --- | --- | --- | --- |
| 入门 | 109 ms | 1 | 12 |
| 初级 | 51 ms | 2 | 59 |
| 中级 | 53 ms | 4 | 656 |
| 高级 | 1,045 ms | 6 | 20,952 |
| 专家 | 2,644 ms | 6 | 60,757 |

首档 109 ms 可能含 Worker 启动；其余是单样本，不代表分位数。
10D 的锦标赛统计更可靠：中级平均 5.9–8.3 ms，高级 85.6–126.7 ms，
专家平均 1,342.5 ms、P90/P95 = 2,600 ms、43% 超时。

### 4.2 超时回退

专家档连续三手在 2.658–2.666 s 返回：深度 6/7，reason「超时回退」，
confidence「启发式」，界面显示「时间预算内未搜完，这一手是启发式建议」。
第四手 81 ms 算到必胜：深度 0，reason「算到必胜」，confidence「精确」。
超时不是错误，但**专家档的用户体感就是经常等满 2.6 秒**。

### 4.3 主线程与渲染

`yarn bench:render`（生产构建，负载 5.95）：

| 指标 | 值 |
| --- | --- |
| TTFB | 5 ms |
| 应用自身（响应结束 → DCL） | 51 ms |
| FCP / LCP | 144 / 144 ms |
| 落子 click → React 提交 | 中位 0.10 ms，最大 0.30 ms |
| 200 手回放拖动 | 中位 1.70 ms，最大 1.70 ms |
| DOM 元素 | 676 |

AI 计算在 Worker 里；专家思考期间点「悔棋」「重新开始」「求提示」都能立即响应，
说明主线程没有被搜索阻塞。没有做正式的 INP/Long Task 统计。

**4× CPU 限速（仅作敏感性参考，不等于真机）**：专家 3 手 2.83–2.90 s、
深度 5/6/7，均标超时回退；思考中悔棋点击 149 ms，等过 2.6 s 预算后盘面仍为 0 子。
限速下搜索变浅但不会卡住主线程，也不能据此推断低端手机的表现。

### 4.4 长跑与内存

单页 25 轮「落子 → 应手 → 提示 → 收起 → 悔棋」：

| 轮次 | 主线程 JS 堆 |
| --- | --- |
| 0 | 3.23 MB |
| 5 | 4.47 MB |
| 10 | 4.53 MB |
| 15 | 4.66 MB |
| 20 | 4.73 MB |
| 25 | 4.76 MB |

前 5 轮预热后增长明显放缓；Worker 始终 1 个；控制台/页面错误 0。
**Worker 堆没有测到**（Worker 上下文无 `performance.memory`），不能据此宣称 Worker 无泄漏。
也没有做多小时 soak。

## 5. 构建产物

| 资源 | 生产（09B） | 候选 | 变化 |
| --- | --- | --- | --- |
| 主 JS（raw） | 342,495 B | 343,278 B | +783 B（+0.23%） |
| 主 JS（gzip -9） | 106,843 B | 107,191 B | +348 B（+0.33%） |
| Worker（raw） | 11,771 B | 13,994 B | +2,223 B（+18.9%） |
| Worker（gzip -9） | 4,449 B | 5,394 B | +945 B（+21.2%） |
| CSS | 35,177 B | 35,177 B | 0 |

Worker 变大的主要原因是把增量评估带进了 Worker 包；绝对值仍然只有 14 KB。
主包只增加 0.8 KB，说明优化没有把复杂度泄漏到主线程。

## 6. 结论

1. **更快成立**：固定深度 2.28×、真实预算 1.93–2.46×、真实对局 1.52–1.64×。
2. **决策不变成立**：16 个固定局面 + 107 个真实配对手 + 4 局棋谱逐手一致。
3. **用户可见延迟**：低/中档毫秒级；高级约 1 秒；专家经常 2.6 秒。
   优化没有降低专家的等待，因为专家本来就会把预算用满。
4. **剩余热点**：棋型扫描（`scanDirection` 约 38.5%）与排序（`analyzeFast` 8.5%）；
   叶子评估不再是主成本。
5. **不能宣称**：跨机器毫秒绝对值、Worker 无内存泄漏、低端真机表现、专家档强度提升。
