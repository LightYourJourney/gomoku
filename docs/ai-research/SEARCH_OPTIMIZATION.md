# 搜索优化记录（Phase 10C）

> 本文记录 Phase 10C 里**每一项**生产搜索优化的改动、证据与代价。
> 所有数字来自 `yarn profile` 与 `yarn strength`；归档在
> [`runs/2026-10-21_07*-phase10c-*`](runs/) 与三份 `*-ab-new_vs_*` 对局报告里。

**一句话结论**：三项改动全部保留，固定深度下合计 **2.27–2.30×**（三次独立运行），
真实 hard 预算对局逐手配对 **1.64×**，**节点数 / 置换表命中 / 深度 / 着法一个都没变**。
搜索策略与评分语义未改。

## 1. 测量方法

### 1.1 必须 bundle vs bundle

引擎计时不能拿「打包产物」和「源码」比：`createLocalEngine` 走的是 vitest 转换后的模块，
**同一个引擎、同样的节点数，包比源码快约 5 倍**（18 ms vs 90 ms）。
拿包和源码做 A/B，量到的是打包方式，不是代码改动。

所以 `bench/profile/upgrade.ab.profile.ts` 每次都把**当前源码现打一份包**
（`bundle-engine.mjs`），再和旧提交打出的包比。两边走同一条 esbuild 管线。

### 1.2 控制组：先量出协议本身的偏差

用**逐字节相同**的两份源码各打一个包互比（`base-6e16ed0.mjs` vs `control-6e16ed0.mjs`，
`diff` 只差注释里的临时目录名）：

| 协议 | 控制组比值 | 读法 |
| --- | --- | --- |
| 5 轮交替、取 min | **1.06–1.09×** | 奇数轮里两边当「每轮先跑」的次数是 3:2 |
| 12 轮交替、取 min | **0.978×** | 先跑次数相等，回到噪声内 |

所以本阶段的协议固定为 **12 轮严格交替、每边取 min**；低于 ±3% 的差别不作为证据。
`ROUNDS` 的注释里写明了这一点，改回奇数轮会重新引入偏差。

### 1.3 固定深度只量「单节点速度」

节点数由 `src/ai/search.equivalence.test.ts` 的 4 条 golden 钉住
（开局 362、安静中盘 1,142、双三 278、残局 286），
A/B 的每个局面再逐字段比对 `着法 / 节点 / ttHits / 深度 / reason`。
**不一致即为失败，不出加速比。** 本轮 16 个局面全部一致。

## 2. 起点：先看 profile 再动手

Phase 10B 的固定深度剖析（归档 `0429`）：

| 归属 | 占比 | 主要函数 |
| --- | --- | --- |
| 着法排序 | **46–47%** | `buildLine` 11.2%、`inBounds` 10.1%、`scanLine` 7.2%、`orderMoves` 5.5%、`idx` 5.3% |
| 局面评估 | **30.7%** | `scoreSegment` 24.2%、`scoreLine` 3.8%、`evaluateBoard` 2.8% |
| 其余 | ~23% | 候选生成、递归、置换表、算杀、匿名内联帧 |

排序里最刺眼的是**每个候选、每个方向、每格都要过一次 `inBounds` + `idx`**，
以及每次 `buildLine` 都新建一个 9 字节 `Int8Array`——而 `analyzeFast` 根本不需要
中间那一行，它只问「有没有五、成五点在哪」。

据此确定三项，按「改动边界从小到大」排序，每项独立验证。

## 3. 优化 1 · 行构造内联边界与索引

**改动**（`src/ai/patterns.ts`）：

- `buildLine` 的边界判断与一维索引直接展开，不再调用 `inBounds` / `idx`；
- 缓冲区由调用方传入：`analyzeFast` 的四个方向复用同一块 9 格 `Int8Array`，
  `analyzeDirection` 自己持有一块（它要在同一行上逐格试放）。

**为什么行为不变**：`inBounds` 额外用 `Number.isInteger` 拒绝非整数，但非整数坐标
落到 `board[小数下标]` 得到 `undefined`，与「界外」同样记为 `-1`；
`idx(x, y)` 就是 `y * 15 + x`。整数输入下逐位等价，非整数输入下可观察结果也相同。

**证据**：`patterns.test.ts` 47 条全绿；4 条搜索 golden 的
着法 / 分值 / 节点 / `ttHits` / 深度全不变。

**效果**（同一次会话内的单次测量，未单独归档）：

| 项 | 值 |
| --- | --- |
| 固定深度 4 合计 | 172.1 ms → 144.1 ms，**1.19×** |
| `analyzeFast` 单价 | 1.73 µs → 1.19 µs |
| 剖析占比变化 | `inBounds` 10.1% → 4.3%，`idx` 5.3% → 2.2% |
| 输出差异 | 0 个局面 |

## 4. 优化 2 · 热路径直接扫窗口，不物化行

**改动**（`src/ai/patterns.ts`）：

- 新增 `scanDirection`：按方向先算还能走几格，再对 5 个五连窗口直接读棋盘，
  落点无条件按「己方已落下」计（与原 `line[CENTER] = 1` 同一语义）；
- `analyzeFast` 改走 `scanDirection`；`analyzeDirection` 保留数组版——它需要
  在原行上逐格试放，那个中间数组有第二个读者。

**为什么可以两套逻辑并存**：这是全阶段唯一一处**有意的重复**。它由一条随机差分测试
兜底：20 个种子 × 60 手随机棋局，每个局面随机问 3 个点（含已有棋子）、黑白两方，
把直扫版与数组版（`analyzeDirection` 聚合）四个字段逐项全等比对。
变异验证：把「落点视为己方」改成不成立，7 条测试立即变红并给出种子与手数。

**效果**：

| 项 | 值 |
| --- | --- |
| 固定深度 4 合计 | 165.0 ms → 125.2 ms，**1.32×**（累计） |
| `scanDirection` 自身耗时 | 从 `buildLine` + `scanLine` 的 23% 降到单一函数，且少了每方向 9 次写 |
| 输出差异 | 0 个局面（16 个 workload 的节点 / ttHits / 深度 / 着法全同） |

## 5. 优化 3 · 接入增量评估

### 5.1 先过条件，再动手

Phase 10B 的验收条件逐条核对：

| 条件 | 证据 | 结论 |
| --- | --- | --- |
| 与 `evaluateBoard` 精确一致 | 24 条测试：手写局面 + 20 种子 × 30 手随机差分 + 10 种子 × 120 次随机撤销；两边视角都比 | 通过 |
| 无状态泄漏 | 每次 `searchBoard` 新建一个实例；不导出模块级可变状态 | 通过 |
| 收益足够 | 生命周期 17–32×，评估占 CPU 31–35% | 通过 |
| 内存合理 | **2,947 B/实例**（5000 个实例的堆 + external 实测） | 通过 |
| 不破坏 core 数据模型 | 内部持有棋盘副本，`core` 零改动 | 通过 |
| 不改变评分语义 | `score(player)` 与 `evaluateBoard(board, player)` 逐位相等 | 通过 |

### 5.2 改动面

`src/ai/search.ts` 只有 6 处：

1. `SearchContext` 增加 `evaluator`；
2. `searchBoard` 在**算杀之后**创建（不让评估器承担「算杀是否完整还原」的假设）；
3. 三处叶子取分：超时早退、`depth <= 0`、无候选可走；
4. 两处落子/撤销（`negamax` 与 `searchRoot`）与棋盘写操作**紧邻成对**：
   `board[index] = player` → `evaluator.place(index, player)`；递归返回 →
   `evaluator.undo()` → `board[index] = 0`。

`incrementalEvaluate.ts` 本身一行未改。`evaluateBoard` 不再被搜索调用，
但保留给提示、诊断与剖析单价测量。

### 5.3 证据

- 4 条 golden：分值、节点、`ttHits`、深度、着法全部不变；
- 16 个 workload 的 A/B：`nodes / ttHits / depth / move / reason` 全同；
- 固定深度对局（medium d4，4 局）：**逐手完全一致**（含每手节点数、ttHits、深度、原因）；
- hard 真实预算（4 + 8 局）：**逐手完全一致**。

### 5.4 效果

| 项 | 值 |
| --- | --- |
| 固定深度 4 合计 | 165.3 ms → 72.8 ms，**2.27×**（累计；三次运行 2.27 / 2.28 / 2.30） |
| `evaluateBoard` 调用 | 19,983 个节点的会话里 **13,741 → 0** |
| 剖析占比 | `scoreSegment` 28.2% → 3.9%（只剩评估器初始化与落子时的局部重算） |
| 调用次数 | `analyzeFast` 603,887、`orderMoves` 5,355、节点 19,983 **全部不变** |

## 7. 为什么停在这里

优化后的固定深度剖析（`0722-phase10c-cpu-profile.json`）：

| 函数 | 占比 |
| --- | --- |
| `scanDirection` | **38.5%** |
| `analyzeFast` | 8.5% |
| `inBounds` + `idx` | 10.9% |
| `threatScoreWith` | 4.0% |
| `isEmptyAt` + `isOwn` + `analyzeRuns` | 8.1% |
| `candidateMoves` | 3.5% |
| `orderMoves` | 1.6% |
| 评估器初始化（`scoreSegment` / `scoreLine`） | 4.5% |
| `place` / `undo` | 0.7% / <0.1% |

**排序仍然占七成以上**，但剩下的收益不再是低风险的：

- **滑动窗口重写 `scanDirection`**：能把每方向的棋盘读从最多 25 格降到 9 格，
  估算再快 1.1–1.2×。代价是同一段窗口逻辑出现**第三份**实现，
  而它已经是对局强度的直接输入。本阶段不做。
- **候选预筛 / 减少打分宽度**（Class B，策略变更）：会改变哪些候选进入搜索，
  必须单独做棋力 A/B 才能判断是强是弱。本阶段不做，见
  [OPTIMIZATION_CANDIDATES.md](OPTIMIZATION_CANDIDATES.md) 的更新说明。
- **VCT**：维持关闭（Phase 10B 已实测代价 38–520 倍且结论无差）。

## 8. 成本与风险

1. **搜索与评估器必须成对**：`negamax` / `searchRoot` 里任何新的棋盘写操作，
   都必须紧邻调用 `place` / `undo`。漏一处，叶子分数会静默偏离当前局面。
   代码里在 `SearchContext.evaluator` 的注释与两处调用点都写明了；
   4 条 golden 与 16 个 workload 的节点比对会在下一次改动时先变红。
2. **每次搜索有固定初始化成本** 75–113 µs。对 265 节点的残局，它把加速比压到 1.25×。
3. **`analyzeFast` 的两份窗口实现**：靠随机差分测试对齐，不靠注释承诺。
4. **绝对微秒数随负载漂移**（本机同一函数跨运行可差 3 倍），
   本文只把比值与占比当结论；固定深度比值在 2.27–2.30 之间复现了三次。
