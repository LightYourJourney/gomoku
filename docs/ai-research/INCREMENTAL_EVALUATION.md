# 增量局面评估（Phase 10B 原型 → Phase 10C 接入）

> **结论先说**：原型做到了与 `evaluateBoard()` **逐位相等**，一次「落子 → 取分 → 撤销」
> 比一次全盘评估便宜 **17–20 倍**。Phase 10B 时投影端到端 1.40 倍、**不足以多搜一层**，
> 所以当时没有接入；Phase 10C 先做完排序优化，再按验收条件把它接进了生产搜索：
> 固定深度合计 **2.27–2.30×**（其中评估器贡献了主要增量），真实 `hard` 对局逐手配对 **1.64×**，
> 节点数 / 深度 / 着法逐位不变。接入结果见 [PHASE_10C.md](PHASE_10C.md) 与
> [SEARCH_OPTIMIZATION.md](SEARCH_OPTIMIZATION.md)。

代码：`src/ai/incrementalEvaluate.ts`（约 180 行）｜测试：`src/ai/incrementalEvaluate.test.ts`（24 条）

## 1. 原理

`evaluateBoard()` 每次扫 72 条线。落一颗子只可能改变**经过该点**的线：
横、竖、两条斜向，最多 4 条（边角上长度 < 5 的斜线不在评估集合里）。
其余 68 条以上的线分数不变。

```
棋盘交叉点 → 受影响的线编号集合
  由 evaluate.ts 的 LINES_BY_CELL 预计算（72 条线上的每格各登记一次）
```

**没有第二套坐标或线段定义**：`LINES_BY_CELL`、`EVALUATION_LINES` 与
`scoreLine()` 都从 `evaluate.ts` 导出，增量实现只调用它们。这是「两份规则逐渐分叉」
的唯一有效防线。

## 2. 状态与 API

```ts
const evaluator = createIncrementalEvaluator(board)  // 复制棋盘，不改入参
evaluator.score(BLACK)      // = evaluateBoard(board, BLACK)，整数，精确相等
evaluator.place(index, BLACK)
evaluator.score(WHITE)
evaluator.undo()
```

内部状态：

| 项 | 形式 | 说明 |
| --- | --- | --- |
| 棋盘 | `Uint8Array` 副本 | 调用方的棋盘永不被改动 |
| 每条线的黑分 / 白分 | 两个 `Float64Array(72)` | 都维护，因为落子会同时改变两侧 |
| 总分 | 两个 number | 维护的是「己方线分之和」；对外返回**差值**（与 `evaluateBoard` 语义一致） |
| 撤销栈 | 每层一个预分配帧（≤4 条线的旧值 + 旧总分） | 撤销是**恢复旧值**，不是重算 |

`place` 的开销 = 2–4 条线 × 2 个颜色各跑一次 `scoreLine`；`undo` 只是写回几个数。

## 3. 精确一致（不是近似）

判据是**逐位相等**，因为分值是整数（`SHAPE_VALUES` 与 `WIN_SCORE` 全是整数），
不存在浮点误差的余地。

测试覆盖（24 条，全部先写红再实现）：

| 组 | 覆盖 |
| --- | --- |
| 基础 | 空盘、单子、两子、横 / 竖 / 两条斜向、贴边 |
| 棋型 | 活三、眠三、活四、冲四、隔子四、多个成五点、成五、**长连**、双方重叠、一手同时改攻防 |
| 状态 | 连续落子 / 逐步撤销、不同分支同一位置、20 轮嵌套撤销、撤销到空盘、不修改入参、非法落子与空撤销报错 |
| 差分 | 20 个种子 × 30 手的随机合法对局，逐手比对**黑白两个视角**；10 个种子 × 120 步的「随机落子/随机撤销」；接近满盘；含五连的终局棋盘 |

差分失败时抛出完整手顺（种子固定，可复现）：

```
种子 7 在第 23 手不一致
手顺：(6,7)B (8,7)W ...
黑：增量 12000 / 全盘 12000
```

**测试本身的鉴别力也验证过**（项目规矩：把修复撤掉确认会红）：

- 只更新第一条受影响的线 → **6 条用例红**；
- 撤销时不恢复总分 → **3 条用例红**。

## 4. 成本（实测）

归档：`runs/2026-10-21_0429-phase10b-incremental.json`。
`min` 为各批平均值的**最小值**；绝对微秒数随机器负载变化很大（同一项在多次运行里差 2 倍以上），
**比值稳定**。

| 局面 | 全盘评估 | `score()` 读取 | 初始化 | **落子+取分+撤销** | 加速比 |
| --- | --- | --- | --- | --- | --- |
| opening-adjacent | 77.4 µs | 0.020 µs | 74.6 µs | **4.35 µs** | **17.8×** |
| bench-midgame | 69.6 | 0.022 | 72.1 | **3.82** | **18.2×** |
| quiet-midgame | 67.7 | 0.022 | 70.1 | **3.67** | **18.5×** |
| bench-double-three | 70.5 | 0.023 | 75.6 | **4.05** | **17.4×** |
| nearly-full | 8.9 | 0.022 | 13.1 | **1.00** | **8.9×** |

多次运行之间，加速比落在 **15.7–21.2×**（接近满盘 8.4–10.0×）；本次归档运行是 17.4–18.5×。

拆开看：

| 操作 | 单价 | 说明 |
| --- | --- | --- |
| `place` | 3.9–7.0 µs | 与「这个点经过几条长线」直接相关；中心附近 4 条线最贵 |
| `undo` | 0.04–0.06 µs | 只写回旧值，不重算 |
| `score` | 0.020–0.023 µs | 两次减法 |
| `init` | 13–76 µs（中盘局面 70–76） | 就是一次全盘评估的工作量（72 条线 × 2 色） |
| **`try/finally` 保护撤销** | **−0.05…+0.10 µs** | 与生命周期同量级的噪声，可视为免费；见 §5 |

`try/finally` 那一行是专门为任务书里「如果采用 try/finally 保护撤销，评估额外开销」量的：
同一段「落子→取分→撤销」套上 `try/finally` 后，五个局面的差值是 −0.047 / +0.100 / +0.025 /
−0.022 / +0.016 µs——**全部落在批次噪声内**。没有异常时它确实不花钱。

**同一棵树、只换叶子取分方式**（深度 3×宽度 6，216 个叶子；另一组 2×8，64 个叶子）：

| 局面 | 全盘 (ms) | 增量 (ms) | 加速比 |
| --- | --- | --- | --- |
| bench-midgame | 15.8 | 1.50 | **10.5×** |
| quiet-midgame | 15.3 | 1.60 | **9.6×** |
| bench-double-three | 4.7 | 0.36 | **13.1×** |

这组之所以只有 10–13×（而不是 18×）：树里每一层都要 `candidateMoves` 与递归，
那部分两边一样，稀释了叶子那一步的差距。

**内存**：5,000 个实例共 7.65 MiB 堆 + 6.47 MiB external ≈ **2.89 KiB/实例**（2,961 B）
（225 B 棋盘 + 2×576 B 线分 + 对象开销 + 首个帧），前后各强制 GC 一次后测量。
撤销栈按深度增长，每层再 +~100 B。

**GC**：整次剖析里 GC 占 **0.44–0.46%**（见 [CPU_PROFILE.md](CPU_PROFILE.md)）。
增量评估既不增加也不减少 GC 压力——它没有每次调用都新建对象。

## 5. 如果接进搜索，栈纪律是什么

搜索是「落子 → 递归 → 撤销」的同一块棋盘。接入后的形状：

```ts
const evaluator = createIncrementalEvaluator(own)   // 每次 searchBoard 一次，~0.15 ms

board[index] = player
evaluator.place(index, player)
const value = -negamax(...)
board[index] = 0
evaluator.undo()
```

需要注意的点（Phase 10B 列成风险清单，Phase 10C 接入时逐条核对）：

| 风险 | 说明 | Phase 10C 的处置 |
| --- | --- | --- |
| Alpha-Beta 提前返回 | 每个 `return` 之前都必须 `undo()`；用 **一个出口**或在 `finally` 里收尾，否则状态会漂移 | `negamax` / `searchRoot` 的落子与撤销之间没有提前 `return`；`undo()` 紧跟在递归之后、`break` 之前 |
| 预算过期 | `hasExpired()` 直接返回评估，同样要保证已落子的帧被撤销 | 过期发生在**子节点入口**，该帧尚未落子；父帧在返回后照常 `undo()` |
| 异常 | 引擎内部不抛错；真抛了就是 bug，宁可炸掉也不要静默带偏 | 维持现状 |
| 置换表命中 | 命中时**没有**落子，也就没有 `place`——不要在这条路径上撤销 | 命中路径没有配对调用 |
| 根节点 | 根节点不落子，只对子节点用增量 | `searchRoot` 的落子同样成对；根局面本身不 `place` |
| 内存 | 每次搜索多一个实例（2.89 KiB）；不共享、不缓存 | 每次 `searchBoard` 新建一个，用完即弃 |

## 6. 端到端收益：Phase 10B 的投影与 Phase 10C 的实测

**投影**（Phase 10B，当时排序尚未优化）：

| 量 | 固定深度 | 真实预算 |
| --- | --- | --- |
| 评估自身耗时 / 调用 | 60.0 µs | 63.6 µs |
| 评估调用次数 | 13,741 | 19,186 |
| 增量循环单价 | ~3.8 µs | ~3.8 µs |
| 可省时间 | 0.77 s | 1.15 s |
| 采样总时长 | 2.69 s | 3.96 s |
| **投影加速** | **1.40×** | **1.40×** |

原因很直接：评估只占 30% 的 CPU（[CPU_PROFILE.md](CPU_PROFILE.md) §4），
把它的单价降到 6% 也只剩下这 30% 可省。

**这够不够多搜一层？不够。** 实测每加一层节点涨 **2.3–4.7 倍**（§3 的任务表）。
1.40 倍买不到一层。

**实测**（Phase 10C，先做完排序优化再接入）：固定深度 4 合计
165.3 ms → 72.8 ms（**2.27×**，三次运行 2.27–2.30）；其中排序两项先把累计推到 1.32×，
增量评估再推到 2.27×。真实 `hard` 预算下逐手配对 **1.64×**。
但完成深度没有变化：`opening-adjacent` 与 `bench-midgame` 在两边都是深度 6，
只是从 1,324 / 986 ms 降到 580 / 502 ms；唯一紧预算局面 `bench-double-three`
在同样 1.6 秒里多搜 86% 节点，**仍未跨过第 6 层**。
（Phase 10B 的 1.40× 投影与这里的 2.27× 不矛盾：投影只算评估一项，且当时排序占比更高。）

## 7. 决定

1. **正确性成立**：可以放心地把它当作「与 `evaluateBoard` 等价的快速评估」使用。
2. **Phase 10B 当时不接入**：约 1.40 倍，复杂度（状态纪律、撤销出口、内存、与 TT/算杀的交互）
   不低，而且不改变搜索深度。
3. **Phase 10C 接入**：先做完排序优化，再按「精确 / 无状态泄漏 / 收益 / 内存 / 不动 core /
   不改评分语义」六条逐项核对，全部通过。`searchBoard` / `negamax` / `searchRoot`
   共 6 处改动；固定深度 2.27–2.30×、真实对局 1.64×，行为逐位不变。
4. **仍需守住的纪律**：将来在 `negamax` / `searchRoot` 里新增任何棋盘写操作，
   都必须紧邻调用 `place` / `undo`。漏一处不会报错，只会让叶子分数静默偏离当前局面。
