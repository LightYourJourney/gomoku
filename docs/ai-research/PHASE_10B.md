# Phase 10B · 搜索热点分析与增量评估实验

**一句话结论**：真实 CPU 的大头是**着法排序（47–48%）**，不是局面评估（30%）；
增量评估原型做到了与全盘评估**逐位相等**、单次生命周期快 **17–20 倍**，
但投影到整次搜索只有 **1.39 倍**，**不足以多搜一层**。
因此本阶段**不把增量评估接进正式 Negamax**，下一阶段先做排序优化。

## 3. 关键结果

### 3.1 CPU 花在哪

两份独立剖析（固定深度 / 真实预算）给出的分组一致：

| 分组 | 固定深度 | 真实预算 |
| --- | --- | --- |
| **着法排序**（buildLine / inBounds / scanLine / idx / orderMoves / threatScoreWith / 三二分析） | **46.9%** | **48.1%** |
| **局面评估**（scoreSegment / scoreLine / evaluateBoard） | **30.3%** | **30.2%** |
| 递归 Negamax | 3.5% | 3.3% |
| 候选生成 | 2.2% | 1.7% |
| 置换表 / 算杀 | <0.2% / <0.2% | <0.2% / <0.2% |
| 匿名内联帧 | 11.9% | 11.6% |
| GC | 0.44% | 0.46% |

**这推翻了此前的工程判断。** `AI_ENGINE.md` 原先写「局面评估是唯一瓶颈」——
实测不对：排序比评估贵得多。原因在下一节。

### 3.2 为什么排序这么贵

- 每个内部节点把 **56.1 个候选**全部打分，然后只留宽度 **12–14** 个：
  **约 78% 的排序计算被丢掉**。
- 每个候选要算**两次** `analyzeFast`（我方 + 对方），每次扫 4 个方向 × 9 格窗口。
- 一个节点的排序原料 **380–609 µs**，而一次叶子评估 **69–150 µs**。

### 3.3 `evaluateBoard` 的调用频率

- **每个搜索节点 0.69–0.73 次**（≈ 叶子占比）。
- hard 档 7,000 节点的搜索 ≈ 5,000 次评估；专家档 2 万节点 ≈ 1.4 万次。

### 3.4 增量评估

| 项 | 结果 |
| --- | --- |
| 与 `evaluateBoard` 一致性 | **逐位相等**（24 条用例、随机差分、变异测试验证鉴别力） |
| 生命周期（落子+取分+撤销） | **3.5–4.3 µs**，全盘评估 70–74 µs |
| 加速比 | **17.1–20.0×**（接近满盘 8.7×） |
| 初始化 | 67–74 µs（≈ 一次全盘评估） |
| 内存 | **≈2.96 KiB/实例**（强制 GC 后测量） |
| 递归树（同树只换叶子取分） | 9.9–13.2× |

### 3.5 端到端收益（投影）

评估只占 30%，所以即使叶子评估变得几乎免费：

| | 固定深度 | 真实预算 |
| --- | --- | --- |
| 可省时间 | 0.75 s | 1.08 s |
| 采样总时长 | 2.64 s | 3.83 s |
| **投影加速** | **1.39×** | **1.39×** |

而实测**每多搜一层需要 2.3–4.7 倍的节点**（深度 4→5 的三组：
786→1,788、890→3,962、1,117→5,282）。1.39 倍买不到一层。

## 4. 最终问题的答案

1. **真实 CPU 主要消耗在哪里？**
   着法排序 47–48%，局面评估 30%，递归 ~3%，候选生成 ~2%，置换表与算杀 <0.2%，
   GC <1%。排序的最大浪费是「给 56 个候选打分只用 12–14 个」。

2. **`evaluateBoard()` 在典型搜索中调用了多少次？**
   每个节点 0.69–0.73 次；7,000 节点的 hard 搜索约 5,000 次。

3. **增量更新能否与原有评分严格一致？**
   能。整数分值、同一份 `scoreLine`，逐位相等；24 条用例含随机差分与含五连终局。

4. **增量更新与撤销的总开销是多少？**
   一次「落子+取分+撤销」3.5–4.3 µs（快照局面），其中 `place` 4.1–14.1 µs、
   `undo` 0.04–0.31 µs、`score` 0.02–0.04 µs；`init` 67–74 µs。

5. **在不同局面下，预计或实测收益如何？**
   叶子层 17–20 倍；同树递归 9.9–13.2 倍；**整次搜索投影 1.39 倍**。
   接近满盘的收益最低（8.7 倍），因为那里评估本身只要 8.5 µs。

6. **额外内存和代码复杂度如何？**
   2.96 KiB/实例；原型约 180 行 + 24 条测试；不改生产搜索；
   若接入，需要一套严格的撤销纪律（单出口 / finally），并处理 TT 命中与超时返回。

7. **是否值得接入正式 Negamax？**
   **单独接入：不值得。** 1.39 倍不足以多搜一层，而复杂度与风险是实打实的。
   **但它没有被否定**：等排序优化把评估占比抬到 40–50%，它的收益会升到 1.55–1.6 倍，
   与排序优化叠加可达 ~1.9–2.1 倍。到那时再评估。

8. **如果不值得，下一阶段应该优先优化什么？**
   排序。顺序见 [OPTIMIZATION_CANDIDATES.md](OPTIMIZATION_CANDIDATES.md)：
   - **先做**：`inBounds` / `idx` 的内部快速路径（低风险，5–10%）；
   - **再做**：一次扫描同时算双方威胁（有「排序分值逐位不变」的等价判据，~13%）；
   - **然后**：候选预筛（收益最大 ~1.3×，但会改变搜索选择，必须用 Phase 10A 的
     评测器做 A/B，没有棋力证据不合入）；
   - 每做完一项重新剖析，不要同时改。

## 6. 局限（必须一起读）

1. **负载不可控**：机器全程跑着无关进程，绝对耗时在多次运行间相差 3 倍；
   占比与比值可引用，微秒数不要跨运行比较。
2. **样本是构造局面**：Phase 10A 的战术局面大多被算杀 / 捷径提前判掉，
   真正进 Negamax 的只有少数几个。真实对局的分布可能不同。
3. **端到端 1.39 倍是投影**，不是改造后的实测；公式与输入都写在
   [INCREMENTAL_EVALUATION.md](INCREMENTAL_EVALUATION.md) §6。
4. **匿名内联帧 10–12%** 无法精确归属，百分比只能当量级看。
5. **增量评估没有接进搜索**，所以「接入后不会引入新的状态 bug」这句话没有证据；
   它只证明了「独立使用时与全盘评估等价」。
