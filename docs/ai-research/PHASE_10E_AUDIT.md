**审计日期**：2026-10-21
**审计基线**：`8160d92`（工作区另有未提交的审计探针 `bench/strength/audit.probe.test.ts`）

## 0. 结论摘要

- **未发现 P0 / P1 缺陷。** 规则、搜索、置换表、增量评估、算杀在独立探针与差分测试里都保持一致。
- **核心性能结论可复现**：固定深度 16 个局面 **2.28×**（历史 2.27–2.30×），
  真实 hard 预算逐局面 **1.93–2.46×**；新旧引擎对局 107 个配对手**逐手指标完全相同**，
  墙钟比 1.52×（高负载下）。没有观察到决策语义变化。
- **棋力改善没有证据**：跑得更快不等于下得更好。A/B 棋谱逐手相同；难度参数也没有变。
  可以确认的是「同样的答案花更少时间」，而不是「新引擎更强」。
- **五档方向单调、无倒挂**，但样本量仍不足以把每一对都称为「明显更强」；
  战术题集出现天花板效应（五档均 15/15），测不出档位差异。
- **发现 1 个 P2、6 个 P3**，全部不阻塞运行时代码；P2 是 A/B 复现文档里的一条命令写错，
  P3 是陈旧注释、门禁提示措辞、剖析计数器、Worker 释放语义、历史 SHA 与战术题集饱和度。
- **发布结论：有条件可以发布。** 技术门禁全部通过；条件见 §7，主要是
  「先经批准部署隔离预览并跑线上 e2e，再发生产」，另需在发布说明里保留已知限制。
- **本阶段没有部署任何东西**，生产仍是 Phase 09B 构建。

## 4. 规则 / 搜索 / 增量 / 算杀的独立检查

### 4.1 规则

新增探针 `bench/strength/audit.probe.test.ts`（12 条，全部通过）覆盖：

- 四方向成五（横 / 竖 / 两斜）；
- 长连（≥5）判胜；
- 已占用点、越界、终局后落子被拒绝；
- 近满盘、边界局面；
- 合法着法一定落在空位。

`findWinLine` 用四个方向扫描并接受长度 ≥5；`validateMove` 检查轮次、状态、占用与越界。
没有发现规则层的确定性缺陷，因此没有需要「最小复现」的错误案例。

### 4.2 搜索树

- Negamax 视角：子节点取负、根节点从行棋方视角返回，符号一致。
- Alpha-Beta：根节点 `-Infinity..-alpha`，内部节点 `-beta..-lowerBound` 的窄窗与 fail-soft 返回值匹配。
- 结束条件：超时由注入时钟判定；`searchRoot` 在层末再查一次，未完成层整层丢弃。
- 候选与排序：空盘天元、必胜、必防三条捷径在搜索前；宽度参数只影响根/内部候选数。
- 深度：`maxDepth` 是上限，超时会退回上一层结果（实测专家 2.66 s 时深度 6/7）。

### 4.3 置换表

- 两张 32 位表（hi/lo），`probe` 先比 hi、再比 lo、再比深度；冲突时保留更深条目。
- exact / lower / upper 的写入条件与查询裁剪正确；`toTableScore/fromTableScore` 按 ply 归一化必胜分。
- 同一局面不同路径：键只由棋盘与行棋方决定，探针验证落子/撤销可逆、黑白互换键不同。
- 根节点不写表（后代不可能命中根键），避免无效条目。

### 4.4 增量评估

- 构造时复制棋盘，逐线算黑白分；落子只重算经过该点的 2–4 条线，撤销恢复旧值。
- 随机差分（含随机穿插撤销、接近满盘、含五连）与 `evaluateBoard()` 逐位一致。
- 搜索中 `place/undo` 与棋盘写操作成对，超时返回路径也会撤销。
- 未发现缓存污染或状态泄漏；唯一问题是文件头仍写着「不是生产路径」（P3-1）。

### 4.5 算杀（VCF / VCT）

- VCF 只枚举冲四与成五应手；对手有反先成五时不算杀；超时返回 `NO_WIN`，绝不返回未验证着法。
- VCT 仍默认关闭；打开时完整枚举防守，代价 38–520×，结论无差。
- `maxPlies` 只作剪枝上界，不改变可搜到的杀；测试覆盖 1/3/5 手、无杀、反杀、满盘、超时。
- 随机 60 个局面 × 双方 × 三组对照，`plies` 逐组相等（10D 已归档）。

### P2-1 · A/B 复现文档把「旧版」也指向当前源码

- **描述**：`ENGINE_AB_RESULTS.md` §6 的旧包构建命令是
  `bundle-engine.mjs --root . --out .../base-6e16ed0.mjs`，`--root .` 指向当前工作树。
  照抄会打出「当前源码 vs 当前源码」，比值约 1.0，读者会误以为 2.27× 不可复现。
- **复现**：在干净工作树执行 §6 第一条命令，再执行 A/B；两边模块 digest 相同，比值≈1。
- **影响**：只影响文档复现，不影响生产代码或已归档结果；但会误导独立复核者。
- **证据**：`docs/ai-research/ENGINE_AB_RESULTS.md:111`；`bundle-engine.mjs` 头部要求用 worktree。
- **根因**：写文档时省略了 `git worktree add <旧提交>` 这一步。
- **修复建议**：改为先在 10C 之前的提交建 worktree，再 `--root <worktree>`；
  同时注明重写后 SHA 已变化，按 `HISTORY_REWRITE.md` 取当前历史里的对应提交。
- **回归测试建议**：复现脚本打印两个模块的 SHA-256；若相同则直接失败并提示「旧包指错了」。

- **回归测试建议**：无需运行测试；可在 review checklist 里加「注释与接入状态同步」。

### P3-2 · 基准门禁的跳过提示把「耗时占比」说成「余量」

- **描述**：`bench/gate.mjs:83-89` 对 `gated=false` 行打印
  「本次耗时占预算 52%，余量不足 20% 这条线」。52% 的余量是 48%，并不「不足 20%」；
  真实判据是「耗时占比 ≤ maxBudgetRatio（20%）」。
- **复现**：`yarn bench:check`，看 hard|开局 的跳过行。
- **影响**：只影响输出可读性；跳过决定由冻结基线决定，判定本身正确。
- **证据**：`bench/gate.mjs:88-89`；本机运行输出。
- **根因**：措辞把「utilization ≤ 20%」写反成「margin ≥ 20%」。
- **修复建议**：改成「耗时占预算 52%，超过 20% 的断言线」。
- **回归测试建议**：给 gate 的消息拼装加一条快照测试。

### P3-3 · 剖析脚本的 `evaluateCalls / evaluateShare` 在增量评估接入后恒为 0

- **描述**：`bench/profile/cpu.profile.ts` 仍用 `counter.evaluateBoard` 与采样函数名
  `evaluateBoard` 代表叶子评估；10C 起叶子走 `evaluator.score()`，于是归档 `0722` 的
  `evaluateCalls=0`、`evaluationsPerNode=0`、`evaluateShare=0`。CPU 采样里的
  `scoreSegment` 等仍真实，但派生指标会误导。
- **复现**：跑 `yarn profile` 看 `derived`；或读归档 `runs/2026-10-21_0722-phase10c-cpu-profile.json`。
- **影响**：只影响剖析报告，不影响产品与门禁。
- **证据**：`bench/profile/cpu.profile.ts:147-156`；归档 `derived`。
- **根因**：10C 接入增量评估时没有同步调整计数器口径。
- **修复建议**：给 `IncrementalEvaluator.score` 加计数器，或把派生字段改为
  「叶子取分次数（增量）」并从 `place/undo` 采样；同时保留旧字段但在接入后标 null。
- **回归测试建议**：剖析脚本对一次搜索断言「叶子取分次数 ≈ 节点数」。

### P3-4 · `AiEngine.dispose()` 不终止 Worker

- **描述**：`dispose` 只置 `disposed` 并拒绝 pending，不调用 `worker.terminate()`；
  当前应用在模块作用域创建一个 Worker 且从不 dispose，所以没有现时影响。
- **复现**：调用 `createBrowserAiEngine().dispose()` 后，Worker 仍存活（需在浏览器里观察）。
- **影响**：潜在；未来若在路由/测试里反复创建引擎会泄漏 Worker。
- **证据**：`src/ai/engine.ts:61-65`；`src/ai/browserEngine.ts` 未暴露 terminate。
- **根因**：`dispose` 的语义被定义成「拒绝未决请求」，没有覆盖 Worker 生命周期。
- **修复建议**：让 `createBrowserAiEngine` 在 dispose 时 terminate；或把方法改名为
  `rejectPending()`，另加 `terminate()`。
- **回归测试建议**：浏览器/Worker 测试里 dispose 后断言 `worker` 的 terminate 被调用。

### P3-5 · 历史文档里的旧 SHA 在重写后不可解析

- **描述**：`AI_ENGINE.md:301` 的 `git show 7a08f32:...`、`ENGINE_AB_RESULTS.md` 与
  `PHASE_10C.md` 里的 `6e16ed0` / `8f3fbb8` 都是重写前标签，当前仓库无法解析。
- **复现**：`git cat-file -t 7a08f32` → 不存在。
- **影响**：复现路径断链；`HISTORY_REWRITE.md` 已说明原因，但没有逐条映射。
- **证据**：`docs/HISTORY_REWRITE.md`；`docs/AI_ENGINE.md:301`。
- **根因**：2026-10-21 全历史重写（隐私脱敏）改变了所有哈希。
- **修复建议**：新增文档不再引用旧 SHA；历史文档在页首加一句「SHA 为重写前标签」，
  或补一张「旧标签 → 当前提交」的映射表。
- **回归测试建议**：无自动测试；可在文档检查脚本里禁止新增 7 位十六进制 SHA。

### P3-6 · 战术题集饱和，测不出档位差异

- **描述**：五档 16 题全部 15 通过 + 1 诊断；`double-threat` 是「已经赢定」的局面，
  任何合法着法都满足强制胜。该题集只能证明「没有明显战术错误」，不能证明梯度。
- **复现**：`yarn tactics`；看五档相同结果。
- **影响**：10D 的「战术上五档都能正确处理」成立，但不能推出「高档战术更强」。
- **证据**：`runs/2026-10-21_11-15-18-153-tactics.json`；`TACTICAL_STRENGTH.md` 已自述天花板。
- **根因**：题集以一手必胜/必防为主，难度低于中高档的实际搜索深度。
- **修复建议**：新增多手、带反先、需要防守交换的题集；每题给出独立证明器的完整应对树。
- **回归测试建议**：新题集要求至少有一档失败或耗时显著不同，否则视为题目无区分度。

## 7. 发布判断

**结论：有条件可以发布。**

技术侧：候选构建通过全部本地门禁、生产构建冒烟、真实浏览器验收与 CI；
没有 P0/P1；性能与等价性结论可复现；旧存档 schema 未变。

条件（都不是运行时代码缺陷）：

1. 经用户明确批准后，先把候选构建部署到隔离预览项目（`gomoku-lab-preview`），
   对新构建跑 `REMOTE_BASE=<预览地址> yarn e2e:remote`，要求 162/162。
2. 预览通过后再手动发布生产；发布后对 `https://gomoku-lab.pages.dev` 再跑一次
   `e2e:remote`，并核对 `_headers` / Worker 加载 / 缓存。
3. 发布说明保留已知限制：专家档 P90/P95 = 2600 ms、约 43% 搜索超时；
   战术题集饱和；仅 Chrome 实测；无低端真机数据。
4. 不修改生产域名、环境变量、数据策略或权限；本次审计没有做任何部署。

## 8. 任务书十个问题

1. **AI 引擎是否比 Phase 10 开始之前更快？**
   是。固定深度 2.28×；真实 hard 预算逐局面 1.93–2.46×；
   相同棋谱的配对对局总耗时 1.52×（高负载）／归档 1.64×。

2. **在什么局面下更快？**
   所有被测固定深度局面都更快：开局 2.26–2.83×、中盘约 2.3×、接近满盘 1.25×
   （残局只有 265 节点，初始化成本占比高）。真实预算下 1.9–2.5×；
   VCF 与候选生成未优化，真实对局整体比值因此低于固定深度。

3. **实际棋力是否改善？**
   **没有证据。** 新旧引擎在 16 个固定局面、107 个真实对局配对手上决策完全相同；
   难度参数未改。可以说「同样决策更快」，不能说「更强」。
   专家档在真实预算下是否因更快而多完成一层，本次没有做逐手等价对照，不能推断。

4. **改善证据是否可信？**
   可信度较高，但范围有限：两边都是独立打包产物、12 轮严格交替取 min、
   同会话真实预算、原始 JSON 归档；独立复现 2.28× 与历史 2.27–2.30× 一致。
   限制是单机、负载敏感、只有 16 个固定局面。

5. **是否引入新的搜索错误？**
   未发现。独立探针 12 条、增量/等价/置换表/算杀四个测试文件 66 条、
   四局 A/B 逐手一致、浏览器五档与超时回退均正常。没有 P0/P1。

6. **五档难度梯度是否合理？**
   方向合理且无倒挂：10D 合计高档 68.8–75.0%，独立 smoke 69.2%；
   入门 vs 初级在独立 smoke 里 50%，这一对最弱。CI 很宽，
   不能把每一对都称为「明显更强」；参数保持不变有实验依据。

7. **搜索最严重的剩余瓶颈是什么？**
   算法侧：`scanDirection` 占 10C 样本约 38.5%，`analyzeFast` 8.5%，
   即候选生成/排序中的棋型扫描；叶子评估已不再是主成本。
   产品侧：专家档的时间管理——43% 的搜索在 2600 ms 内没搜完，P90/P95 顶满预算。

8. **有没有不值得保留的复杂优化？**
   没有发现。增量评估约 200 行、+2,961 B/次搜索，换来 2.28×，且有逐位等价测试；
   排序融合与行缓冲是局部改动。没有并行评估器、重复缓存或未使用原型。
   代价是测试面变大，但属于必要成本。

9. **生产 Worker 是否稳定？**
   是。候选构建在生产预览路径下 Worker 正常加载（`e2e:prod` 5/5）；
   真实浏览器每页 1 个 Worker，25 轮操作无增长，旧响应被 requestId/gameVersion 丢弃；
   线上旧构建跑完整 e2e 162/162。限制：仅 Chrome，未测 Safari/Firefox 与低端真机。

10. **是否可以发布新版本？**
    **有条件可以发布。** 条件见 §7：先预览部署并跑线上 e2e，再生产部署并复验；
    发布说明保留专家等待与测量边界。技术门禁与运行时候选没有阻塞项。

## 9. 本阶段没有做什么

- 没有部署到 Cloudflare（生产或预览），没有改域名、环境变量、数据策略或权限。
- 没有修改任何正式难度参数、评估权重或搜索策略。
- 没有为了通过门禁调整 `bench/baseline.json`、测试棘轮或 CI 阈值。
- 没有做低端真机、Safari/Firefox、多小时 soak、Worker 堆测量。
- 没有对专家档做「新旧引擎真实预算逐手等价」对照（只做了 hard 与固定深度）。
- 没有重跑 standard 规模的五档棋力矩阵（每对 16 局）；本次只做 smoke。
  10D 的矩阵结论按原报告与其 CI 引用，未被独立扩大样本复核。
