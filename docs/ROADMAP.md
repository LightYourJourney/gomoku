## Phase 2 · 强化 AI ✅

**验收标准**：AI 能识别直接获胜、必须防守和常见战术威胁，且界面不被搜索阻塞。

- [x] 棋型识别改为**窗口枚举**（含跳三、跳四等隔一子结构）。没有走「模式串匹配」那条路：枚举包含落点的全部 5 个五连窗口，隔子型的空位自然落在窗口里，比维护一张模式表更短也更不容易漏。
- [x] 置换表（Zobrist 哈希，双 32 位半值），配合杀手着法
- [x] 迭代加深调优：合并了排序与必胜判断的重复扫描，把算杀限制在 35% 预算内——**但「时间预算真正转化为棋力」只做到一半**，专家档的深度上限仍未达到，见下方已知不足
- [x] 算杀搜索：连续冲四取胜（VCF）已启用；威胁空间搜索（VCT）已实现并有测试，但实测代价是 VCF 的 **38–520 倍**，且没有任何一个被测局面是 VCF 找不到而 VCT 找得到的，**默认关闭**
- [x] 双威胁识别：双四、四三、双活三（`shapeScore` 的组合加成）
- [x] 开放中级 / 高级 / 专家三档；档位差异由 `difficulty.test.ts` 的**深度接线测试**（给足时间时每档都完整搜到自己上限、上限越高实际越深）与 `yarn bench` 的实测数据负责——自对弈测试为了控制时长把深度钳到 3，三档走出的棋完全一样，证明不了强弱
- [x] AI 提示：紧急度徽标、**结论可靠度**（精确 / 启发式，超时回退时如实告知）、前 3 个候选（坐标 + 评分 + 攻防棋型中文说明）、棋盘上的编号标记
- [x] 提示固定使用 `purpose: 'hint'` 的只分析请求，绝不落子；与落子请求共用引擎但互不挤占
- [x] 引擎对局测试：`src/ai/selfplay.test.ts`（六个用例）——**保留在测试套件里**，没有拆成独立脚本。它把深度压到 3 以控制时长，档位差异靠算杀开关体现；固定时钟保证同一开局跑两次得到完全相同的棋谱。

Phase 2 结束后跑过一轮两轴代码审查，另做了一轮 3 次自审 + 1 次终审的计划评审（记录在 `docs/superpowers/plans/2026-10-10-gomoku-lab-phase2.md`）。

**已知不足（不阻塞验收，转入 Phase 5）**：

- **专家档的深度上限（8 层）从未达到**：构造基准上最多 6 层，真实对局中观察到 7 层；高级档用 1.1 秒就能完成基准上的同样 6 层。要让它名副其实，得先把单节点成本压下去。
- **单次 `evaluateBoard` 约 76 µs**（归档 `7a08f32` 实测 76.3；多次运行落在 70–82 µs），是当前真正的瓶颈。下一步性能优化应该做增量评估（只重算受落子影响的线段），而不是继续调 alpha-beta。
- **不算 VCT**，也找不到需要两层以上活三的杀型。实现与测试都在，按需可开。
- **局面评估不识别跨方向的组合形状**：单点分析有双四/四三/双活三的加成，整盘评估仍是按线段独立累加。
- 提示的棋型分析（`analyzePoint`）确实比 `analyzeFast` 贵（实测约 **3.4 倍**），但绝对量很小：整轮提示分析（44 个候选点、攻防各一次）实测 **0.53 ms**——相对数百毫秒的预算可以忽略。做成开关不是为了省钱，而是出出着法时这两个字段根本不会出现在响应里。
  > 这一条原先写的是「比搜索贵得多」，**是错的**（差三四个数量级）。`docs/AI_ENGINE.md` 的「已知局限」第 6 条已更正，这里同步。

## Phase 3 · 教学与残局 ✅

**验收标准**：课程与题目真实可操作、可完成，答案经过验证。

- [x] 数据驱动的课程运行器：讲解页（含**手顺演示**，用 `replay` 逐手还原）+ 练习（棋盘操作 + 即时反馈）
- [x] 8 节课程：基本规则、活二与眠二、活三与眠三、冲四与活四、双三与双四、如何防守、常见进攻组合、基础必胜战术
- [x] 15 道残局题，覆盖六个分类（一步获胜 / 挡住直接胜着 / 构造活四 / 双重威胁 / 连续冲四 / 强制获胜路线）
- [x] **解法由搜索证明，不写死坐标**：题目只声明局面与目标谓词，判定用引擎自己的棋型分析与算杀
- [x] 错误解释（算出来的，不是写死的）、三级渐进提示、重试
- [x] 学习进度存 IndexedDB，含「上次停在哪节课 / 哪道题 / 哪一页」，刷新后回到原处

`content.test.ts` 是这一阶段的验收装置：它把 8 节课 + 15 道题逐个跑一遍求解器（`solveMove`），并检查开局没有分出胜负、题目本身成立、手数奇偶一致。**第一次跑就抓出 13 个问题**（9 处手数奇偶对不上、2 道「挡成五点」的题里白棋其实是活四根本堵不住、1 道斜线活三的一端被自己的白子堵死、1 处棋盘写成 16 行），逐条修的是题目而不是断言。

**已知不足（不阻塞验收，转入 Phase 4/5）**：

- **课程内容没有难度梯度之外的个性化**：做错了只是给一次重试，不会记下「这个人在活三上反复出错」并回头补课。真正的自适应教学要等有了错题统计之后。
- **残局题只有 15 道，且都是黑先**。白先、以及需要多手规划才能看出杀机的题目还没出。
- **没有 7 手以上的强制取胜题**。五处 `forcedWin` 目标（题库四道 + 第 8 节练习）实测**全是 5 手取胜**，没有一处是 7 手；其中只有 `forced-counter` 声明 `maxPlies: 7`（**上界不是紧界**），其余四处在第四轮审查时已逐个量过并收紧到 5。构造一条真正 7 手的链需要在两条线的交叉处制造两次「冲四 + 活三」，而那样的盘面在根节点上就已经存在五手杀——求解器先找到的就是它。**造不出来就如实记成没有，不编一个更深的。**
- **学习进度没有迁移机制，只有「版本不符即弃」**：`progress.ts` 的版本闸门（`PROGRESS_SCHEMA_VERSION`）在字段形状变化时会**静默清零全部存量进度**——老数据没有这个字段，读回来就是 null。Phase 3 内这样是安全的（第一个版本还没有任何用户），但正式发布后每次递增版本号都意味着用户白学一遍，除非先补上迁移函数。
- 讲解页的手顺演示只能前进后退，没有自动播放。

## Phase 4 · 棋谱与复盘 ✅

**验收标准**：对局可以保存、恢复、回放并进行真实分析。

- [x] 棋谱库迁到 IndexedDB，支持多局保存与载入（终局自动入库，`onGameEnd` 只在「进行中 → 终局」这一跃迁上回调一次）
- [x] 任意回合回放：上一步 / 下一步 / 跳转 / 自动播放（游标 + `replay(moves.slice(0, cursor))` 纯派生局面）
- [x] 落子编号显示（小半径编号徽标，棋子露在数字外面——否则看不出每手是谁下的）
- [x] 基于有限搜索预算的失误识别（逐手跑引擎，按分差排序取前 3）
- [x] 分析结论注明引擎版本（`ENGINE_VERSION`）、档位与预算；**不设「最佳 / 失误」固定档位**，只给分差与可靠度
- [x] 分析结果缓存（会话内，键掺引擎版本 + 档位 + 预算）
- [x] 关键局面分析与推荐着法（列出实际着法与引擎推荐坐标）

**实测**：9 手对局 = 9 个局面请求（相邻手共享后续局面请求，不是 18 个），400ms 预算串行约 4 秒跑完。

**已知不足（不阻塞验收，转入 Phase 5）**：

- **分析缓存只在复盘页打开期间有效**：缓存随页面的两个 store 一起创建，离开复盘页即失效（在跑的分析会被丢弃结果；引擎没有取消接口，已发出的那一次搜索仍会跑完，最多一个 400ms 预算）。结论还依赖 `ENGINE_VERSION`，跨会话持久化的收益撑不起失效管理，先不做。因此来回翻看同一局会重跑一遍（9 手约 4 秒）。
- **分析编排是朴素版**：逐局面串行，相邻手共享后续局面请求（N 手 = N 个请求）。没有做「整局一次性批处理」那种更省的方案；当前规模够用。
- **回放游标不持久化是有意的**：它是浏览行为，不是学习进度；刷新后从第 0 手开始。
- **分析固定用「初级」档 + 400ms 预算**（结论区标注得很清楚）。高档位/长预算的分析没有入口——那属于「想深挖某一手」的场景，等有需求再说。
- **同一时刻只分析一局**：换一局会停掉上一局的分析。
- **满盘和棋的末局无结论**：那一手之后已经无棋可走，引擎没有可比的首选着法，该手直接跳过（不编造结论）。

## Phase 5 · 最终打磨 ✅

**验收标准**：稳定、交互完整、无关键规则错误、可实际部署。

- [x] 视觉细节打磨与动画节奏调整 —— **用纯 CSS 做完了，没有装回动画库**。四个 `@keyframes`（落子落下、最后一手脉冲、面板淡入、反馈条滑入）加一条 `prefers-reduced-motion` 媒体查询就够了；引一个运行时库来换这四个效果不划算，而且 `motion` 在 Phase 1 就是因为「装了但全库零引用」被移除的
- [x] 移动端与平板适配复核：`tablet` 项目（iPad 横屏 + 触摸）7 条用例——无横向溢出、三栏不压盖、竖屏退化为堆叠、四角与四边中点命中、拖动不落子、连点只落一子、AI 思考期间触摸无效
- [x] 音效与动画完善：胜负音（上行 / 下行）；`arm(target)` 在首次 `pointerdown` 里 `createContext()` **并 `resume()`**——只 create 不 resume 等于白造一个被挂起的上下文
- [x] 性能优化（首屏、搜索、渲染）—— **实测后判定不做**，见下
- [x] 错误处理与错误边界：顶层 `AppErrorBoundary`，兜底界面用最简 DOM，不依赖 store / 主题 / 自有组件
- [x] 自动化测试补全：键盘操作（方向键 / Home / End / Enter / 空格）与 ARIA grid、状态播报、`prefers-reduced-motion`
- [x] 发布构建与部署配置：`yarn e2e:prod` 独立通道跑 `dist`；`VITE_BASE` 支持子路径部署
- [x] 使用文档：[docs/USAGE.md](USAGE.md)

**性能：测过、不做**（数字见 [TEST_REPORT](TEST_REPORT.md) 的「Phase 5：性能实测」）

| 候选 | 实测 | 结论 |
| --- | --- | --- |
| 棋盘 225 个命中 `<rect>` 每帧重建 | 落子一手 click→React 提交中位 **0.30 ms** | 差三个数量级，加 `React.memo` 只换来一层要维护的依赖比较 |
| 把教学 / 题库拆出主包 | 首屏「应用自身」共 **136 ms**，拆出去的份额按源码算约两成 | 省个位数到几十毫秒，却要给教学页加 Suspense 边界、额外 chunk 请求与加载态 |

**已知不足（不阻塞验收）**：

- **性能结论有前提**：上面两条的「不做」建立在当前渲染路径上。若棋盘将来改成每帧重绘（拖拽预览、动画重采样），落子成本必须重量一遍再决定。
- **`bench:render` 的数字受机器负载影响**：探针量的是墙钟时间，负载高时只会偏高（所以是保守上界）。要拿绝对值请在空闲机器上跑。
- ~~**基准仍不做断言**~~：**2026-10-13 已偿还**——`yarn bench` 有阈值了（`yarn bench:check`，
  只断言余量充足的行与机器无关的不变量），CI 里也在跑。`yarn bench:render` 仍是只产数字：
  它量的是墙钟时间（见上一条），跨机器设阈值会变成假红制造机。
- **子路径部署没有自动化用例**：`VITE_BASE` 的效果靠构建产物断言（见 README 的两条 `grep`），没有 e2e 覆盖。
- **复盘页对读屏用户只是一张图**：回放棋盘 `interactive={false}`，走的是 `role="img"` 加一句「已落子 N 手、最后一手在 X」。逐手编号是画在 SVG 里的文字，读屏读不出来，也没有实时播报——要做得先给回放设计一套可读的逐步导航。

## UI/UX 改版 · Phase 03（棋盘质感、交互反馈与 AI 信息呈现）✅

**注意编号**：这一阶段的任务书与 `ui-redesign/PLAN.md` 的 Phase 03 不是同一批工作
（交集只有 F-UI-03）。完整记录见 [ui-redesign/PHASE_03.md](ui-redesign/PHASE_03.md)。

**修掉两条真缺陷**（都带实测证据）：

- **最后一手不再是一圈红环。** `--c-danger` 是「认输 / 错误 / 判错」的颜色，
  而最后一手只是正常的落子；量上更站不住——环的着墨是一颗棋子的 36%，
  却是整块棋盘上**唯一带色相**的东西。改成**与所在棋子反色的小点**（半径 0.13 格，着墨少 76%），
  黑白子上都清楚（实测 6.63:1 / 12.69:1）。
- **多字标记不再溢出底色。** 真实浏览器 `getBBox` 实测：`补这里` 三个字比底色圆宽 **87%**，
  白字落在浅色木纹上等于看不见。改成**底色随文字生长的 pill**（一个字仍是圆），
  并钉住不变量 **pill 半宽 < 1 格**——相邻棋子的中心永远露着。

**AI 面板改成两级信息**：默认层是一句由真实引擎输出（`reason` / `confidence`）生成的中文，
技术详情（深度 / 节点 / 耗时 / 评分 / 判断 / 结论 + 算法说明）收进「?」。
顺带修掉默认层暴露 `Web Worker` 的实现细节（`DESIGN_SYSTEM.md` §7 的禁用清单第一条）。

**顺带达成的**：`PLAN.md` 验收标准 1 的两行——`battle-midgame` @1440 右栏溢出 **0**、
`battle-hint` 棋谱顶边 **605 ≤ 750**（第二轮收紧侧栏之后；此前 617）。
（`battle-hint` 的右栏溢出另算：进本阶段时是 **143**，两轮收紧后到 **0**，
逐档数字见 `PHASE_03.md` §13 与 §14。）为让这条判据第一次真的可判，
探针的 `headings` 补了 `top`/`h`（此前只记 `level` 与 `text`，**几何根本读不到**）。

**一次都不跑却照样印 ✓**（第一版就是这样：令牌是十六进制而解析器只认 `rgb()`，74 行全是空的）。

**测试**：单测 912 → **958**，e2e 103 → **116**（两个棘轮的基线都只许涨，`yarn gates` 实测通过；

## UI/UX 改版 · Phase 05（残局挑战重构）✅

**注意编号**：任务书的「Phase 05」与 `PLAN.md` 的 Phase 05（状态、反馈与错误）**不是同一批工作**
——后者在 Phase 02/03 里就已经交付了。完整记录见 [ui-redesign/PHASE_05.md](ui-redesign/PHASE_05.md)。

**残局从「题目目录」变成训练流程**：首页顶部是总进度与「继续挑战：<题名>」，
每个分类标题带自己的 `X / Y`，卡片补上它属于哪一类；详情页题名升 `h1`；
做对之后「下一题 →」可以一路练下去，做完一类给分类完成提示，做到最后一题给结束状态，
全部做完通向实战。课程页与残局页的进度区抽成了共用的 `ProgressBlock`
（进度条、载入占位、`progressbar` 的 aria 只有一份实现）。

**一处真缺陷，写 e2e 时才暴露**：「走到题库的最后一道」与「全部做完了」被混成一个状态，
于是直接进去做最后一题会说「15 道题都通过了」——而列表**不锁顺序**，那是允许的路径。
这与 Phase 04 抓到的「全部课程讲完了」**完全同形**（同一个错误在这个项目里犯了两次），
所以修法不是顺手判一下：它现在是一个显式字段 `allSolved`，两条路径各有用例。

**三个刻意的「不做」**：不编难度等级（题库 15 道题**没有任何难度字段**，
分类的先后是**教学顺序**，文档如实这么写）；不做星级 / 积分 / 排行榜 / 成就
（任务书 §九 点名禁止，且本应用没有账号体系）；**不加持久化字段**
（`solvedPuzzles` 已经够，分类进度、推荐、完成提示全部派生，`PROGRESS_SCHEMA_VERSION` 仍是 1）。

**一处真实的界面不一致被修掉**：用满三级提示拿到点位之后，只要落一手别的，
棋盘上「解」的标记就消失，而提示面板还写着「棋盘上标出了其中一种解法」。
现在判错时两个标记并存（「错」在你的落点、「解」在解法点），判对时只留「对」。

**测试**：单测 984 → **1028**（60 个文件）、e2e 121 → **141**

验收时补的，见 `PHASE_05.md` §15.1）、探针 29 → **34** 个状态 / 236 → **276** 张。

### 第二轮：两轴审查与整改（固定点 `891b4ac`）

  `lastVisited` 在退出到列表时被清成 `null`，读它的分支**到不了**（与 Phase 04 删掉的
  `resolveNext` 优先分支同类）。代价是刷新后偏好丢失，如实写在文档里。
- **首次完成提示**：首次说「第一次做对这道题。」、重进已通过的题说「这一题已经通过。」
  （靠挂载时的一次快照区分，`PuzzleView` 因此要按题重建）。
- **平板 768–1023 只在横屏改双栏**：新增 `wide-layout` 变体
  （`≥1024`，或 `≥768 且横屏且高度 ≥500`），竖屏保持纵向——那时纵向让棋盘吃到
  **478px**（实测），改双栏只剩约 408px，**缩棋盘换同屏不划算**。
  `min-height` 那一条拦住横屏手机（915×412），三条 e2e 守着。

**难度分级仍然不做**：任务书 §三 的原话是「没有独立难度数据时，**不得**随意生成
「简单 / 困难 / 大师」等级冒充客观难度」——题库 15 道题没有任何难度字段。

**第三轮**（同一命令，固定点 `2464b2f`）报了 12 条，复核后**全部成立**——包含两条
**推翻我自己结论**的：`wide-layout` 在 768–1023 横屏击穿了棋盘 320px 底线
（我写下的阈值依据算错了，根因是 `BoardStage` 的解除条件没跟着换），
以及「提示文案与标记绑在同一变量上」**并没有真的绑在同一处**（`win-h` 两端都能成五，
走另一头就对不上）。另修了一条硬违规：重进已通过的题时同屏两颗可用的实心主按钮。

**反向验证 4 条**（按类推荐、首次判定、提示文案条件、两栏高度下限），
每条精确注入，全部按预期变红。

## UI/UX 改版 · Phase 06（棋谱复盘与 AI 分析重构）

依据：用户在 2026-10-16 给出的 Phase 06 任务书。计划与实施记录见
[`ui-redesign/PHASE_06.md`](ui-redesign/PHASE_06.md)（含侦察结论、两轮独立终审与逐条整改）。

**做了什么**

- **复盘空状态**从两行字改成引导区：图形标识 + 标题 + 说明 + 「开始一局对战」
  主操作（**真的切到对战页**）。**不做示例棋谱**——任务书 §二 说本阶段默认不新增，
  而一个装饰图形不会被误当成真实对局。
- **棋谱库**的呈现项（胜负 / 人机双人 / 手数 / AI 难度 / 认输信息）此前已经齐了，
  本阶段补的是**读不出来时怎么办**：`list()` 加了两个信号——`degraded`
  （存储不可用，数据来自内存兜底）与 `skipped`（读到了但没通过校验被丢掉）。
  界面**如实说明**，不再把两种情况一起伪装成「你还没下过棋」。
- **回放时间轴**：原生 `<input type="range">`，键盘（方向键 / Home / End）与
  读屏支持几乎白送；上一步 / 下一步 / 跳到开局 / 跳到终局 / 自动播放 / 暂停
  全部就位。**播放位置始终只有 `replayStore` 一个游标**（任务书 §五 的硬要求）。
- **播放速度**三档：慢 1400 / 标准 900 / 快速 400 毫秒。
  `REPLAY_STEP_MS` **保留**为「标准」档的值——三个文件 import 它，删掉就是成片红。
- **点分析结论跳转**：点「第 17 手」→ `goTo(moveIndex + 1)`。
  「当前选中」**不新增状态**，由游标推导——所以不可能出现
  「棋盘停在第 5 手、面板说选中第 7 手」这种分叉。

**顺手修掉的三个既有缺陷**

1. **`play()` 在终局不检查 `hasNext`**：按「自动播放」会先把按钮变成「暂停」，
   等一个 tick 才发现到头、再弹回来。现在终局压根不启动。
2. **`analysisStore.stop()` 不清 `verdicts` 与 `total`**：换棋谱之后，面板会拿
   **上一局的结论和计数**继续渲染。修法**零 store 改动**——`target` 里带着 `seq`，
   界面对一下就知道结论属于哪一局。
3. **复盘回放页整页没有 h1**（只有 `h2 回放` / `h2 引擎分析`）——
   教学练习页与残局详情页在 Phase 04/05 都修过同一个毛病，这是第三处。

**数据结构没有变**：`GameRecord` 一个字段没动，`GAME_RECORDS_SCHEMA_VERSION` 仍是 **1**，
**存量棋谱照常读取**。棋谱里**没有、也不该有**时间戳（`Date.now()` 的调用只允许出现在
`ai/search.ts`，先后由 IndexedDB 自增主键表达；补上去会让所有存量棋谱作废）——
所以列表**不显示时间**，任务书 §三 问的「如果真实存储了时间」答案是「没有」。

**测试**：单测 1028 → **1046**（61 个文件）、e2e 141 → **145**、
探针 34 → **38** 个受控状态 / 276 → **308** 张。
新增的是 `replayStore` 7 条（速度档、终局不启动、手动定位暂停）、
时间轴 7 条、复盘页 3 条（详情页 h1、空状态跳转、当前手半径），e2e 4 条。
**反向验证 5 条**（速度不残留双表、终局不启动、手动定位暂停、off-by-one、
`getTimerCount`）——全部按预期变红，跑完即还原。

**探针抓到过我一次**：新加的高亮卡片写了 `bg-accent-soft` 却没换文字色，
16 处对比度违规（浅色 4.49:1 / 深色 3.91:1）。改成只改边框。**同一轮里，
同一个坑踩了两次**——纸上想明白过一次（否决给当前手换 tone），代码里没想起来。

**没做到的一条，如实记**：`F-UI-14`（回放落子编号只有 6.91px）**修不掉，只缓解**。
字号 = `radius × 1.25` 用户单位，而小半径是为了让棋子露在编号外面（`Board.tsx` 的注释）。
当前手放大到 0.32 已经是极限——再大就把棋子的可见边吃掉了（`STONE_RADIUS = 0.44`）。
要真达标得改掉「小半径」这个设计前提本身（编号要么盖住棋子、要么另找载体），
**超出本阶段范围**。任务书 §七 那句「不能因此丢失查看完整手顺的能力」也是这么守的：
没有减少编号数量，因为复盘页**没有手顺列表**，编号是唯一载体。

## 长期待办

以下事项已识别但尚未排期：

- **增量局面评估**：当前 `evaluateBoard` 每次重扫全盘（约 76 µs/次，归档 `7a08f32`），是搜索的主要开销。改成只重算受落子影响的 4 条线段后，专家档才有可能真正搜到第 7 层。

- **Web Worker 降级**：极老的浏览器不支持 module worker 时目前没有回退路径。
