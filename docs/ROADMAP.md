# 路线图

## 总览

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| Phase 1 | 规则 + 棋盘 + 初级 AI + 悔棋重开 | ✅ 已完成 |
| Phase 2 | 棋型 + 搜索强化 + 五档难度 + AI 提示 | ✅ 已完成，待验收 |
| Phase 3 | 互动教学 + 残局挑战 | ⏳ |
| Phase 4 | 棋谱持久化 + 回放 + AI 复盘 | ⏳ |
| Phase 5 | 视觉打磨 + 移动端 + 音效 + 自动化测试 | ⏳ |

一次只推进一个阶段，每个阶段跑完「类型检查 → 单元测试 → 生产构建 → 真实浏览器验证」再进入下一个。

## Phase 1 · 基础可玩版本 ✅

**验收标准**：真实玩家能与电脑完整对战一局。

已完成：

- 工程初始化（Vite 8 / React 19 / TS 6 / Tailwind 4 / Zustand 5 / Vitest 5 / Playwright）
- 设计令牌与深浅两套主题
- 15×15 棋盘 SVG 渲染，自适应尺寸、四条边坐标、落子预览、最后一步标记、胜利连线高亮
- 完整规则模块（纯函数、与 UI 完全分离）
- 初级 AI，跑在 Web Worker 中
- 悔棋 / 重新开始 / 认输 / 终局弹窗 / 棋谱记录 / 当前回合提示
- 玩家执黑或执白、人机或本地双人、坐标开关、落子音效
- 本地自动存档与刷新恢复
- 桌面三栏 / 移动纵向的响应式布局
- 完整的自动化测试（Phase 1 收尾时为单元用例 261 个 / 16 个文件，端到端 13 条；当前总数见 `docs/TEST_REPORT.md`）

Phase 1 结束后做过一轮两轴代码审查（标准轴 + 规格轴），发现的问题已全部修复，详见 `docs/TEST_REPORT.md` 的「代码审查」一节。

**已知不足（不阻塞验收，转入 Phase 2）**：

- 只开放入门、初级两档难度
- 引擎不识别跳型棋型，没有置换表与算杀
- 没有 AI 提示功能（Phase 2）
- 首次音效若由 AI 应手触发，可能被浏览器的自动播放策略拦下（详见 TEST_REPORT.md）

## Phase 2 · 强化 AI ✅

**验收标准**：AI 能识别直接获胜、必须防守和常见战术威胁，且界面不被搜索阻塞。

- [x] 棋型识别改为**窗口枚举**（含跳三、跳四等隔一子结构）。没有走「模式串匹配」那条路：枚举包含落点的全部 5 个五连窗口，隔子型的空位自然落在窗口里，比维护一张模式表更短也更不容易漏。
- [x] 置换表（Zobrist 哈希，双 32 位半值），配合杀手着法
- [x] 迭代加深调优：合并了排序与必胜判断的重复扫描，把算杀限制在 35% 预算内——**但「时间预算真正转化为棋力」只做到一半**，专家档的深度上限仍未达到，见下方已知不足
- [x] 算杀搜索：连续冲四取胜（VCF）已启用；威胁空间搜索（VCT）已实现并有测试，但实测代价约为 VCF 的 15 倍而收益看不出来，**默认关闭**
- [x] 双威胁识别：双四、四三、双活三（`shapeScore` 的组合加成）
- [x] 开放中级 / 高级 / 专家三档；档位差异由自对弈验证（`src/ai/selfplay.test.ts`）
- [x] AI 提示：紧急度徽标、前 3 个候选（坐标 + 评分 + 攻防棋型中文说明）、棋盘上的编号标记
- [x] 提示固定使用 `purpose: 'hint'` 的只分析请求，绝不落子；与落子请求共用引擎但互不挤占
- [x] 引擎对局测试：`src/ai/selfplay.test.ts`（五个用例）——**保留在测试套件里**，没有拆成独立脚本。它把深度压到 3 以控制时长，档位差异靠算杀开关体现；固定时钟保证同一开局跑两次得到完全相同的棋谱。

Phase 2 结束后跑过一轮两轴代码审查，另做了一轮 3 次自审 + 1 次终审的计划评审（记录在 `docs/superpowers/plans/2026-10-10-gomoku-lab-phase2.md`）。

**已知不足（不阻塞验收，转入 Phase 3/5）**：

- **专家档的深度上限（8 层）从未达到**：构造基准上最多 6 层，真实对局中观察到 7 层；高级档用 1.1 秒就能完成基准上的同样 6 层。要让它名副其实，得先把单节点成本压下去。
- **单次 `evaluateBoard` 约 72 µs，是当前真正的瓶颈**。下一步性能优化应该做增量评估（只重算受落子影响的线段），而不是继续调 alpha-beta。
- **不算 VCT**，也找不到需要两层以上活三的杀型。实现与测试都在，按需可开。
- **局面评估不识别跨方向的组合形状**：单点分析有双四/四三/双活三的加成，整盘评估仍是按线段独立累加。
- 提示的棋型分析（`analyzePoint`）比搜索贵得多，只在 `purpose: 'hint'` 时才付这份钱。

## 长期待办

以下事项已识别但尚未排期：

- **增量局面评估**：当前 `evaluateBoard` 每次重扫全盘（72 µs/次），是搜索的主要开销。改成只重算受落子影响的 4 条线段后，专家档才有可能真正搜到第 7 层。
- **基准回归**：`yarn bench` 目前只产数字、不做断言。若要防性能回退，应该在 CI 里对关键指标设阈值。

- **键盘操作**：棋盘目前只能鼠标/触摸操作，成型的键盘落子与焦点管理放在 Phase 5。
- **首次音效被拦**：`AudioContext` 若在页面加载后由 AI 应手触发创建，会被浏览器自动播放策略挂起。当前实现会在下一次用户手势触发的播放时自愈，彻底的做法是绑定首个 `pointerdown` 预热。
- **Web Worker 降级**：极老的浏览器不支持 module worker 时目前没有回退路径。
