## 1. 优化目标

任务书给这一轮的定义是：**在不推倒重写的前提下，让整站具有统一的产品体验、
可靠的交互逻辑和可维护的代码结构**。拆开是四件事：

1. **一致性** —— 四个页面（对战 / 教学 / 残局 / 复盘）共用一套颜色、排版、
   控件状态、圆角、间距、加载与错误表达。
2. **响应式与触控** —— 六个指定视口 + 矮窗口 + 文字缩放 + 深浅主题下，
   不溢出、不裁切、棋盘不塌、控件不被遮、没有多重滚动陷阱。
3. **无障碍** —— 键盘走完全流程、焦点可见且可管理、读屏有播报、
   控件有可访问名、对比度达标、尊重 `prefers-reduced-motion`。
4. **结构** —— `core / ai / learn / store / persist` 的职责边界不被 UI 改版破坏；
   不留下两套并行的视觉或状态系统。

Phase 00 的基线（`BASELINE.md`）是这一切的对照点：19 个受控状态 / 156 张截图 /
156 条 DOM 量测，跑法与产物路径都可复跑。

## 4. 视觉与交互改善

以下每条都有**可观察依据**：要么是探针的同口径量测差值，要么是真实浏览器里的
操作记录。完整差值表在 `FINAL_TEST_REPORT.md` §4。

### 4.1 量化差值（before → final，156 个共同组合）

| 指标 | 变化 | 依据 |
| --- | --- | --- |
| 棋盘宽度中位 | 409 → **642 px** | 棋盘塌陷（F-UI-01）与 1024–1439 被侧栏压扁（F-UI-02）都修掉了 |
| 棋盘最小宽度 | **169 → 340 px** | 169 是塌陷值；340 在 320 底线之上 |
| 内容被裁（`clipped`） | **16 → 0** | 课程摘要的 `truncate`（F-UI-26）+ 390 下讲解页标题 |
| <24px 命中区 | **40 → 8** | 剩余全是棋盘交叉点（规范 §8 的 20×20 与 WCAG 的已知豁免） |
| 深色 `theme-color` | `#f6f4f0` → **`#0f1115`** | 手机地址栏不再挂亮横条（F-UI-17） |
| reduce 下仍在播的动画 | **1 → 0** | 「思考中」的转圈停掉（F-UI-07） |
| 对比度违规 / 横向溢出 | 0 → 0 | 保持 |
| 判据 7（最后一手、标记文字、胜利环） | 全过 | Phase 03 建立，本轮未回归 |

### 4.2 用户能直接感觉到的改善（按页面）

- **对战**：三个断点各有明确形态（单列 / 两栏 / 三栏）；状态条贴在棋盘上方；
  会重建棋局的操作全部先确认；AI 面板默认说人话，「?」才展开技术细节；
  五档难度一行一个。
- **教学**：课程分阶段展示，顶部给「已完成 x / 8」与推荐；讲解可翻页、可回头；
  练习的三级提示逐级具体，第三级才在棋盘上标点位；做对后给解法说明与「下一节」。
- **残局**：首页给总进度与分类计数；错着有明确理由与「重试」；做对后「下一题」
  直接换题且状态不串；分类与全部完成各有提示。
- **复盘**：空状态给下一步；棋谱列表可辨认；时间轴、速度、播放/暂停齐备；
  分析结论标出处与局限，关键手可点击跳转；和棋/认输/终局措辞各归各位。
- **全站**：深浅主题共用一份实现（组件里 `dark:` 为 0）；顶栏在页面之间不跳；
  换页焦点落在新页面正文；手机上刘海与手势条不再压内容。

## 5. 工程结构影响

### 5.1 职责边界（grep 实证，全部通过）

| 约束 | 结果 |
| --- | --- |
| `core` / `ai`（除 `worker.ts` / `browserEngine.ts`）/ `learn` 不 import React / DOM / Zustand / localStorage / IndexedDB | ✅ 0 命中 |
| `store/` 不 import `features/` 或 `components/` | ✅ 0 命中 |
| `ai/` / `core/` 不被 `learn/` 反向依赖 | ✅ 0 命中 |
| `applyMove` / `undo` / `resign` 返回新对象 | ✅ 未改动 |
| AI 请求绑定 `requestId` + `gameVersion` | ✅ 未改动，e2e「迟到的响应」覆盖 |
| 提示只读（`purpose: 'hint'` 不落子） | ✅ e2e「提示之后棋局一手未变」 |
| 教学内容按目标谓词判定 | ✅ `content.test.ts` 逐题跑求解器 |

### 5.2 结构审计结论

15 项逐项核查（超大组件、重复 JSX、复制样式、无意义 hook、不必要的全局状态、
派生状态重复、effect 依赖、事件监听、定时器、渲染、过度抽象、隐式耦合、
兼容层、测试实现细节、业务规则进 UI）：

- **Blocking / High：0。**
- **审计标 Medium 的 6 项**，终审逐条对照「用户能不能观察到」后**下调为 Low**
  （不构成可观察缺陷），全部是既有的设计取舍，**不在终审阶段重构**——逐条理由见
  `KNOWN_ISSUES.md` L-4。其中唯一有实际风险的是 `learnStore` 的
  `view` / `progress.lastView` 双份，但只有测试的 `setState` 能让两者不一致，
  用户路径不经过。
- **没有发现两套并行的视觉或状态系统**：组件里 `dark:` 前缀为 0；颜色全部来自
  28 个令牌；四个页面共用 `PageShell` / `AppHeader` / `Button` / `Panel`。
- **没有发现被遗忘的旧 UI 或过渡性代码**：grep `deprecated|legacy|compat`
  在**产品代码里零命中**；测试里有两处局部变量名（`Button.test.tsx` 的
  `legacy`、`gameRecords.test.ts` 的 `legacy`），都不是兼容层。

### 5.3 本轮新增的工程约束

- `AGENTS.md` 的测试约定里固化「布局预算」的量化判据（320px / 620px /
  互不压盖），并点名高度极小横屏窗口是已知例外。
- e2e 的「四个页面标题」用例从三页扩到四页——原先的名字与实现不符。

## 8. 后续可选建议

按收益/代价排序，**都不是本次交付的缺口**：

1. **复盘页加手顺列表**（M-2 的正解）。编号 pill 在三位数时密排，
   列表能同时解决「看完整手顺」与「跳转定位」。这是一次设计变更，值得单开。
2. **分析面板区分算杀手数**（F-UI-23 的正解）。给 `SearchResponse` 补 `plies`，
   把「下一手成五」与「三手算杀」分开说。需要改 `ai/` 的接口与基准。
3. **增量局面评估**。`evaluateBoard` 每次重扫全盘（约 72 µs），是专家档的主要
   开销；改成只重算受落子影响的 4 条线段后，专家档才可能真正搜到第 7 层。
   已有历史记录（`ROADMAP.md` 的长期待办）。
4. **把 `GameStatusDescriptor` 移出 `features/battle`**。共享组件 `StatusPill` /
   `ResultDialog` 对 feature 的类型反向依赖，运行时无环但层次不干净。
5. **极小横屏的高度策略**。若决定「横屏手机也要 320px 棋盘」，需要把工具栏
   收进抽屉或浮层——先改 `DESIGN_SYSTEM` §8.1 的措辞，再动布局。
