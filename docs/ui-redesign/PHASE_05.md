## 二、目标与**不做什么**

### 2.1 目标

把残局从「题目目录」变成「有目标、有进度、有出口的训练流程」：

1. 首页说清**练到哪了**、**下一题是哪道**（与教学页同一套语言）。
2. 每道题的卡片说清**它是什么题**（类别 + 完成状态）。
3. 通过之后能**直接往下走**，最后一题有收束。
4. 判错时棋盘上的标记与文字反馈**说的是同一件事**。

### 2.2 明确不做（每条都写清楚为什么）

| 不做 | 理由 |
| --- | --- |
| **难度等级**（简单 / 困难 / 大师） | 题库没有难度数据，编一个等级就是**假装有客观依据**（任务书 §三 点名禁止）。分类顺序可以表达「由浅入深」，但那是**教学顺序**，会在文档里如实这么写 |
| **星级 / 积分 / 排行榜 / 成就系统** | 任务书 §九 点名禁止；且本应用没有账号体系，任何"排行榜"都只能是假的 |
| **顺序解锁**（做完第一类才能进第二类） | 任务书 §四 / §七 明确「不要求按顺序解锁」。推荐是**推荐**，八道门都得开着 |
| **新增持久化字段** | `solvedPuzzles` 已经够表达一切；分类进度、推荐、完成提示全部**派生** |
| **「首次完成」提示** | 它不携带新信息——卡片上的 ✓ 与「这一题已经通过。」已经说了同一件事。只做**分类完成**与**全部完成**两条（它们跨越了一次状态边界） |
| **给每一题加图标 / 插画** | 任务书 §三「不要给每题加入大量装饰图标」 |
| **改判定、改提示层级、改题库内容** | 任务书的硬约束；`src/learn/**` 除 `content.test.ts` 外预期零改动 |

## 三、设计决策（含被否决的方案）

### D1 · 把进度区抽成共用的 `ProgressBlock`（替换 `LessonProgress`）

**现状**：`LessonProgress.tsx`（Phase 04 写的）承担教学页的「进度条 + X/N + 主操作」，
内含载入占位、`role="progressbar"`、aria 三件套、全完成文案。残局要的东西与它**同构**。

**决策**：抽出 `src/features/learn/ProgressBlock.tsx`，`LearnScreen` 与 `PuzzleScreen` 各调一次。

```ts
interface ProgressBlockProps {
  readonly loaded: boolean
  readonly done: number
  readonly total: number
  /**
   * e2e 契约。两页各有一个稳定的抓手，且**不许与文案耦合**——
   * 教学页是 `learn-progress`、残局页是 `puzzle-progress`，
   * 各有已存在的断言钉着它（`e2e/learn.spec.ts`、`screens.test.tsx`、探针的 boot）。
   * 做成参数而不是从 `unit` 推：那是拿一个文案去生成一个契约，改文案就会断测试。
   */
  readonly testId: string
  /**
   * 这一块的文案，打包传。
   *
   * 它们**总是一起变**（同一个块的口措辞）——`Data Clumps` 的判据：
   * 几个字段反复同行，就该有自己的类型。摊平成四个 prop 只是把同一个事实写四遍。
   */
  readonly texts: {
    readonly loading: string
    readonly unit: string
    readonly action: string
    readonly allDone: string
  }
  readonly next: { readonly id: string; readonly title: string } | null
  readonly onContinue?: () => void
}
```

**七个顶层参数，没有插槽。** 这一条是终审逼出来的：初稿只写「八个参数、不留插槽」，
却漏了「同一个节点在两页要有两个不同的 `data-testid`、载入文案也随页面不同」
——实施时必然临时加第九、第十个参数，而那种「加一个再说」正是接口失守的方式。
现在把它一次性写清楚。

**被否决的方案**：
- *残局自己再写一个*：进度条实现、载入占位、aria 三件套会有两份，
  而这两块 UI **注定要一起演进**（改进度条样式就要改两处）。
  这不属于「小重复不值得抽」——那条裁定针对的是**测试**（`FINDINGS.md §10.3`）。
- *让 `ProgressBlock` 收 `children` 插槽*：本来是想用来放「分类进度」的，
  但 D2 决定分类进度**就地放**（见下），插槽就没有第二个用途了——
  **一个只有一处使用的插槽就是 Speculative Generality**。

**守卫**：`ProgressBlock.test.tsx` 承接原 `LessonProgress` 的用例（含载入占位那条），
两页各有一条「它真的出现在页面上」的用例。

### D2 · 分类进度**就地**放在各分类标题旁，不集中在顶部

```
一步获胜                        3 / 3
├ ✓ 横向补满
├ ✓ 斜向补满
└ ✓ 竖向补满
```

**理由**：就近（读者想知道「这一类练完没」时，眼睛就在那一类上）、
**不增加顶部高度**（顶部每多一行，1440×700 的棋盘就少一点——`DESIGN_SYSTEM.md` §10.2 第 4 条）、
且完全由 `PUZZLES` × `solvedPuzzles` 派生。

**硬约束：`X / Y` 必须放在 `h2` 的<ins>外面</ins>，不能塞进标题文字里。**
覆盖率基线按 `level:text` 钉着 `h2:一步获胜` 这些键（实测：`quality/coverage.baseline.json`
里 `puzzle-list` 那一组有 6 条 `h2:〈分类名〉`）。塞进去键就变成 `h2:一步获胜 3 / 3`，
旧键消失 → 棘轮按「丢了标题」报红。放在 `h2` 外面则是**新增**一个普通文本节点，
`level:text` 不变 ✓（棘轮只看标题与按钮，不看任意文本）。

### D3 · 判错后**保留**「解」标记（修一处真实的不一致）

**改动前**的长这样（当时在 `PracticeBoard.tsx` 的标记那段）：

```ts
if (attempt !== null)      marks = [玩家那一手：对 / 错]
else if (solution !== null) marks = [解法点：解]
```

于是：玩家用满三级提示拿到点位标记 → **落一手别的** → 判错 →
棋盘上「解」的标记**消失了**，而提示面板还写着「棋盘上标出了其中一种解法」✗
文字在一处、标记在另一处，**语义不一致**——正是任务书 §六 点名的那种情况。

**决策**：判错时两个标记都给（「错」在玩家落子的点、「解」在解法点）；
判对时只给「对」（解法点必然就是玩家那个点，重叠无意义）。

**不做的替代方案**：把对手的成五点也标出来（`blockFive` 的失败理由里点了那些坐标）。
理由：对 `blockFive` 这类题，成五点**就是答案**，标出来等于判错一次就送答案。
任务书 §六 要的是「标记与文字一致」，不是「把答案铺在盘上」。

### D4 · 「下一题」按 `PUZZLES` 的真实顺序，跨分类

`nextPuzzleAfter(PUZZLES, id)` → 数组里的下一道；最后一道返回 `null`。

**为什么不按分类内循环**：任务书 §七 说「根据现有题库中真实的顺序决定」。
`PUZZLES` 的声明顺序就是唯一的真实顺序（分类顺序 × 类内顺序），
另造一条顺序就是**第二个真相**。跨分类往下走也符合「训练流程」的直觉：
一类做完接着做下一类。

### D5 · 完成时的出口用**描述符**，不并列两个可选回调

与 `LessonExit`（`LessonView.tsx:15`）同一套做法：两个都可传时「哪个优先」
就是一条没写下来的隐式规则。这里 `PuzzleExit` 有三态：

```ts
type PuzzleExit =
  | { kind: 'next'; run }        // 还有下一题 → 「下一题 →」（primary）
  | { kind: 'allDone'; run }     // 这是最后一题 → 「去实战试试 →」+ 完成文案（primary）
```

「再做一次」不是 exit（它不换题），作为常驻的 secondary 按钮与 exit 并列。

**为什么末题通向对战**：教学页的末课通向残局（Phase 04 §九），
残局是这条链的最后一环——它通向**实战**，闭环。不给「去复盘」：
复盘要看的是自己的对局，此刻还没下过。

### D6 · 详情页标题升 `h1`

改动前 `PuzzleScreen` 里那道题名是个 `span`。升 `h1` + `text-xl font-semibold`
（§3.2「页面标题」档，与 `PageHeader` / `LessonView` 同一套）。

**连带**：探针的 `headings` 会量到新键 → `quality/coverage.baseline.json` 要**显式**改，
并在提交信息里说明——这是棘轮自己写的正当路径（Phase 04 已走过一次）。

### D7 · 新增 `features/puzzles/puzzleOutline.ts`（纯函数，与 `courseOutline.ts` 对称）

```ts
export function resolveNextPuzzle(puzzles, solved): Puzzle | null   // 第一道没做的
export function categoryProgress(puzzles, solved): readonly { category, done, total }[]
export function nextPuzzleAfter(puzzles, id): Puzzle | null
```

**为什么不放 `src/learn/`**：`learn/` 是**内容层**（题库、判定、提示），
而这三个是**展示层派生**——与 `courseOutline.ts` 住在 `features/` 下的理由一致。
依赖方向不变（`features → learn`）。

**为什么是纯函数**：它们各有一条守卫用例（顺序、边界、派生正确性），
而纯函数能在单测里逐个钉住，不用起浏览器。

### D8 · 卡片补上类别——**这是本阶段唯一会动覆盖率基线的地方**

任务书 §三 要求每题展示「题目类别」，而首页已经是**按类别分组**的：
类别就写在卡片头顶的 `h2` 上。那卡片里再写一遍，是满足字面要求还是纯冗余？

**决定：写。** 两个理由站得住：长列表滚动时分组标题会滚出视野，
卡片自带类别才回答得了「这题是哪一类」；而且任务书就是这么要求的。
细节上做成题名**下面一行 12px 的 `text-muted`**（与教学页的 `summary` 同一个位置与字号），
不是徽标、不是图标——任务书 §三 要「简洁统一」。

**代价必须说清楚**：卡片的可访问名会从 `·横向补满›` 变成带类别的新文本，
而覆盖率基线用 `textContent` 把**这 15 个名字**钉在了 8 行量测里
（实测：`quality/coverage.baseline.json` 的 `puzzle-list` 组，每行 19 个按钮，
其中 15 个是题目卡）。旧键消失 → 棘轮会按「丢了按钮」报红（**实测 120 项**）。

处置：**显式更新基线**，且按下面的流程做，不许无脑覆盖：

1. 改完代码、跑完 `yarn ui:probe`，拿到新量测；
2. **先 diff 再改**：逐条比对新旧按钮集合，确认差异**只有**这 15 个卡片名
   （数量一致、导航的 4 个键 `对战 / 教学 / 残局 / 复盘` 原样在）——
   否则说明真的丢了控件，那是缺陷不是改名；
3. 只替换那 15 个键，其余一概不碰；
4. 重跑 `yarn check:coverage`，并核对「实比控件与标题」的总数没有掉档；
5. 在提交信息里写明「哪几个键因何改名」。

（**升 `h1` 不动基线**——这一条我初稿写反了：棘轮的规矩是「新增不用改，少一条才红」
（`coverage.ratchet.mjs:12`），而探针只收 `h1–h4`（`MEASURE` 里那句 `querySelectorAll('h1, h2, h3, h4')`）、
残局详情页的题名今天是 `span`，所以升 `h1` 是**新增**键。Phase 04 之所以要改基线，
是因为那次是把**已经扫到的** `h1` 降成了 `h2`——方向相反。）

### D9 · 「分类完成」提示必须有落地动作（它是任务书 §九 点名的）

初稿在 §二 承诺了「只做分类完成与全部完成两条」，却在改动清单、验收标准、
用例表里都没有对应动作——**承诺没有落地就是没做**（终审指出的第 3 条）。

落地方式：通过后的 footer 里，在「下一题」上方多一句**由真实数据推导**的话：

| 条件 | 文案 |
| --- | --- |
| 这一次通过后，该类全通 | `「一步获胜」这一类全部通过了。` |
| 这一次通过后，15 道全通 | `15 道题都通过了。`（取代上一句，不叠加） |

判定放在 `puzzleOutline.ts` 里（`categoryProgress` 的直接消费方），
不在组件里现算——组件只问「这一类通了吗」。

**时序要说清楚**：`onSolved` → `solvePuzzle(id)` → store 更新 → 重渲染，
所以 footer 渲染时 `solvedPuzzles` **已经含当前这道题**，
`categoryProgress` 的 `done === total` 判的就是「这一次通过之后」✓
不需要手工把当前题加进去（手工加就是第二份真相）。

## 八、验收标准

### 11.2 实施中发现的一处真缺陷（写 e2e 时才看出来）

**初版把「走到题库的最后一道」与「全部做完了」混成了一个状态。**

`PuzzleExit` 原本只有 `{ kind: 'allDone' }`，文案写死「{total} 道题都通过了」。
可列表**不锁顺序**（任务书 §四 / §七 明确要求），玩家可以直接进去做最后一道题
——那时屏幕上会说一句「15 道题都通过了」的假话。

这与 Phase 04 §20.3 第 6 条**完全同形**（教学页的出口只由「是不是最后一节」决定，
于是做对最后一节就显示「全部课程讲完了」）。同一个错误在一个项目里犯了两次，
所以这次的修法不是「顺手判一下」，而是把它变成一个**显式字段** `allSolved`：

- 真全做完 → 「15 道题都通过了——这些棋型，去实战里用用看。」+「去实战试试 →」
- 只是走到最后一道 → 「这是题库里的最后一道。前面还有没做的，随时回列表接着练。」
  +「回到残局列表」

两条路径各有一条用例（`screens.test.tsx` 两条 + e2e 的「做到最后一道」一条）。

### 13.2 用户拍板的三件事

**B1 · 「继续挑战」按类推荐。** 仍指第一道没做的；但**本次会话里打开过的那一类**
若还有没做的，优先给那一类里的第一道——跳着练的人不会被弹回最前面。

**这条有一个必须写下来的约束**：`lastVisited` **不能**用来实现它。
点「← 残局列表」会把它清成 `null`（`PuzzleScreen` 的 `backToList`），而列表页能显示的前提
正是它不是一道有效的题——**读它的那个分支到不了**（与 Phase 04 删掉的
`resolveNext` 分支同类）。所以用**会话内记忆**（列表页自己的 state）。

**局限**：离开残局页就丢——`PuzzleScreen` 切视图即卸载（`App.tsx` 的
`{view === 'puzzles' && <PuzzleScreen />}`），所以**刷新、以及切到教学 / 对战再回来**
都会回退到「第一道没做的」。（初稿只写了「刷新后丢失」，两轴审查指出那不全。）

不引持久化字段换来这个局限是划算的——跨视图要区分「用户主动退出到列表」
与「用户就停在那道题里」，那需要新增一个状态，而任务书 §四 明确要求
分类进度这类东西**由现有数据推导**。

**B2 · 补「首次完成提示」。** 首次做对那句与重进已通过的题不同。
需要一个「进入这道题时它是否已经通过」的判定——`isPuzzleDone` 是 store 状态，
做完之后也为真，**区分不出来**，所以要在挂载时取一次快照。
`PuzzleView` 因此要加 `key={puzzle.id}`：换题必须重建，否则那道快照会跟着串题。

**B3 · 平板 768–1023 只在横屏改双栏。** 竖屏（768×1024）保持纵向堆叠——
那时纵向让棋盘吃到 **478px**（实测），改双栏只剩 ~408px，违反
`DESIGN_SYSTEM.md` §10.2 第 1 条「先缩面板 → 再折叠面板 → 最后才动棋盘」。

实现不写 `md:landscape: lg:` 两遍（`PracticeBoard` 的 aside 有 5 处 `lg:` 前缀，
双写就是 10 处）：在 `index.css` 定义一个**自定义变体**，
把「≥1024」与「≥768 且横屏」合成一个条件，五处类名只改一处定义。

## 十五、第四轮：独立验收与整改

### 15.1 本轮发现的真缺陷（1 条，用户可见）

**对战页在 768–1023 横屏、高 ≥500 的窗口里，棋盘塌成 0×0——整块棋盘消失。**

实测（`chrome`，逐档量 `[data-testid="board"]` 的 `getBoundingClientRect`）：

| 视口 | `wide-layout` | 棋盘 |
| --- | --- | --- |
| 900×700 / 800×600 / 1023×800 | 命中 | **0×0** |
| 1024×800 | 命中（`lg` 也命中） | 629×629 ✓ |
| 900×480 / 768×900 / 960×1040 | 不命中 | 243 / 478 / 556 ✓ |

> 最后一行的 `900×480 → 243px` **低于 §8.1 的 320px 底线**。这里的 ✓ 是说
> 「这一档修复前后没有变化」，**不是「合规」**——两者不是一回事，写在 §15.7 第 4 条。

- **根因**：`b212001` 把共享件 `BoardStage` 的解除条件从 `lg:` 换成 `wide-layout:`，
  而 `BattleScreen` 是**唯一不走 `PageShell`** 的页面——它自己那六处条件仍是 `lg:`。
  前者命中、后者不命中时，那个 `container-type: size` 的 section 拿到
  `height:auto; min-height:0`，`100cqh` 没有确定值，于是塌成 0：
  正是 `BoardStage.tsx` 自己注释里写的那句。
- **为什么没被抓到**：§14.4 论证「两者在 ≥1024 等价」时，看的是**探针矩阵里的页面**
  （残局），没看**所有调用 `BoardStage` 的页面**；`layout.spec.ts` 的 768 档是竖屏、
  其余 ≥1024——「对战页 × 768–1023 横屏」这个格子一条用例都没有。
  §15.2 那条假注释又让它看起来像「对战页与 `wide-layout` 无关」的既定事实。
- **修法**：**不是把条件收回去**——单列那一档的固定高是
  `min(100vw−1.5rem, 56dvh)` 减 `py-3` 的 24px，900×500 下即 `280 − 24 = 256px`，
  本来就低于 §8.1 的 320px 底线。改成让对战页与另外三页共用 `wide-layout`
  （`App.tsx` 的根容器 + `BattleScreen` 的六处类名）。**≥1024 行为逐字不变。**
  （这一句原先写的是「264px」——那是减 `py-2` 的值，而 `py-2` 只在**解除之后**
  才生效，拿它当「不能收回单列」的依据是把因果绕反了。两轴评审的规格轴抓到的。）
- **守卫**：`e2e/layout.spec.ts` 的「对战页 @{宽}×{高}（768–1023 横屏）：棋盘不塌」，
  四个角各一条（768×500 / 800×600 / 900×500 / 1023×800）。
  反向验证：修复前 900×500 那条实跑**红**（`unexpected value "hidden"`），修后绿。

### 15.7 尚未解决的风险（如实列）

1. **焦点管理**（§15.4）：换题/换节后焦点落到 `<body>`，键盘用户要重按 8 次 Tab。
   全仓既有模式，建议单开一个任务统一处理，而不是塞进本阶段。
2. **覆盖是补齐的，不是系统的**：`e2e/layout.spec.ts` 现在用四个角钉住了
   「对战页 × 768–1023 横屏」，但同类空格还有多少没系统查过——本轮的教训是
   **按调用点排查，不是按页面排查**。
3. **小屏棋盘低于 §8.1 的 320px 底线**（既有，本轮未修）。§8.1 的原话是
   「**任何布局**都不得把棋盘压到这个值以下」，但高度 <500 的横屏窗口
   （900×480 → 243px）与横屏手机（915×412 → 约 207px）都在它下面。
   物理上放不下：320 + 顶栏 60 + 工具栏 44 > 412。这是 Phase 05 之前就有的取舍，
   §15.1 的表里给这两档标的是「无回归」而不是「合规」——本轮把这句话补上，
   是因为原先那个 ✓ 容易被读成后者。真要修得先改 §8.1 的措辞（它是绝对的）
   或改小屏的高度策略，两件都超出「最小必要修复」。
4. `AppHeader` 的 `lg:px-6`、`MoveList` 的 `lg:max-h-56` 仍是 `lg:` 而不是
   `wide-layout:`。**本轮没改**：它们不构成缺陷，也**不与其他组件有条件耦合**
   （§15.1 的根因是「共享件的条件与调用方不一致」，这两处没有对应物），
   改它们只会白白扩大验证面。记在这里，等下次真的要动那个组件时顺手对齐。
