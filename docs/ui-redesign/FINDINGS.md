## 1. P0

### F-UI-01 · 教学 / 残局 / 复盘三页在 ≥1024px 下棋盘塌陷

**现象。** 屏幕宽到 1024 以上时，这三个页面的棋盘缩小到 **169–409 px**，
而且**与视口大小无关**——1440 和 1920 下一样大。棋盘下方是一大片空白。

**位置。** 三处同一条模板：

| 文件 | 行 |
| --- | --- |
| `src/features/learn/LessonView.tsx` | 62 |
| `src/features/puzzles/PuzzleScreen.tsx` | 147 |
| `src/features/review/ReplayBoard.tsx` | 44 |

```html
<main class="... lg:grid lg:grid-cols-[minmax(0,1fr)_344px] lg:grid-rows-[auto_minmax(0,1fr)]">
```

**证据。**

| 状态 | 1024 | 1280 | 1440 | 1920 |
| --- | --- | --- | --- | --- |
| `learn-practice` 棋盘 / 视口 | 16.5% | 13.2% | **11.7%** | **8.8%** |
| `puzzle-wrong` | 23.0% | 18.4% | 16.4% | 12.3% |
| `review-replay` | — | 31.9% | 28.4% | 21.3% |
| `battle-midgame`（对照） | 35.4% | 48.3% | 54.0% | 41.2% |

1440 下 `learn-practice` 的棋盘是 **169×169 px**，**交叉点命中区 11×11 px**
（截图 `learn-learn-practice__1440-light.png`）。

那个 11×11 是探针量到的，不是折算的：`boardDetails.intersectionHit = {width: 11, height: 11}`，
出现在 `learn-practice` 的 1024 / 1280 / 1440 / 1920 与 1440 深色共 5 处。
**11 px 的目标意味着「想点中某一格，误差不能超过 11 px」**——这是这条 P0 最直接的后果，
也是它与 F-UI-10（移动端 21×21）的区别：手机上那是物理上限，桌面上这是纯损失。

**根因（复现）。** 临时诊断脚本（真实浏览器，1440×900）打出的布局链：

```
main     display=grid  gridTemplateColumns="1096px 344px"  gridTemplateRows="218.5px 567.75px"
section  （棋盘容器）  rect = 1096×219 @ y=114      ← 在第 1 行
aside    （右侧栏）    rect =  344×219 @ y=114      ← 也在第 1 行
```

`grid-rows-[auto_minmax(0,1fr)]` 的两行里，**只有第 1 行有内容**，第 2 行（`1fr`，
567.75 px）完全空着。棋盘落在 `auto` 那一行，行高由右侧栏的内容高度决定——
所以右侧栏里多一张结论卡，棋盘就大一点。

这条模板是**给「工具栏当网格第一行」写的**：`e58dd56`（2026-10-11）当时
`<div className="order-3 ... lg:order-1 lg:col-span-2">← 课程列表 …</div>` 确实在网格里。
`fd0d5e0`（同日，第四轮两轴审查）把工具栏移出网格（`lg:col-span-2` 随之消失），
**`lg:grid-rows-[auto_minmax(0,1fr)]` 没有跟着删**。从那以后棋盘就一直在 `auto` 行里。

**为什么一直没被发现。** 三条端到端用例都在跑（平板横屏 1080×810 也是 `lg`），
但它们只断言「不横向溢出 / 是正方形 / 完全可见 / 三栏不压盖」——
**169 px 的棋盘全部满足**。测试守的是「有没有坏」，没守「够不够大」。见 F-UI-05。

**影响。** 桌面宽度下（1024 以上是主要使用场景），教学讲解、课程练习、
残局挑战、复盘回放四个界面的棋盘小到几乎无法操作：一格 11 px，
而"点哪一格就下哪一格"是这个产品全部交互的基础。

**修复方向（已在真实浏览器里验证过）。**
删掉 `lg:grid-rows-[auto_minmax(0,1fr)]`。三处一起改。

验证方式**没有改仓库文件**：只往页面里注入一条
`main { grid-template-rows: none !important }`，量修复前后的棋盘。

| 页面 / 视口 | 修复前 | 修复后 | 放大 |
| --- | --- | --- | --- |
| 教学 · 练习 1024×900 | 169 px（16.5%） | **630 px（61.5%）** | 3.73× |
| 教学 · 练习 1440×900 | 169 px（11.7%） | **736 px（51.1%）** | 4.36× |
| 教学 · 练习 1920×900 | 169 px（8.8%） | **736 px（38.3%）** | 4.36× |
| 教学 · 讲解 1440×900 | 330 px（22.9%） | **736 px（51.1%）** | 2.23× |

机制核对得上：删掉行模板后只剩一个隐式行，`align-content: normal`（= `stretch`）
会把它撑满 `main` 的 786 px 高度——所以修复不是「碰巧」，是网格布局的既定行为。

**为什么两次审计都没抓到。** 这条回归出现在 `fd0d5e0`（2026-10-11），
而全仓工程审计的起点 `4987c33` 在它**之后 29 个提交**——也就是说那次审计是在
棋盘已经塌了的代码上做的，结论「没有发现 P0/P1」依然成立。
原因是两次审计看的东西不同：那次看的是算法正确性、依赖图、类型安全、资源释放，
唯一涉及视觉的一条写着「纯视觉，已被目视复核与对比度守卫覆盖」。
**不看几何的审计，看不见几何的缺陷。**

**回归范围。** `learn.spec.ts`、`tablet.spec.ts` 全量 + 新增一条「棋盘不得小于 320px」的断言。
本条的验收判据写进了 `DESIGN_SYSTEM.md` §12。

## 2. P1

### F-UI-02 · 1024–1279 的对战页：棋盘被两侧栏压到 35–48%

**现象。** `lg` 断点（1024）一开，两侧栏就以固定宽度出现，中列被压到 412 px。

**证据（实测）。**

| 视口 | `grid-template-columns` | 棋盘 | 占比 |
| --- | --- | --- | --- |
| 1024 | `268px 412px 344px` | 362 px | **35.4%** |
| 1280 | `268px 668px 344px` | 618 px | 48.3% |
| 1440 | `268px 828px 344px` | 778 px | 54.0% |
| 1920 | `268px 1308px 344px` | 791 px | 41.2%（被高度卡住） |

1024 下棋盘周围是约 240 px 的上下空白，左栏下方也有约 280 px 的空背景
（截图 `battle-battle-midgame__1024-light.png`）——**空间是有的，只是没给棋盘**。

**位置。** `src/features/battle/BattleScreen.tsx:132` 的
`lg:grid-cols-[268px_minmax(0,1fr)_344px]`。

**影响。** 直接违背「棋盘是主要视觉资产」。1024–1279 是笔记本的常见宽度区间。
交叉点的命中区在这个区间只有 **21–32 px**（实测 1024 为 22.63 px）。

**修复方向（已在真实浏览器里试算过）。** 侧栏宽度改 `clamp()`。
同样用注入 CSS 的方式比了三组取值（`main { grid-template-columns: … }`）：

| 视口 | 现状 268 / 344 | **A：`clamp(220px,18vw,300px)` / `clamp(280px,24vw,380px)`** | B：`clamp(240px,17vw,290px)` / `clamp(300px,22vw,360px)` |
| --- | --- | --- | --- |
| 1024 | 362 px（35.4%） | **474 px（46.3%）** | 434 px（42.4%） |
| 1280 | 618 px（48.3%） | **692 px（54.1%）** | 690 px（53.9%） |
| 1440 | 778 px（54.0%） | 785 px（54.5%） | 791 px（54.9%） |
| 1920 | 791 px（41.2%） | 791 px（41.2%） | 791 px（41.2%） |

四档全部**没有横向溢出**。方案 A 是推荐值：它在 1024 上给出最大收益（+31%），
在 1440 上与原状持平（不伤大盘），1920 上侧栏从「两条窄边」变成 300 / 380 px。
**注意**：这只解决「侧栏占宽」，不解决 1920 下棋盘被**高度**卡在 791 px——
那属于「居中留白」的观感问题，本阶段不列为缺陷。

### F-UI-03 · 默认界面常驻算法说明，右栏内容在桌面宽度下就装不下

**现象（两件互相加重的事）。**

1. **算法说明常驻**：`AI 引擎` 面板默认展开一段 11 px 的说明，
   讲 Negamax / Alpha-Beta / Zobrist / 杀手着法 / 算杀；`AI 提示` 面板底部也有一段。
2. **右栏装不下**：实测右栏（`aside`）在多个状态下纵向溢出。

**证据（实测，`scrollContainers`）。**

| 状态 | 视口 | 右栏被藏起来的高度 |
| --- | --- | --- |
| `battle-empty` | 1024 / 1280 / 1440 / 1920 | 20 px |
| `battle-midgame` | 1024–1920 | **244 px** |
| `battle-hint` | 1024–1920 | **378 px** |
| `battle-ai-error` | 1024–1920 | 310 px |
| `battle-midgame` | 1280×**680** | **464 px** |

也就是说：求过提示之后，棋盘下面的内容有 378 px 落在折线以下（`棋谱`面板整个看不见）。
`typeSamples` 里那段说明（`p{引擎跑在 Web Worker 里…}`）在 **7 个状态**里出现。

**位置。** `src/components/panels/AiPanel.tsx:103`、`src/components/panels/HintPanel.tsx:153`。

**影响。** 与产品定位「技术性信息采用渐进披露，不在默认界面堆积算法说明」正面冲突。
移动端更严重：这些说明把真正要用的东西推到很下面。

**修复方向。** 按 `DESIGN_SYSTEM.md` §7 收进「?」展开。
判据已写明：1440×900 下右栏四块面板总高不得超过侧栏可视高度。

### F-UI-04 · 切换「模式」会立刻开新局，没有确认、没有提示、没有撤销

**现象。** 点一下「本地双人」或「人机对战」，当前 30 手的对局立刻被清空。

**位置。** `src/components/panels/SettingsPanel.tsx:57`（`<Field label="模式">`，**没有 `hint`**）
→ `src/store/gameStore.ts:396`（`setMode(mode) { newGame({ mode }) }`）。

**证据（读码 + 实测）。** 同面板里「执子」带提示 `切换会开新局`，
「AI 难度」带提示但不重开——**只有「模式」是"会重开又没有提示"的那一个**。
截图 `battle-battle-midgame__1440-light.png` 里左栏可对照三者的措辞。

**影响。** 一次误点丢掉一整局，且不可撤销（悔棋在重开后无手可悔）。
这属于「破坏性操作没有护栏」。

**修复方向。** 三选一：加确认；把重开做成可撤销（"已开新局 · 撤销"）；至少补上与「执子」同样的提示。

### F-UI-05 · 布局回归没有守护：塌成 169 px 也全绿

**现象。** 46 条端到端用例里，与布局有关的 4 条都只断言**不变量**，
不断言**量级**。

**位置。** `e2e/tablet.spec.ts:92`（不溢出 / 正方形 / 可见）、`:109`（三栏不压盖）、
`e2e/mobile.spec.ts:32`（正方形且不超过视口宽）。

**证据（读码）。** 断言只有 `toBeLessThan`、`toBeGreaterThanOrEqual`、
`abs(width - height) < 1` 这类相对判据——**任何尺寸的正方形都通过**。
F-UI-01 就是在这些用例全绿的情况下活了整整两天。

**影响。** 这不是「少了一条测试」，是**整类缺陷（布局量级）没有守护**。
改版期间会大量改布局，没有守护等于每次改完都只能靠肉眼。

**修复方向。** 补一组「布局预算」断言（属于 Phase 01，五条具体断言列在 `PLAN.md`
的 Phase 01 验收 2）：棋盘 ≥ 320 px、≥1024 时棋盘占中列宽 ≥ 70%、
复盘页 h1 不塌成竖排、列表页顶栏不随内容滚走、窄屏导航占满整行。

**注意边界**：「右栏不得溢出」**不是**本阶段的判据——它是 Phase 03 的目标，
Phase 02 的字号变大会先把它推高。这一条原先被误列进来过，会在 Phase 01 当场变红。

## 3. P2

### F-UI-06 · 「轮到 AI」但并没有在思考时，状态药丸仍然转圈

**位置。** `src/features/battle/status.ts:72`（药丸色调只按「轮到 AI」给 `'thinking'`）
→ `src/components/panels/StatusPill.tsx:31`（`tone === 'thinking'` 就渲染 `animate-spin`）。

**证据（实测）。** 截图 `battle-battle-ai-error__1440-light.png`：
药丸写着「轮到 AI」而左侧的转圈仍在转；同一屏的 `AI 引擎` 面板是红色的错误提示。
`measurements.spinner = { animationName: 'spin', animationDuration: '1s' }`。

**影响。** 转圈的语义是「正在进行」。这里真实情况是「引擎挂了 / 欠着一手」。
**反馈在撒谎**——玩家会继续等，而不是去点「重试」。

**修复方向。** 把「轮到 AI」与「AI 正在思考」拆成两种色调，
只有 `aiThinking === true` 时才渲染转圈。

### F-UI-07 · 「减少动态效果」下，状态药丸的转圈照转

**位置。** `src/index.css:243` 的 `@media (prefers-reduced-motion: reduce)` 只关掉
`.motion-stone-drop` / `.motion-last-move-pulse` / `.motion-panel-in` / `.motion-banner-in`
四个类；转圈用的是 Tailwind 的 `animate-spin`，**不在名单里**。

**证据（实测）。** 探针在 `reducedMotion: 'reduce'`（媒体查询命中 `true`）下扫描全页，
**仍在播放动画的元素恰好 1 个**：

```
reducedMotion = { mediaMatches: true,
                  stillAnimating: ["span.h-3.5 w-3.5 animate-spin rounded-full border-2 border-c"] }
```

**影响。** 一个无限循环的动画，用户明确要求减少动态后仍在播，
且没有任何暂停入口。WCAG 2.2.2（A）与 2.3.3（AAA）都指向这里。
叠上 F-UI-06 之后更糟：它可以在「AI 卡住」时无限转下去。

**修复方向。** 把 `animate-spin` 纳入同一个 `@media` 块，
或改成不依赖动画的静态指示（例如「…」或图标）。

### F-UI-08 · 复盘页标题在 390px 下被压成一字一行

**位置。** `src/features/review/GameLibrary.tsx:46`：
`<header className="mb-4 flex items-baseline gap-3">` 里放了一个 `<h1>复盘</h1>`
和一段很长的 `<p>` 说明。h1 作为 flex 项被压缩到约一个字的宽度。

**证据（实测）。** 截图 `review-review-library__390-light.png`：
竖排的「复」「盘」两行。同一模式在 `LearnScreen.tsx:74` / `PuzzleScreen.tsx:58` 也有，
只是那两处的副文案短，没触发。

**影响。** 移动端页面标题不可读。这是「复盘」这一页在手机上给用户的第一眼。

**修复方向。** `flex-wrap`（说明换到下一行），或给 h1 加 `shrink-0`。

### F-UI-09 · 三个文本按钮低于 WCAG 2.5.8 的 24×24 下限

**证据（实测，390 宽）。**

| 按钮 | 尺寸 | 出现处 |
| --- | --- | --- |
| `收起` | **24×16** | `HintPanel` |
| `重试` | **24×16** | `AiPanel` 的错误条 |
| `知道了` | **36×16** | `AiPanel` 的错误条 |

**影响。** 这三条恰恰出现在「出错了要恢复」和「收起提示」的路径上——
是最需要一次点中的地方。它们在触屏上的命中区只有 24×16。

**修复方向。** 按 `DESIGN_SYSTEM.md` §6.1 收进 `text` 按钮档，
用负 margin + padding 把命中区撑到 ≥24 px 高，视觉不变。

### F-UI-10 · 移动端交叉点命中区只有 21×21，且触屏没有落子前预览

**证据（实测）。** `boardDetails.intersectionHit`：

| 视口 | 棋盘 | 一格 |
| --- | --- | --- |
| 390 | 340 px | **21.25 px** |
| 768 | 478 px | 29.88 px |
| 1024 | 362 px | 22.63 px |
| 1440 | 778 px | 48.63 px |

**影响。** 225 个目标，每个 21 px。低于 44 px 的建议值，也低于 24 px 的下限。

**这条要如实说清楚**：一格 = 棋盘宽 / 16，所以 15×15 棋盘在 390 px 屏幕上
即使满幅也只有 390/16 ≈ **24 px**，**不可能**满足 44 px。
所以问题不是「命中区太小」——它已经按格铺满、没有死区了——
而是**触屏缺少鼠标那条路径上的落子前预览**（`Board` 的 `hovered` 只在 `mouseenter` 上触发）。
桌面用户可以「移上去看预览再点」，触屏用户只能直接点。

**修复方向。** 触摸时先给一次可撤销的预览/确认（第二次点确认），
或长按放大。不要试图靠放大命中区解决。

### F-UI-11 · 页面的标题层级不一致，讲解页还倒挂

**证据（实测，各状态在 1440 下的可见标题）。**

| 页面 | 大纲 |
| --- | --- |
| 对战（`battle-*`） | `h2 对战` `h2 显示与声音` `h2 对局` `h2 AI 引擎` `h2 AI 提示` `h2 棋谱` —— **没有 h1** |
| 教学列表 | `h1 互动教学` `h2 学完之后` ✔ |
| 教学讲解 | `h2 讲解 2 / 3` → **`h1 五个连成一线就赢`** → `h2 棋盘演示` ✘ |
| 教学练习 / 残局详情 | 只有 `h2 练习` —— **没有 h1** |
| 残局列表 | `h1 残局挑战` + 六个 `h2` ✔ |
| 复盘列表 | `h1 复盘` ✔ |
| 复盘回放 | `h1 棋谱回放` → `h2 回放` `h2 引擎分析` ✔（**Phase 06 修的**） |

**影响。** 读屏用户按标题跳转时：对战页没有任何一级标题可跳；
讲解页先遇到 `h2` 再遇到 `h1`（大纲顺序是反的）；
练习页整页没有页面级标题。标题是读屏导航的主要手段，这不是形式问题。

**修复方向。** 每个页面**有且只有一个 `h1`**，`Panel` 保持 `h2`；
讲解页把课程标题提到 `h1`，`Panel` 的「讲解 N / M」退回 `h2`。

### F-UI-12 · 判题标记的红圈里写着「1」

**位置。** `src/features/learn/PracticeBoard.tsx:48`
（`marks.push({ point: attempt.move, tone: solved ? 'good' : 'bad' })`，**不带 label**）
→ `src/components/board/Board.tsx:501`（`mark.label ?? String(index + 1)` 回落到序号）。

在判题场景里它什么都不是——玩家刚下的那一步被标了个「1」，
既有提示的暗示（"这是第 1 推荐"），又没有实际含义。**一个视觉语言，两种意思。**

**修复方向。** 判题标记给明确的符号（✗ / 刚落的子加描边），或干脆不写字。

### F-UI-13 · 五个难度挤进三列，第二行只剩两项

**位置。** `src/components/panels/SettingsPanel.tsx` 的 AI 难度 `<Segmented columns={3}>`
+ `AVAILABLE_DIFFICULTIES` 有 5 项。

**证据（实测）。** 截图 `battle-battle-empty__1920-light.png` 左栏：
第一行 `入门 初级 中级`，第二行 `高级 专家` 后面空一格。
五个难度按钮实测 **63×28**（1920 与 1440；390 下侧栏通栏，是 107×28）。

**影响。** 五个同级选项在视觉上不成组；「高级 / 专家」的位置取决于列数而不是语义，
扫读时容易漏掉第二行。

**修复方向：改用纵向单选列表，不要改成 5 列。**
算一下就知道了：左栏 268 px 减去 `aside` 的 `px-4`（32）、面板边框（2）、`p-3.5`（28），
内宽 206 px；`Segmented` 的槽 `p-1`（8）与 4 个 `gap-1`（16）再扣掉，5 列每列只有 **36.4 px**。
而一个两字标签本身 24 px、加 `px-1.5` 的 12 px 内边距**正好 36 px**——刚好卡在临界值上，
字号或文案一变就压盖（按钮是 `whitespace-nowrap` + `minmax(0,1fr)`，不会换行，只会挤出去）。

**更关键的是它与 Phase 01 打架**：Phase 01 为了把 1024 下的棋盘拉到 45%，
要把左栏压到 `clamp(220px, …)` 的下限 220 px，那时每列只剩约 26.8 px，**必然压盖**。
两个阶段各按自己的数字写，执行到 Phase 03 就会撞车——所以这里直接排除 5 列方案。
纵向列表在左栏完全放得下（左栏在 1440 下本来就有约 280 px 的空白）。

### F-UI-14 · 复盘回放的落子编号约 6.91–8.31 px

**位置。** `src/features/review/ReplayBoard.tsx:41`（`radius: 0.26`）
→ `Board.tsx` 的编号字号 = `radius × 1.25` = 0.325 用户单位。

**处置（Phase 06）：缓解了，但字号仍未达标——如实记。**
当前手那一枚放大到 `0.32`（其余保持 `0.26`），在密排的编号里能一眼找到「我现在在哪」。
**但 0.32 已经是上限**：棋子半径 `STONE_RADIUS = 0.44`（`Board.tsx`），编号与棋子同心，
`0.26` 时棋子边缘余 3.8px、`0.32` 时只剩 2.6px（390 视口），再大就把棋子吃掉了——
而「小半径」这个设计前提的全部意义就是**让棋子露在编号外面**。
0.32 × 1.25 = 0.4 用户单位，仍低于 `DESIGN_SYSTEM.md` §8.2 的 10px 下限。
真要达标得**换载体**（编号盖住棋子，或另加一条手顺列表），那是改设计前提，
**超出 Phase 06 的范围**。

**证据（实测）。** 换算基准是 `Board.tsx` 的 `viewBox`：
`MARGIN = 1`、`EXTENT = 14`、`VIEW_SIZE = 16`，所以**1 用户单位 = 棋盘宽 / 16**。
这一条不用信推算——探针量的 `intersection-7-7` 就是「一格」：
340/16 = 21.25、478/16 = 29.88、362/16 = 22.63、778/16 = 48.63，四次全部吻合。

于是：回放编号 0.325 单位 → 390 下棋盘 340 px 时 **6.91 px**；
1440 下棋盘 409 px 时 **8.31 px**。**两个都不足 10 px。**
（同页坐标标签 0.52 单位 → 390 下 11.05 px，达标。）

**影响。** 逐手回放的核心信息是「第几手」，而它是最小的字。
`ReplayBoard` 的注释说明了取舍（小半径是为了让棋子露在数字外面）——
两个目标冲突时应该换一种画法，而不是把字缩到读不出。

**修复方向。** 放大棋盘（F-UI-01 修完自然变大）、或把编号移到棋子旁边的
屏幕坐标层、或只在当前手显示编号。

### F-UI-15 · 面板标题比它里面的正文还小

**证据（实测，`typeSamples`）。**

- `Panel` 标题：**12 px / 16 px / w600 / `text-muted`**（如 `h2{对战}` 17 个状态）
- 面板内的正文与值：**14 px**（如 `span{显示坐标}` 15 处）
- 全页字号分布：12 px 是主力（单页最多**渲染 87 处**）；11 px 在**源码里出现 18 处**
  `text-[11px]`，**单页最多渲染 17 处**（`battle-hint@390`）。
  两个数不是一回事，混用会得出「页面上有 18 个 11px」这种量不出来的结论。

**影响。** 容器的标签弱于内容，层级是反的——扫读时先看到的是内容，
却不知道它属于哪一块。11 px 的阅读性文字（算法说明、脚注、出处行）
在中文里偏小：18 处里有 5 处是成段的句子。

**修复方向。** 按 `DESIGN_SYSTEM.md` §3.2：`Panel` 标题提到 13 px；
阅读性文字不用 11 px。11 px 只留给品牌副标题。

### F-UI-16 · 窄屏下面板的「标签 —— 值」被拉到整宽两端

**现象。** 768 px 下，`对局` 面板宽 744 px，
而一行只有「模式」和「人机对战」两个短词，被 `justify-between` 顶到两端，
视线要横跨 700 px 才能把两者对上。

**证据（实测）。** 截图 `battle-battle-midgame__768-light.png`；
`regions.main` 在 768 下是 768×—（单列）。

**影响。** 扫读效率。它只在 640–1023（单列 + 通栏）这个区间明显。

**修复方向。** 给这类「标签 / 值」行加最大宽度，或改为上下排布。

## 6. 一条需要额外说明的发现

### F-UI-23 的复现过程

「直接取胜」这四个字在 `AiPanel` 里对应 `reason: 'win'`，而 `reason: 'win'` 有两个来源：
**立刻成五**（`searchBoard` 的捷径）与 **算杀找到强制取胜路线**（`findForcedWin`）。
两者在界面上共用一句话。

复现（真实浏览器 + 项目自己的搜索代码，都不是推测）：

1. 构造一个「双方都没有成五点」的 29 手局面（校验器确认过 0 个成五点）；
2. 浏览器里跑专家档 → `AI 引擎` 面板显示 **判断 直接取胜 · 搜索深度 0 层 · 搜索节点 1 · 耗时 4 ms**；
3. 但**对局没有结束**——棋局继续，状态条回到「轮到你落子」；
4. 用项目自己的 `findForcedWin` 单独验证同一局面：

```
current = 2  moves = 29  status = playing
白棋的成五点： 无
findForcedWin = { move: 'K9', plies: 3, nodes: 1 }
```

结论：引擎的判断**是对的**（确实存在 3 手强制取胜），
但界面把它说成「直接取胜」——用户读完会以为这一手就赢了，
实际还要走两手。**这是文案与事实的落差，不是引擎缺陷。**

同理，「搜索深度 0 层」也会让人以为没搜，实际是走了算杀分支。
措辞建议：`win` 的界面文案按 `plies` 分档（一手成五 =「直接取胜」，≥3 手 =「算杀得手（N 手）」），
或在面板里给出算杀手数。

**本阶段不改文案**——它属于要动的界面，排在后面的阶段。
