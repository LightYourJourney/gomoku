## Medium

### M-1 · 恢复一局已结束的存档时，结果弹窗不说明「这局在不在棋谱库」

**现象。** 从存档恢复一局已经分出胜负的对局，结果弹窗只写「共 N 手。」，
不写「已存入棋谱库」——而正常下完一局会写。

**证据。** `ResultDialog.tsx` 只在 `saveState !== 'idle'` 时渲染存档那一行；
`restore` 路径刻意不触发入库，所以恢复场景恒为 `idle`。截图
`battle-battle-finished__1440-light.png` 与恢复后的弹窗可对照。

**为什么不修。** 这不是错误信息，是信息缺失（不显示 ≠ 说谎）。要如实显示，
得异步查 `gameRecords` 里是否已有这个 `seq`，并处理查询中 / 查询失败两种状态——
那是新增交互，不是缺陷修复；而 `saveState` 本身不持久化，恢复后无法从内存判断。
**入口**：如果要做，先在 `GameRecord` 或恢复流程里加一个「已入库」的确定信号。

### M-2 · 三位数回放编号密排时的可读性仍未实测

**现象。** 回放编号的字号已经达标（F-UI-14 修复：10.84px @390），但 ≥100 手时
pill 会宽到 1.189 用户单位，相邻两个重叠 **0.1886 单位**（@390 约 4px）；
后画的 pill 会盖住前一格**文字的右缘**约 0.069 单位（约 1.5px）。

**证据。** `ReplayBoard.tsx` 的注释里有完整推导；`bench/render.probe.mjs` 的
`LONG_RECORD_MOVES = 200` 只用来测拖动耗时，**不判编号可读性**；手上没有
≥100 手的真实棋谱，所以「数字仍读得出」这句话**没有实测支撑**。

**为什么不修。** 需要先造一份 200 手的真实对局存档并人工目视，或者给复盘页
加手顺列表（换载体）。前者是一次数据准备 + 目视验收，后者是设计变更——
都超出「终审修复」的半径。**入口**：`bench/render.probe.mjs` 已经能构造 200 手
棋谱，加一个截图与人工判读即可。

### M-3 · 高度极小的横屏窗口里，棋盘低于 320px

**现象。** 900×480 的窗口下棋盘约 **243px**，915×412 的横屏手机约 **207px**，
都低于 `DESIGN_SYSTEM` §8.1 的 320px 底线。

**证据。** `PHASE_05.md` §15.1 与 §15.7 第 3 条实测；探针的 1280×680 / 1440×700
矮窗口不在这一档（那里棋盘仍 ≥500px）。

**为什么不修。** 物理上放不下：320 + 顶栏 60 + 工具栏 44 > 412。
要么改 §8.1 的绝对措辞（例如「在高度允许时」），要么改小屏的高度策略
（例如横屏时把工具栏收进抽屉）——两件都超出最小修复，且后者有交互代价。
**入口**：先决定 §8.1 是硬约束还是目标，再决定改规范还是改布局。

## Low

### L-1 · 视觉规范没有逐项核销（F-UI-25）

Phase 01 改了圆角/间距令牌与嵌套边框，但没有一条「全仓核销」的记录。Phase 07
重新量化：矩形圆角现为 `rounded-md` **7** 处 / `rounded-lg` 15 处 / `rounded-xl` 8 处 /
`rounded-2xl` 2 处（另有 `rounded-full` 15 处，用于棋子、徽标、药丸，不属于体系发散）。
`rounded-md` 比 Phase 07 初次统计多 3 处，是收尾时把 `HintPanel` 两处与 `MoveList`
一处的裸 `rounded` 归并进来的结果；裸 `rounded` 现在全仓 0 处。
四档对应「小控件 / 卡片 / 面板 / 大容器」，是有层级的。**判定：已收敛，不再逐处改。**

### L-2 · 图标语言混用（F-UI-19）

顶栏用内联 SVG，其余页面用文字符号 `←` `→` `›` `✓`。不是缺陷：文字符号在中文
界面里可读、无歧义、不依赖图标字体，且天然有可访问名。统一成 SVG 是审美偏好，
会牵动多处按钮名与测试。**判定：接受。**

### L-3 · 触屏没有落子前预览（F-UI-10）

桌面有 hover 预览，触屏没有——平台本来就没有 hover。交叉点命中区已按规范放大，
四角与四边中点由 `tablet.spec.ts` 实测。**判定：接受。**

### L-4 · 结构审计的六项观察（审计标 Medium，终审下调为 Low）

Phase 07 的只读结构审计（`FINAL_AUDIT.md` §5 有完整表）按「可能影响维护成本」
标了六项 Medium；终审逐条对照「用户能不能观察到」之后**统一下调为 Low**——
它们都不改变任何可观察行为，且多数是既有设计取舍：
超大组件（`Board.tsx` 681 行等）、三处卡片 JSX 相似、`useAnalysis`/`useReplay`
两个单行 hook wrapper、`learnStore` 的 `view` 与 `progress.lastView` 双份、
`components/panels` 对 `features/battle/status` 的**类型**反向依赖、
测试对 DOM 结构的依赖。

逐项判断：**都不构成用户可观察的缺陷**，且多数是既有设计取舍——
- `Board.tsx` 的体量来自 SVG 几何与命中区，拆开会让「一处改动要跨文件」；
- 卡片 JSX 三处的标题/摘要/徽标结构相似但内容模型不同，抽 `Card` 会让
  三个调用点各带一组可选 prop；
- 两个 hook wrapper 删掉只省一行 `useStore(store)`；
- `view`/`lastView` 只有测试的 `setState` 能让它们不一致，用户路径不经过；
- 类型反向依赖不产生运行时循环（`madge` 通过），搬家收益是纸面整洁；
- 测试对 `data-player` / `stone-x-y` 的断言是 SVG 棋盘唯一可断言的载体。

**判定：记录，不在终审阶段重构。** 任务书明令禁止「为了追求表面完成度而大规模
推倒重写」，而以上改动都不改变用户看到的东西。

### L-5 · `BattleScreen` 订阅整个 settings store

`useSettingsStore()` 没有 selector，任一设置字段变化都会让对战页整页重渲染。
当前只有 3 个字段、变化频率极低（用户手动切换主题/声音/坐标），实测无可感知影响。
**判定：记录。**

### L-6 · 已完成课程的卡片边框对比度只有 1.77:1

`border-good/40`（`LearnScreen.tsx` / `PuzzleScreen.tsx` 的已完成卡片）对底色
只有 **1.77:1**，低于 WCAG 1.4.11 对非文字控件的 3:1 口径。

**为什么不修。** 完成状态另有 **✓ 徽标**与**读屏描述**两条通路（Phase 04 §21.2
之后两条都齐），边框只是第三层冗余；把不透明度提上去会让「已完成」在视觉上
抢过「当前推荐」。这是 Phase 04 做过的判定，本轮复核仍成立——补记在这里，
因为此前它只躺在 `PHASE_04.md` 的记录里，没进四档清单。
