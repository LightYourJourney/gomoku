## 二、布局决策（任务书 §二）

### 2.1 三档结构

| 视口 | 结构 | 棋盘（1440×900；「现」列是实测，新列是算出的下限，待探针复核） |
| --- | --- | --- |
| **< 1024** | 单列堆叠：状态条 → 棋盘 → 工具栏 → 右栏各面板（文档自然滚动） | 390 下 340（不变） |
| **1024–1439** | 两栏：`minmax(0,1fr)` + `clamp(300px,24vw,380px)` | 1024 下 **674**（现 362） |
| **≥ 1440** | 三栏：`clamp(240px,18vw,300px)` + `minmax(0,1fr)` + `clamp(300px,24vw,380px)` | 1440 下 **715**（现 778） |

侧栏宽度用 `clamp()` 而不是固定 px——固定 268/344 正是 F-UI-02 的成因。

### 2.2 1440 这个断点由 JS 决定，不是 CSS

**决策**：新增 `useMediaQuery('(min-width: 1440px)')`，用它决定「设置面板渲染在左栏还是右栏底部」，
以及中列的栅格模板。CSS 侧只保留 `lg:`（1024）这一档负责「堆叠 ↔ 两栏」。

**为什么不让 CSS 各写一份、用 `display:none` 切换**：

> 初稿在这里写过「读屏软件会看到两份」，**那是错的**——`display:none` 的子树根本不进 a11y 树，
> Playwright 的 `getByRole` 也跳过它。真正的受害面只有一个：**jsdom 里没有样式表**。

组件测试不 import `index.css`（只有 `lib/contrast.test.tsx` 用 `?raw` 读它），
所以 `hidden` 类在单元测试里**根本不生效**——同一组表单控件会出现两份，
`getByRole('radio', { name: '本地双人' })` 直接撞上 strict mode 违规。
代价是**此后每一条碰到设置面板的用例都得写 `within()`**，而这个阶段要新写九条这样的用例。

**宁可要一个 15 行的 hook，也不要两套控件**，更不要给测试套件加一笔永久的税。

**代价与约束**：

- **两个栅格模板必须互斥，用三元择一，禁止 `cx(base, wide && THREE)` 那样拼**。
  Tailwind 的同名工具类之间**没有优先级**，谁在生成的 CSS 里靠后谁赢——
  独立终审用本仓的 `index.css` + Tailwind 实编译过：两栏那一条排在**后面**，
  两条同时挂上去时 ≥1440 会**静默**退回两栏，而 JS 认为自己在宽档，左栏就不见了。
  这类坑仓库里已有先例（`Panel.tsx` 的 `bodyClassName` 注释）。
  同理 `lg:min-h-[344px]` 能压过 `BoardStage` 自带的 `lg:min-h-0`，也**只是因为它排得靠后**——
  这是运气不是保证，所以 §7.1 不靠它，靠的是把下限算对（见那条）。
  **反向验证清单里加一条**：把互斥改成并存，≥1440 的断言必须红。
- 断点值只允许出现在 `useMediaQuery` 的常量里一处；**CSS 里不得再写一个 1440 的媒体查询**，
  否则两处会分叉。
- `useSyncExternalStore` 在客户端首次渲染时**同步**读取 `matchMedia().matches`，不存在首帧闪烁。
- jsdom 没有 `matchMedia`（调用即抛错）。hook 里做能力判断，缺了就返回 `false`
  （= 走窄档分支），**不往全局塞桩**。

### 2.2.1 这件事与仓库一条**成文立场**正面冲突，必须正面回答

`docs/ARCHITECTURE.md:207` 与 `src/lib/motion.ts:5` 都写着一条立场：
**动效降级不判 `matchMedia`**，理由是两条——「用户中途改系统设置时分支不会更新」
「jsdom 里 `matchMedia` 缺失，靠它判定会让测试与真实行为脱节」
（`lib/motion.test.ts` 甚至有一条剥掉注释后 grep `matchMedia` 的守卫）。

本阶段要在布局上判媒体查询，**得说清楚为什么那两条在这里不成立、或者代价由谁付**：

1. **「中途改设置分支不更新」在这里不成立。** 那条针对的是**一次性读** `matchMedia(q).matches`
   的写法。这个 hook 用 `useSyncExternalStore` **订阅** `change` 事件——
   拖动窗口跨过 1440、或外接显示器换分辨率，分支都会跟着更新。
   **这正是它与动效那一处的区别**：动效要的是「CSS 自己降级」，判不判都得在 CSS 里；
   而布局这件事 CSS 做不到（见 §2.2 开头的理由），只能订阅。
2. **「jsdom 缺失 → 测试与真实行为脱节」这是真代价，我认。** 对价写明白：
   **宽档分支永远不被单测覆盖**，它由 `e2e/layout.spec.ts` 的真浏览器断言守
   （1440 有左栏 / 1439 没有 / 四个宽度下设置面板都恰好一份），
   再加一条反向验证（把 1440 改成 1280，断言必须红）。
   hook 自身只测两件事：没有 `matchMedia` 时不炸、有变化时跟着更新。
3. **`ARCHITECTURE.md` 要在动效那一段旁边补一句例外**（写进 §八 的文档清单）：
   否则下一个人读到「不许 `matchMedia`」会判这个 hook 违规，再下一次就会有人把它删掉。

### 2.3 中列的纵向预算（任务书 §七）

中列是 `flex flex-col`：`[状态条] gap [棋盘 flex-1] gap [工具栏]`。棋盘是**高度受限**的一方，
所以这条预算必须写在明处。**下面每个数字都是在真实浏览器里量出来的**（dev server + Playwright，
本轮改动之前），不是估的：

| 量 | 实测值 |
| --- | --- |
| 顶栏 | **69px**（不是 `min-h-15` 的 60——`py-3` 也占高，而**当时药丸还在顶栏里**） |
| `main` | 视口高 − 69（900 → 831，700 → 631） |
| `BoardStage`（≥1024） | 高度 = `main` 全高，`py-6` = 上下各 24px |
| 棋盘 | `min(列宽 − 48, main − 48) − 2`（2 = 边框） |
| 现状 @1920×900 | main 831 − 48 − 2 = **781** ← **已经被高度卡住**，不是被侧栏卡 |
| 现状 @1440×900 | 828 − 48 − 2 = 778 ← 宽度卡住 |
| 现状 @1024×900 | 412 − 48 − 2 = **362** |

**顶栏那个 69 是「药丸还在里面」时的值。** §3.1 把药丸搬进中列之后，
顶栏只剩品牌 + 导航 + 主题，`min-h-15`（60px）很可能重新成为下限——
那会让棋盘**多出约 9px**。所以推演表是**保守**的：实测只会更好，不会更差；
但**实施后必须重新量一次**，把这里的输入换成新值，不拿旧输入当结论。

新结构在中列多出两块，同时把 `BoardStage` 的 `py-6` 收到 `py-3`（**这一步是必须的**，
不留着 `py-6` 会直接把 1920×900 的占比打到 34%，见下面的反算）：

| 项 | 新值 |
| --- | --- |
| 状态条 | 38px（药丸 `py-2` + `text-sm`） |
| 工具栏 | 36px（`Button` 的 `md` 档 `min-h-9`） |
| 两个间隙 | 各 8px（`gap-2`） |
| `BoardStage` 内边距 | `lg:py-3` = 24px |
| 边框 | 2px |
| **合计** | **116px**（现状 50px） |

推演结果（未实施，实施后由探针复核）：

| 视口 | 新棋盘 | 现棋盘 | `boardRatioOfViewport` |
| --- | --- | --- | --- |
| 1024×900 | 674（宽度卡住） | 362 | **65.8%** ✓ |
| 1280×900 | 715（高度卡住） | 618 | **55.9%** ✓ |
| 1440×900 | 715（高度卡住） | 778 | **49.7%** ✓ |
| 1920×900 | 715（高度卡住） | 781 | **37.2%** ✓ |
| 1440×700 | 515（高度卡住） | 581 | **35.8%** ✓ |

判据是「任何 ≥1024 的视口下 ≥35%」（`DESIGN_SYSTEM.md` §12 第 3 条）。
**最紧的是 1920×900 与 1440×700 这两行：2.2 与 0.8 个百分点。**
所以 `py-6 → py-3` 不是审美选择而是判据要求（反算过：留着 `py-6`，1440×700 会掉到 **34.1%**，
直接红；1920 掉到 36.0%，勉强过）。实施后必须实测——不够就得再省，**不许改判据**。

不为了凑高度去加 `Button` 的第三档尺寸：`Button` 的注释写明「只有两档，第三档没有真实需求」，
36px 也高于 WCAG 2.5.8 的 24px 下限。

### 2.4 不因侧栏展开而跳动

左栏的「对局设置」折叠**只改变纵向高度，不改变列宽**——列宽是 `clamp()` 的定值，
所以棋盘不会因为折叠/展开而改尺寸。三档之间切换时棋盘尺寸本来就会变，那是响应式应有的行为。

## 三、对局状态呈现（任务书 §三）

### 3.1 新增 `MatchBar`

位置：中列顶部，紧贴棋盘上方。结构：

```
┌────────────────────────────────────────────────────────────┐
│ ● 你 · 黑（先行）      [ 轮到你落子 ]      ○ AI · 初级  12 手 │
└────────────────────────────────────────────────────────────┘
```

- **左 = 黑方、右 = 白方**：固定的空间映射，与「你」在哪一侧无关。
  人机模式下玩家的那一侧标「你」，另一侧标「AI · 难度」；本地双人标「黑方 / 白方」。
  **不沿用单人视角**——双人时写「你」是错的，任务书点名。
- 中间是状态药丸（沿用 `StatusPill`，保留 `data-testid="status-pill"`）。
- 行动方（`game.current`）高亮：**`bg-accent-soft text-accent`**，另一方 `text-muted`。
  终局两侧都不高亮。
  **不用 `bg-surface-2`**：`DESIGN_SYSTEM.md` §2.2 把 `surface-2` 定义为「面板内的次级块 /
  悬停底色」，而「当前所在位置」的既定映射是 `accent-soft` + `accent`（顶栏导航选中项就是它）。
  §10.3 还专门写过为什么不能靠「浮起/凹陷」表达选中——`surface-2` 在浅色比 `bg` 深、
  在深色比 `bg` 浅，同一套类名一张下沉一张浮起。这一对颜色也在 `lib/contrast.test.tsx`
  的配对表里，两套主题的对比度都有人守。
- 右端是手数。用 `grid grid-cols-[1fr_auto_1fr]` 让药丸居中，右格内容右对齐。

### 3.2 状态的唯一真相仍是 `describeStatus`

`MatchBar` 只从 `describeStatus` 拿**标签与色调**，两侧的姓名/身份自己拼——不复制任何胜负判断。
这样界面可见状态与 `BoardAnnouncer` 的读屏播报不会分叉（任务书要求）。

### 3.3 顺手修掉 F-UI-06：「轮到 AI」时转圈在说谎

`StatusPill` 现在只要 `tone === 'thinking'` 就转圈。而 `describeStatus` 在人机模式下
**只要轮到 AI 就返回 `thinking`**——包括「轮到 AI」但根本没有请求在飞的情况
（引擎报错后卡住、点重试之前）。截图证据在 FINDINGS 的 F-UI-06：
`battle-battle-ai-error__1440-light.png` 里药丸写着「轮到 AI」，转圈照转，同一屏的引擎面板是红的。
**转圈的语义是「正在进行」，这里真实情况是「引擎挂了 / 欠着一手」——反馈在撒谎。**

**处置**：`StatusPill` 增加 `busy` 入参（来自 `aiThinking`），转圈判据改成
`tone === 'thinking' && busy`；不忙时退回显示 `status.player` 的棋子点。
`describeStatus` 的判定一行不改（它是 `BoardAnnouncer` 共用的真相）。

**连带影响**：探针的 `measurements.spinner`（读 `[data-testid="status-pill"] .animate-spin`）
在 `battle-ai-error` 状态下会从「有」变成 `null`。这是修复本身的可查证据，
不是指标丢了——after 对照里要点明这一条。

### 3.4 「AI 出错 / 欠着一手」这一档，状态区只做一半，另一半留给引擎面板

任务书 §三 要求区分九种情形，其中第 3 种是「AI 轮次尚未完成或出现错误」。
**本阶段的处置**：状态药丸显示「轮到 AI」且**不转圈**（§3.3），与「AI 思考中…」明确分开。

**刻意没做的**：不在状态条里再放一个「重试」。
理由：`AiPanel` 已经是这条恢复路径的入口（它的注释写明「重试入口的显隐只由 `canRetry` 决定」），
再放一个就是同一动作两个入口。**代价要说清楚**：<1024 时引擎面板在棋盘下方，
出错时玩家看到的只有「轮到 AI」，得往下滚才知道发生了什么。
这条取舍如果终审认为不可接受，改法是让状态条在 `aiStuck` 时多一行「引擎没落子，去下面重试」的
提示，而不是再放一个按钮。

## 四、工具栏重组（任务书 §四）

### 4.1 一个工具栏，四个动作

`ControlBar` 重写为：`[悔棋] [求提示] [重新开始] ……… [认输]`

- `flex flex-wrap items-center gap-2`；认输 `ml-auto` + `border-l border-border pl-3`。
  窄屏放不下时自然换行，认输落在自己那一行的右端——**可发现，但与普通操作分开**。
- **「求提示」用 `variant="primary"`**：`DESIGN_SYSTEM.md` §6.1 把它列为 `primary` 的典型
  （「当前唯一的下一步」），而它现在是 `HintPanel` 里自绘 `bg-accent` 的裸 `<button>`——
  搬过来顺手收编进 `Button`。搬完要复核「一屏最多一个 `primary`」：
  终局弹窗的「再来一局」也是 `primary`，但两者不同屏。
- 禁用条件**全部沿用现有 store 判据**，不自己发明：
  `canUndo({game,mode,humanColor})`、`canHumanPlay(...)`（求提示的可用条件）、
  `game.status === 'playing'`（认输）、`hintThinking`（求提示进行中）。
- **禁止绕开业务逻辑改棋盘数据**：工具栏只调 `undoMove` / `requestHint` / `newGame` / `resign`。

### 4.2 「求提示」只留一个入口

按钮从 `HintPanel` **移出**，落到工具栏。`HintPanel` 变成纯展示（候选、紧急度、置信度、
「收起」，以及**有候选时才出现**的技术脚注，见 §6.4）。空状态的引导文案从「点『求提示』…」
改成「用棋盘下方的『求提示』…」。这样同一个请求不可能被两个入口重复触发（任务书要求）。

## 五、防误触确认（任务书 §五）

### 5.1 触发条件表

| 操作 | 何时拦 | 何时放行 | 确认后 |
| --- | --- | --- | --- |
| 重新开始 | `status==='playing' && moves.length>0` | 空棋盘、终局 | `newGame()` |
| 认输 | `status==='playing'`（**不看手数**） | 只有终局 | `resign()` |
| 切换模式 | `status==='playing' && moves.length>0` | 空棋盘、终局 | `setMode(next)` |
| 切换执子 | 同上 | 同上 | `setHumanColor(next)` |
| 终局弹窗的「再来一局」 | **不拦** | —— | `newGame()` |

**认输与其余三条的条件不同，这是有意的**（初稿把两者说成一样，被独立终审抓到）：
任务书只对「重新开始」写了「空棋盘无需不必要的二次确认」，对认输写的是
「进行中的对局点击认输，需要明确的确认」——**没有豁免**。
所以空盘点认输**照样确认**：那时虽然盘上没有子，但玩家仍然是在结束一局。

难度切换沿用既有语义（只改 `difficulty`，**不重开**），不加确认——任务书点名不许擅自改。

### 5.2 确认之前不提交任何东西

这是本节最容易做错的一条。做法：

- 设置面板里的 `Segmented` 是**受控**的，`value` 来自 store。
  点击只调 `onModeChange`，而 `BattleScreen` 给它的回调**先判断要不要拦**：
  要拦就只 `setPendingConfirm({kind, next})`，**一次都不碰 store**。
- 于是「取消后原有选中项保持不变」是**结构性成立**的，不靠回滚。
- 取消路径完全不碰 store → 「AI 正在思考时取消不应中断原请求」也是结构性成立的。
  测试仍要断言 `pendingRequestId` 与 `aiThinking` 原样保留（防止将来有人在取消里加了副作用）。
- 确认路径调的就是原来的 store action，`requestId` / `gameVersion` 的安全语义一行不改。
  「旧 Worker 响应不得进入新棋局」由 `newGame()` 把 `pendingRequestId` 置空保证——
  store 层已有 4 条用例守着（`gameStore.test.ts` 的「过期与不匹配的 AI 响应」）。

**`Segmented` 要增加一个 `canChange?: (next: T) => boolean` 否决口。**
不加的话键盘路径会留下一个坏状态：`Segmented` 的 `moveTo` 是
「先 `onChange(next)`、**再**把焦点搬到 `next`」（`Segmented.tsx:53-57`），
而拦截正好挂在 `onChange` 上——方向键 → 弹确认 → 取消之后，
焦点落在那个 **`aria-checked=false` 且 `tabIndex=-1`** 的选项上，
roving tabindex 与选中项对不上：整组的 Tab 停靠点说「选中的是 A」，焦点却在 B。

有了否决口，两条路径统一成：

- 键盘：`canChange(next)` 为假 → **不改选中、也不搬焦点** → 焦点仍在选中项上 ✓
- 点击：浏览器已经先把焦点给了被点的按钮（Safari 除外），否决时显式
  `focus()` 回选中项 ✓

于是「取消后焦点回到原操作位置」落到的**永远是那个 `aria-checked=true` 的选项**，
§9.1 第 6、7 条据此加一条断言：取消后 `document.activeElement` 的 `aria-checked` 为 `true`。

### 5.3 `ConfirmDialog`

基于现有 `Modal`（不复制弹窗实现）：

```
title        「重新开始？」/「认输？」/「切换模式？」
description  后果描述（会丢掉什么、保留什么）
footer       [取消] [确认重新开始 / 确认认输 / 确认切换]
```

**确认按钮的文案必须与工具栏那颗不同名。** `Modal` 只盖一层遮罩，
**不设 `aria-hidden` / `inert`**（`Modal.tsx:122`），底下的工具栏按钮仍在 a11y 树里——
确认按钮若也叫「认输」，同页就有两个同名按钮，Playwright 与 Testing Library 会直接抛
strict mode 违规，而 §9.4 里「点按钮 → 点确认」的写法就不成立了。
「确认认输」这样的文案同时也更清楚：按钮自己说出了后果。

- 认输那一颗用 `variant="danger"`。
- **Escape = 取消**：`Modal` 的 `onClose` 接到 `onCancel`。
- **焦点**：
  - 打开时仍由 `Modal` 把焦点搬到对话框容器（`tabIndex=-1`），
    读屏软件因此能念出标题与后果描述——这正是任务书要的「清楚的标题与后果描述」；
    Tab 之后的顺序仍由 `Modal` 的循环处理器约束在框内。
  - **取消后焦点回到原操作位置**：见 §5.4。
  - **确认后焦点落在仍有效的控件上**：三条确认路径的触发控件在确认后都仍然有效
    （重新开始按钮、模式/执子的选中项），所以同一条规则覆盖；
    认输的触发按钮会 `disabled`，同一次提交里终局弹窗会接管焦点。

### 5.4 `Modal` 的焦点归还：为什么这次可以做了

`Modal.tsx` 里现在有一段注释，说明「关闭后把焦点还给原处」**加过又撤掉了**，理由是：
本应用唯一的弹窗是终局结果弹窗，而它**不是被某个控件打开的**（对局结束自动弹），
打开前持有焦点的元素在对局结束时必然不可聚焦，实测还原从未生效。

**这个理由对确认弹窗不成立**：确认弹窗是被点击打开的，触发控件在关闭后通常仍然有效。
所以本阶段把它加回来，判据是：

```
关闭时：
  focusAfterClose 给了 → 聚焦它（ResultDialog 走这条，行为与之前逐字相同）
  否则若「焦点已经被别处拿走」（activeElement 不是 body）→ 什么都不做
  否则 → 聚焦「打开那一刻的 document.activeElement」
```

**第二道门不能省，计划里必须写明**（初稿只写了三条「还能不能聚焦」的检查，
漏了这道门）：弹窗开着的时候焦点有可能被别处拿走（程序化 `focus()`、浏览器行为），
那时抢回来是帮倒忙，而 `Modal.test.tsx` 既有的那条「不传这个 prop 时不动焦点」
描述的正是这个场景。

**「还能不能聚焦」的三条检查最后被删掉了，只留「打开时确实有东西持有焦点」。**
原因写在 `Modal.tsx` 的注释里，这里是它的出处：反向验证时发现那三条**观测不到**——
禁用控件与已卸载的节点本来就 `focus()` 不动，浏览器与 jsdom 都不会把焦点给它们，
撤掉判据用例照样绿。观测不到的判据就是没有判据。**独立终审建议改成
`el.matches(FOCUSABLE)` 也是这个方向，但那同样观测不到**，所以按
`AGENTS.md` 的「不做没验证的复杂度」从简。

配套：新增单元用例证明「点按钮打开 → 取消 → 焦点回到那个按钮」与
「弹窗开着时焦点被别处拿走 → 关闭时不抢回来」（两条都做过反向验证），
并在 `e2e` 里复核真实 Tab 顺序（jsdom 不做真实焦点顺序）。
`Modal.test.tsx` 顶部那段「刻意不测」的注释要同步改写——它描述的事实变了。

## 七、棋盘尺寸与空间分配（任务书 §七）

### 7.1 `BoardStage` 的两处改动

1. **增加 `className` 入参**，供调用方追加布局类。
2. **删掉 `order-1 lg:order-2`**。

为什么删：`BoardStage` 现在是「我在父布局里排第几」这件事由它自己声明。对战页的新中列里
它的兄弟是状态条与工具栏，`order-1` 会把棋盘排到工具栏后面去——**同一份声明在两种父布局下
含义不同，这本身就是缺陷**。位置属于父布局。

**三个既有调用点一行都不用改**（这一条是核对过的，不是推测）：
`PracticeBoard` / `StepView` / `ReplayBoard` 里 `BoardStage` 都是 DOM 里的第一个孩子，
它们的 `aside` 带着 `order-2 lg:order-3`（ReplayBoard 是 `order-2 lg:order-2`）。
棋盘退回默认 `order: 0` 之后仍然排在 aside 前面（0 < 2），与现在 `order-1/lg:order-2`
的结果**逐字相同**，而 DOM 顺序本来就是棋盘在前。也就是说那两行类名一直是冗余的。

对战页给它的类：`lg:flex-1` 加上下限。

**下限原本打算写 `lg:min-h-[344px]`（= 320 + 24 内边距），最终一个都没写。**
独立终审的推导是对的：`cqh` 量的是**内容盒**，而 `BoardStage` 自带 `lg:py-3`，
若照 320px 写下限，棋盘会缩到 296px、**静默**跌破 `DESIGN_SYSTEM.md` §8.1 的硬下限。

但实施之后发现**下限本身不需要**：棋盘是跟着高度**收缩**的（任务书允许「尺寸收缩」），
而探针实测最矮的两档 SHORT 视口下是 497 / 517px，离 320 还远（§13.3）。
无下限就无内边距折算问题，也省掉了「`lg:min-h-[344px]` 与自带 `lg:min-h-0` 谁赢」
那场 CSS 顺序赌博。**判据仍由 `yarn ui:probe` 的闸门实判**（判据 2：棋盘 ≥320）。

**顺带改一句会变成假话的注释**：`BoardStage.tsx:6` 把「移动端的 `order-1`」
列为抽出来的理由之一，删掉那两行之后这句就不成立了。

### 7.2 不动的部分

- 15×15 的棋盘算法、`AXIS`、`HALF_CELL`、`STONE_RADIUS`：一行不改。
- SVG 坐标系与命中区（`rect[intersection-*]`、roving tabindex、方向键）：一行不改。
- `container-type: size` + `aspect-square w-[min(100cqw,100cqh)]`：保留。
  它在 ≥1024 成立的前提是父容器高度确定——新中列必须给它一个确定高度（`lg:flex-1` + `min-h-0`），
  否则 `cqh` 循环求值会塌成 0。

### 7.3 矮窗口

≥1024 时应用根是 `h-dvh overflow-hidden`（`App.tsx`），溢出会被裁掉而不是滚动。

**中列最终没有加 `lg:overflow-y-auto`**（初稿打算加）：棋盘本身就是跟着高度缩的，
滚动条永远不会出现——留一段永远不执行的 CSS 不如不加。任务书那句话是
「允许合理滚动**或尺寸收缩**」，这里走的是后半条，实测见 §13.3。
移动端（<1024）是文档单滚动，实测只有棋谱列表那一个元素级滚动容器 ✓。

## 十、风险与取舍（写在这里接受复核）

1. **JS 断点是第二处真相。** 1440 只允许出现在 `useMediaQuery` 的常量里；
   CSS 里不得再写 1440 媒体查询。若将来有人加了，两处会分叉——
   这条在 `DESIGN_SYSTEM.md` §10.1 里写明。
2. **≥1440 棋盘高度会变小。** 现状 1440 下 778、1920 下 781；
   新结构把状态条与工具栏放进了棋盘所在的列，中列自己的开销从 **50px**（`BoardStage` 的
   `py-6` 48 + 边框 2）涨到 **116px**，棋盘降到 **715**。
   **这是任务书指定结构的必然代价**，如实记进报告与 before/after。
   绝对尺寸仍远高于 320px 下限，占比 37–50%（判据要求 ≥35%）。
   **1024 与 1280 是净改善**（362 → 674；618 → 715）。
3. **1024–1439 的设置藏在右栏底部。** 用户需要往下滚才看到。低频设置如此处置比挤压棋盘好，
   但与宽屏「左栏常驻」不一致。取舍记在 `DESIGN_SYSTEM.md`。
4. **确认弹窗多一次点击。** 用严格条件把它限制在「进行中（重新开始 / 模式 / 执子还要已有落子）」，
   终局与难度切换不打扰。
5. **`HintPanel` 的按钮搬走后，它的既有单测要改 10 处左右。** 这是**搬入口**不是删功能：
   候选、置信度、收起都还在。改测试时逐条确认断言的东西仍然成立，不许整体删断言。
6. **`StatusPill` 的转圈判据变了**，`e2e/a11y.spec.ts` 里若有关于 spinner 的断言需要复核。
7. **`Panel` 加 `collapsible` 会影响约十个使用点。** 默认 `false`，未传参的调用行为逐字不变。

## 十三、实施记录

按时间顺序，只记**与计划分叉的地方**和**实施中才发现的事实**。计划的最终形态见上，
两者不一致时以本节为准。

### 13.1 计划的 §5.2 有个真 bug：否决口被写成了纯谓词

计划把 `Segmented` 的否决口设计成 `canChange: (next) => boolean`，拦截逻辑写在
`BattleScreen` 的 `onChange` 回调里。实施后 e2e 直接打红：**点「人机对战」什么都不发生**。

原因：`canChange` 返回 `false` 时 `Segmented` **不会调 `onChange`**——
于是「打开确认弹窗」那半件事压根没执行，两边都不动。

改法：钩子改名 **`beforeChange`**，并且**把「拦下」整个写进钩子**
（打开弹窗的副作用由它自己完成）。名字从 `canChange` 改成 `beforeChange` 就是为了
说清它不是纯谓词。这个 bug 只有真点一下才会暴露——两条单元用例都写不出来，
因为它们都在测「否决之后状态没变」，而那恰好就是 bug 的表现。

### 13.2 终审警告的 CSS 顺序坑，真的踩了一次

给 `BoardStage` 传 `className="lg:py-2"` 想覆盖它自带的 `lg:py-3`——**没生效**，
实测棋盘比算出来的小 16px。Tailwind 的同名工具类之间没有优先级，
自带的那条在生成的 CSS 里更靠后，赢了。改法是把默认值改在组件内部，
并在注释里写明「这个值只能改在组件里，从调用方传类名是没用的」。
终审在计划阶段就点出过这一类风险（§十二 的 P1-3），它是对的。

### 13.3 一条判据真的红了，而且是量出来的

中列纵向开销 142px 时，**1440×700 的 `boardRatioOfViewport` 是 34.0%，低于 35% 的判据**。
不是估的，是探针式的实测。逐项量过之后按这个顺序砍：状态药丸 `py-2`→`py-1.5`、
`BoardStage` 的 `lg:py-3`→`lg:py-2`、中列 `py-3`→`py-1.5`、`gap-2`→`gap-1.5`，
开销降到 126px，1440×700 变成 **35.9%**。**判据一个字没改。**

顺带删掉了计划 §7.3 里的 `lg:overflow-y-auto`：棋盘是跟着高度缩的，
滚动条永远不会出现——留着就是一段永远不执行的 CSS。
任务书允许「尺寸收缩」，而 SHORT 档（1280×680、1440×700）实测棋盘 497 / 517，
都在 320 下限之上。

### 13.4 设置默认折叠的决定，被既有 e2e 推翻了

计划（终审也认可）让 1024–1439 的两组设置都默认折叠。实施后 **9 条 e2e 变红**，
其中 5 条是既有用例——它们全在第一步就 `getByRole('radio', { name: '本地双人' })`。

那不是测试写错了，那是**测试套件在说「切模式是第一步就会做的事」**。
任务书 §六 也把模式/执子/难度定义为「需要经常调整的基础对战设置」。
于是改成：`对局设置` 恒展开、`显示与声音` 恒折叠，折叠状态不随视口变。
代价是右栏在 1024–1439 的高度账从「−140」变成「相抵」，如实记在 §6.4。

### 13.5 空盘求提示本来就没有候选

新写的键盘用例里，我在空盘上求提示，等不到候选，一度以为是工具栏没接上。
实测下来是**引擎在空盘上没有威胁可算，候选本来就是空的**——
既有的「请求提示后棋盘上出现候选标记」那条也是先落了一手才求提示的。
是用例的局面设错了，不是产品缺陷。

### 14.4 探针抓出来的三个**本阶段自己引入**的缺陷

三条都不是估的，是量出来的，而且都属于「不量就发现不了」的那一类。
**基线两次量测都是干净的**（`contrastViolations` 0、`clipped` 里没有 battle 状态），
所以三条都是本阶段引入的：

1. **对比度 4.49:1，比 4.5 的线差 0.01。** `battle-thinking` / `battle-ai-error` 两态各报 1 处，
   元素是 `span{专家}`——`MatchBar` 里 AI 那一侧的**难度**文字。原因：那一侧被
   `bg-accent-soft` 点亮，底色比页面底色浅，`text-faint` 就压线了 0.01。
   修法：行动方那一侧不用 `text-faint`（继承父级的 `text-accent`）。
2. **折叠标题的命中区 20px**，低于 WCAG 2.5.8 的 24px。136 处，全是
   `button{对局设置}` / `button{显示与声音}`——`Panel` 新加的折叠按钮只有标题文字那么高。
   修法：`min-h-7`（28px）。
3. **390 下状态条把 AI 那一侧切成了「A」与「初…」。** 6 个状态各 2 处
   （`span{AI}` clientWidth 10 / scrollWidth 19）。成因：状态条写的是
   `grid-cols-[1fr_auto_1fr]`，两侧各分到固定一半，30 手时「30 手」把右侧挤爆。
   第一版修法是窄屏不显示手数；**两轴复审时改成按内容占宽**
   （`auto_minmax(0,1fr)_auto` + 药丸居中），两样都留得住——任务书 §三 本来就要求
   状态区默认展示手数，藏掉它是在拿规格换空间。现在 390 下的 `clipped` 是空的。

**这三条排在「本阶段最值得记的事」里**：判据与探针是给**新代码**准备的，
它们抓到的第一批东西就是新代码。三条里没有一条是单元测试能抓到的。

### 14.5 反向验证（撤掉修复，确认用例真的会红）

| 撤掉什么 | 结果 |
| --- | --- |
| `Modal` 的焦点归还整段 | `Modal.test.tsx`「取消之后焦点回到触发它的按钮」**红** ✅ |
| `Modal` 的「焦点不是 body 才还」那一道门 | 「焦点被别处拿走就不抢回来」**红** ✅ |
| `Segmented` 的 `beforeChange` | 两条否决用例**红** ✅（写代码之前就是红的） |
| 转圈判据从 `busy` 退回 `tone` | `StatusPill` 与 `MatchBar` 各一条**红** ✅ |
| 断点常量 1440 → 1280 | `三档结构` 的两条**红** ✅ |
| 两个栅格模板由互斥改成并存 | **`对战页：棋盘尺寸预算` @1440/@1920 红**（棋盘塌到 263 / 298px）✅ |

**最后一条有个意外的结论**：`三档结构` 那组**抓不到**模板并存——

真正抓住它的是**棋盘尺寸**那条（263px < 620）。
「结构对不对」与「东西够不够大」是两回事，前者可以被后者兜住，反过来不行。
