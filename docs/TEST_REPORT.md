### 整分支终审（独立上下文，审全部 9 个提交）

终审抓到 5 个真问题，全部修掉并各补了先红后绿的用例：

| 问题 | 影响 | 修法 |
| --- | --- | --- |
| 分析管线的响应闸门只比局面号，而每个 run 的局面号都从 0 开始——上一局的迟到响应会被下一局当成自己的 | B 的分析永久卡在「分析中 0/9」，缓存永不写入 | 加 `runId`：响应必须属于当前这一次分析；被丢弃的响应不许改写 `inflightIndex` |
| 0 手棋谱（开局即认输）没有请求也没有收尾；满盘和棋的末局响应 `move === null` 直接 return | 面板永久停在「分析中 0/0」或「N-1/N」 | 空队列立即收尾；`move === null` 走收尾路径（并补上「给上一手补后续评分」的重试） |
| 终局后悔棋再终局会第二次触发入库 | 棋谱库里同一局两条 | **保留「终局可悔棋」这一既有行为**（Phase 1 的测试钉着它），改为 `replacesSeq`：第二次终局替换上一条而不是新插一条 |
| `put` 把失败吞进内存兜底后照常 resolve，`'failed'` 不可达 | 隐私模式下界面说「已存入」、刷新就没了 | `put` 返回 `{ record, persisted }`；没真落库就抛错，界面如实显示失败 |
| 引擎走捷径（必胜/必防）时评分是 `±WIN_SCORE` 量纲，与真实评估不可比——「亏损榜」前三行全是「与引擎一致」 | 亏损榜由「哪个局面触发捷径」决定，不是亏损 | 着法与引擎首选相同即 `loss = 0`，且不参与亏损榜排序 |

外加两处：离开复盘页时停掉分析（丢弃结果；引擎没有取消接口，已发出的那一次搜索仍会跑完）；ROADMAP 的「会话内缓存」改为如实的「复盘页打开期间有效」。

### 对上述修复的两轴复审（`/code-review max --fix`）

审 `720ad70`（就是上面那批修复本身）。两轴独立跑，**都指向同一条**——而且它是这一阶段最该记住的教训：

| 发现 | 性质 | 修法 |
| --- | --- | --- |
| **上一条修复落在死代码里**：`buildSummary` 加了「loss 为 0 不进亏损榜」的过滤，但全仓**没有任何生产调用点**——界面自己 `sort + slice` 重算了一遍。修复提交声称「亏损榜不再全是『与引擎一致』」，而真实界面上一行没变 | 修复未落地 | `ReviewScreen` 改走 `buildSummary`；补一条按界面实际渲染路径断言的用例（脚本化引擎造出「捷径评分差很大但着法相同」的手，断言榜单只有真正走亏的那一手） |
| `move === null`（满盘和棋的末局）仍被写进上一手的「后续评分」——`score: 0` 硬编码，于是末手算出凭空的巨额亏损，与 ROADMAP 写的「直接跳过（不编造结论）」相反 | 编造结论 | `fillReply` 在 `move === null` 时不再写 reply；该手连同它的「后续局面」一起跳过，`total` 相应减一，面板不会停在「N-1 / N」 |
| 替换棋谱的顺序是**先删后写**：写入退到内存兜底时旧条已删、新条没落库——刷新后整局从棋谱库消失（比原来「多一条」更严重） | 新引入的丢失窗口 | 逻辑下沉为 `saveGameReplacing`：**先写后删**，没落库就不动旧的；并在 `replacesSeq` 为 null 时按**内容**（手顺 + 先手方）找旧条，覆盖「刷新后内存链接丢失」的路径 |
| `docs/ARCHITECTURE.md` 仍写「分析过期校验改走 `moveIndex`」，`stop()` 被描述成「停掉在跑的分析」 | 文档与实现不符 | 改为**三重闸门**（runId + inflightIndex + moveIndex/gameVersion）；措辞改成「丢弃结果——引擎没有取消接口，已发出的那一次搜索仍会跑完」 |

规格轴同时确认了一条重要的**否定结论**：这次 loss 语义的改动**没有把真实亏损一起抹掉**——实测「引擎走捷径（score = WIN_SCORE）而玩家走了别的」时 loss = 2,000,000、标签「分差极大」、排面板第一；loss 强制 0 的充要条件就是「着法相同」，那时玩家做的正是引擎自己的选择。

**教训**：上一条修复写在了没有调用点的函数上，测试也只测那个函数——**测试全绿、文档说修好了、用户看到的没变**。这正是「断言比名字弱」的另一种形态：测的不是用户走的那条路。

### 发现并修复的缺陷

**1. 棋盘命中区偏移半格（真实交互缺陷，已修复）**

现象：点在交叉点正中，棋子却落在右下相邻的那一交叉点上。

原因：命中区起初是半径半格的圆，相邻圆只相切、格间留死区；改成整格正方形后仍不准。实测 `document.elementFromPoint` 在交叉点正中返回的是对角相邻那一格，把命中区域逐点扫描后发现每个格子的命中范围比它声明的几何**向外多了半格**。

根因是 SVG 规范里 `pointer-events: all` 的命中范围是「内部 **+ 周界**」，而未指定 `stroke` 时 `stroke-width` 的初始值是 `1`——周界因此有一整个用户单位宽，每边多出半格。修复是把命中矩形的 `strokeWidth` 显式置为 `0`。

这个缺陷**单元测试抓不到**：jsdom 不做命中测试，`fireEvent.click` 直接把事件派给指定元素。只有真实浏览器能暴露它。修复后补了 E2E 用例「落子位置与点击的交叉点一致」，覆盖四个角与天元。

**2. 文案换行（布局缺陷，已修复）**

「重新开始」「跟随系统」在各自容器里被折成两行。修复：按钮与分段控件加 `whitespace-nowrap` 并收紧内边距，同时把右栏宽度从 324px 调整为 344px。

**3. 棋盘右下方留白不平衡（视觉缺陷，已修复）**

坐标标签原先只在顶部与左侧，右下留白显得空。改为四条边都标注，外框因此均衡。

**4. 胜利连线压在棋子上（视觉缺陷，已修复）**

连线原先把棋子糊住。改为连线绘制在棋子**下方**、高亮环绘制在棋子**上方**，棋子质感得以保留。

### 那道「重复题」，以及我自己在这一轮把它固化了下来

`forced-deep` 与 `vcf-basic` 共用 `FOUR_THREE` 这个常量。标准轴先发现「同一个字符画抄了三遍」，我照着抽成了共享常量——**于是这条错误从「两份重复」升级成了「有意的共享」**，看起来更正当了。规格轴拿 `JSON.stringify` 一比对，两个盘面逐字相同，而题面写着「比上一题多了一手棋的准备」。

修法是换盘面，而且**换完必须重量一遍，不能照着新盘面顺手编一段题面**。实测：

| 候选着法 | `maxPlies=3` | `maxPlies=5` | `maxPlies=7` |
| --- | --- | --- | --- |
| 新盘面的 (6,10) | **无解** | 5 手取胜 | 5 手取胜（不再变深） |

`analyzePoint` 确认 (6,10) 是 `four: 1` + `openThree: 1`——**横向冲四、纵向活三，是真四三**。于是 `maxPlies` 从 7 收紧到 5：原来那个 7 是照抄的，5 才是量出来的。

顺带说明为什么「多一手棋的准备」这条路走不通：要 7 手取胜得凑出 2+2+3 三段，而那样的盘面在根节点上就已经存在五手杀（求解器先找到的就是它），**构造不出「只有七手杀」的局面**。所以这一节如实记成「两个真四三、五手杀」，不编一个更深的。

## 四、已知问题

**存档格式升级会丢弃旧存档。** `SCHEMA_VERSION` 已从 1 升到 2（新增 `resignedBy`）。升级瞬间，旧格式的存档会被 `decodeSession` 判为不合法而丢弃，进行中的对局会凭空消失、回到空盘——**这是静默的**，界面上不会提示。App 尚未发布，实际影响为零；但正式发布之后若再改格式，必须写迁移函数，不能继续用「不匹配就丢弃」这一招。

**首次音效可能被浏览器拦下。** 页面加载后如果第一手音效由 AI 应手触发（而非用户点击），`AudioContext` 会在没有用户手势的情况下创建，Chrome 会挂起它并打印 `The AudioContext was not allowed to start`。影响是这一手没有声音；下一次由点击触发的播放会调用 `resume()` 自愈。彻底的修复（绑定首个 `pointerdown` 预热）排在 Phase 5。

**专家档的深度上限（8 层）从未达到。** 时间预算才是真正的约束，`depth` 只是安全上限。构造基准上最多完成 6 层，真实对局中观察到 7 层。要让它名副其实，得先把单节点成本压下去。

**单次 `evaluateBoard` 约 72 µs，是当前引擎的瓶颈。** 专家档一次 2.6 秒的搜索里，光局面评估就占一秒以上。下一步性能优化应该做增量评估（只重算受落子影响的线段），而不是继续调 alpha-beta。

**不算 VCT。** `threatThrees` 五档全为 `false`，即只用 VCF。实现与测试都在 `src/ai/threat.ts` / `threat.test.ts`，实测代价是 VCF 的 38–520 倍，而在测过的三个局面上 VCF 都给出了同样的结论。后果是「先做活三逼出弱点、再用冲四收掉」这类需要两层活三的杀型找不到。这是一处**有意的漏杀**。

**算杀的活三链只允许一层**（`MAX_THREE_LAYERS = 1`），更长的活三链同样是有意的漏杀。

**局面评估不识别跨方向的组合形状。** 单点分析有双四 / 四三 / 双活三的加成，整盘评估仍是按线段独立累加的，看不到它们的联动。

**尚无键盘操作。** 棋盘目前只能鼠标 / 触摸操作，排期在 Phase 5。

**残局题只有 15 道，且都是黑先。** 白先、以及需要多手规划才能看出杀机的题目还没出。

**没有 7 手以上的强制取胜题。** 两道 `forcedWin` 的题目里引擎给出的都是 5 手路线（`maxPlies: 7` 是上界不是紧界）。构造一条真正 7 手的链，需要在两条线的交叉处制造两次「冲四 + 活三」，手工出题的成功率很低——这一条是**如实记下没做到**，不是「已支持」。

**学习进度没有个性化。** 做错只给一次重试，不会记下「这个人在活三上反复出错」并回头补课。

Phase 1 遗留、现已解决的两项：只开放两档难度（Phase 2 起五档全开）、引擎不识别跳型棋型（Phase 2 改为窗口枚举，`mm.mm` 这类结构能看见了）。
