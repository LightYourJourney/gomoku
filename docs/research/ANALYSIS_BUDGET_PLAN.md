# 复盘分析档位与预算：实验计划（裁定 21）

> 现状：复盘分析固定用**初级档、每局面 400 ms**（`ReviewScreen` 的 `AnalysisPanel`，`ANALYSIS_BUDGET_MS`）。
> 原先不放开的理由是「分析与落子共用一个 Worker，分析会挡住落子」——阶段 B 改成双 Worker 后这个前提不成立了。
> 本计划只做**实验**、出数字，选哪一组由所有者定；实验期间不改产品代码。

## 要回答的问题

1. 换更高的档位 / 更多的预算，「未算分差」少多少、结论（亏损榜）变多少？
2. 代价多大：一局 60 手的棋，从点「开始分析」到全部出结论要多久？
3. 档位越高越「对」吗？——分差是引擎的看法，档位一变结论就变；**需要说明的是一致性，不是正确性**。

## 候选组

| 组 | 档位 | 每局面预算 | 理由 |
| --- | --- | --- | --- |
| A（现状） | 初级（宽 10、深 2） | 400 ms | 基线 |
| B | 中级（宽 10、深 4，算杀 5 手） | 1,000 ms | 对局里中级的预算；深一倍、开算杀 |
| C | 高级（宽 12、深 6，算杀 9 手） | 1,600 ms | 再上一档，看收益是否递减 |

专家档（2.6 s / 局面）不进候选：一局 60 手要两分半以上，体感上不可接受，不值得量。

## 怎么量

**① 口径与检出（确定性，不受负载影响）**：`bench/review-loss.measure.ts` 加两个环境变量 `REVIEW_DIFFICULTY` / `REVIEW_BUDGET_MS`
（缺省即现在的初级 + 给足的预算），三组各跑一次，沿用它现有的两个样本（随机着法 205 手、入门档自对弈 26 手），报：

- 有亏损 / 零亏损 / 未算 各多少手，未算的原因分布；
- 相对 A 组，**亏损榜前五**有几手变了（同一局里「最该看的几手」稳不稳）；
- 续搜次数。

预算给足（60 s）时搜索恒搜满档位深度，结果只取决于档位；这一步量的是「档位的上限」。

**② 真实预算下的耗时与截断（受负载影响）**：同一脚本以真实预算（400 / 1,000 / 1,600 ms）再跑，多报：

- 每局面搜索耗时的中位 / P90 / 最大；
- **被时间截断**的局面占比（`reason === 'timeout'` 或实际深度 < 档位深度）——截断多了，高档位就名不副实；
- 与 ① 的结论差几手（预算不够时结论退化成什么样）。

**③ 体感（真实浏览器）**：生产构建 + Playwright，分别用三组参数（临时改 `ANALYSIS_BUDGET_MS` 与档位的本地构建，不提交）
打开同一局 60 手左右的棋谱、点「开始分析」，量到「分析完成」的墙钟时间，以及分析期间落子页的第一手应手延迟（确认双 Worker 下确实不挡落子）。

②③ 只在 1 分钟负载 < 5 时跑，并把负载记进结果。

## 产出

`TEST_REPORT` 新节 + 一张三组对照表（未算比例、榜单变动、一局总耗时、截断比例），附我的建议；交所有者在 A / B / C（或别的组合）中选。
选定后另起实施：改的只是一两个常量与界面上标注的档位文案，以及 `AI_ENGINE.md`「复盘分差的口径」一节的基线数字。

## 不做

- 不做「用户自选档位」的界面：先看一个固定档位能不能整体变好。
- 不改分差口径（同视界、续搜规则）本身。

## 自审

1. 候选组覆盖「不变 / 升一档 / 升两档」，专家档的排除有数字理由（预算 × 手数）。
2. ① 与 ② 分开：档位的上限与预算的截断是两件事，混在一起说不清是哪个造成的。
3. 测量脚本只加环境变量、缺省行为不变，`bench:review-loss` 现有输出不受影响；③ 的临时构建不提交。
4. 负载要求与阶段 E 第 6 项一致（< 5），两件事可以在同一个空闲时段做完。
