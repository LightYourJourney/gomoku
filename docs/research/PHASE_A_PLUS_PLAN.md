## 口径（先把要算什么说清楚）

一手棋有两条「走法」要比：实际着法、引擎首选。每条走法最多有两级评估：

| 级 | 局面 | 谁走 | 记法 |
| --- | --- | --- | --- |
| 一级 | 走完这一手之后 | 对手 | `after`（已有：实际着法一边是局面 *i*+1，引擎首选一边是对照请求） |
| 二级 | 再走完对手那一手应着之后 | 自己 | `follow`（**新增**：续搜请求） |

把每条走法折成「**走这一手的一方**视角」的一个值，并标明它是不是已证明的：

| 来源 | 值 | 已证明 |
| --- | --- | --- |
| 一级：这一手当场成五（`'ended'`） | `+WIN_SCORE` | 是 |
| 一级：对手 `win`（对手成五 / 算杀） | `−score` | 是 |
| 一级：对手 `search` | `−score` | 否（视界一） |
| 二级：自己 `win` | `+score` | 是 |
| 二级：自己 `search` | `+score` | 否（视界二） |
| 其余（`block` / `timeout` / `opening` / `no_move` / 缺失） | 无 | — |

**分差 = max(0, 引擎首选的值 − 实际着法的值)**，按下面的顺序取第一条成立的：

1. 两边都有一级值 → 用一级值（与阶段 A 已上线的结论逐字相同）。
2. 两边都有已证明的值（**任一级**）→ 用它们。
3. 一边有已证明的值（任一级），另一边有搜索值 → 用那个已证明值，和另一边的搜索值（有一级用一级，否则用二级）。
4. 两边都有二级搜索值 → 用它们。
5. 否则不算（`null`）。

要点：**已证明的值跨级可比**（成五就是成五，不随搜索视界变）；**两个搜索值只在同一级内可比**（阶段 A 修掉的奇偶层偏差就是跨级相减造成的）。所以一边需要二级时，另一边若是常规搜索也要跟着续搜一层——事先不知道续完会不会变成已证明。

## 设计决定

| # | 决定 | 理由 |
| --- | --- | --- |
| P1 | **只续搜一层。** 二级结论仍是 `block`（对手那一手应着又逼出一个必防）就不算。 | 每多一层都要两边同步多一层，请求数翻倍；原型实测一层已把未算从 18% / 31% 降到 5% / 12%（见下）。 |
| P2 | 一边要二级时，另一边的常规搜索也续搜一层（跟着对手的最佳应着走）。 | 同视界才可比。 |
| P3 | 续搜是**专用请求**，不复用相邻手的请求。 | 实际着法一边的二级局面有时恰好等于下一手的对照局面，可以共享；但共享要处理「下一手着法相同时没有对照」等三四种分支。初级档一次搜索几毫秒，不值得。 |
| P4 | 一级可比时**仍用一级**，不为了统一而全部重算。 | 不动阶段 A 已上线、已复核的结论；请求数也最少。 |
| P5 | 应着落不下去、或应着之后棋局结束：**两边都不续**、这一手不算（真实引擎不可达）。先算出两边的续搜局面，只要有一边算不出就一个都不发。 | 与阶段 A 的 D7 同一原则：没法比就如实说没法比，不另开错误路径；也不发一个注定没用的请求。 |
| P6 | 一级结论是 `timeout` 的一边**不续**（「能续搜」只认 `block` 与 `search`）。 | 不是续不了——超时的响应也带着应着；是不值得跟：那一手可能来自没搜满的一层，甚至一步贪心。 |

**已知代价（原型实测，2026-11-17，初级档、预算给足、确定性）：**

| 样本 | 着法不同的手 | 阶段 A（未算） | 续搜后：有亏损 / 零亏损 / 未算 | 多发的请求 |
| --- | --- | --- | --- | --- |
| 随机着法 | 205 | 37 | 172（≥ 5,000 的 126）/ 22 / **11** | 70 |
| 入门档自对弈 | 26 | 8 | 9（≥ 5,000 的 5）/ 14 / **3** | 16 |

- 随机样本里 4 手「有现成的五连没走」全部算出：分差 988,000–1,013,400（「分差极大」）。它们都是**冲四**（只有一个成五点）：没走，对手就堵上了。
- **活四没走成五按引擎的判断不亏**：对手只能堵一头，下一手照样成五，续搜后自己一边是 `win`，分差 0，显示「与引擎首选相当」。这是如实的（晚一手赢仍是赢），不是缺口；文档要这么写，复核也按这个预期验。
- 仍未算的 14 手全部是「二级结论还是 `block`」（P1）。**终审指出其中 2 手（随机样本）在口径规则 3 下其实可比**（一边二级是 `win`，另一边一级是搜索值）；规则已改，预计随机样本的未算从 11 降到 9，Task 3 以实跑为准。
- **一级与二级的分差会在同一张榜单里混排。** 二级多看了两层，对坏手的惩罚看得更清：在两级都算得出的 84 手上，二级分差比一级分差高的 46 手、低的 23 手、相同的 15 手，中位数高 1,000（P90 高 13,400）。这不是奇偶层那种方向固定的偏差（两条走法始终同级），但量级不完全一致——要写进文档。

Task 3 把这组数字做成 `yarn bench:review-loss` 的输出；对不上就停下来查。

### Task 2: 分析管线发续搜请求

**Files:** Modify `src/store/analysisStore.ts`；Test `src/store/analysisStore.test.ts`

**行为规格：**

1. 记下应着：`reply` 与对照的响应除 `score` / `reason` 外多记 `move`；对照任务的局面（`state`）留在挂起结论里备用。
2. 任务多一种：`{ kind: 'follow'; index; side: 'played' | 'engine'; state }`。请求的 `board` / `player` 取 `state`；`moveIndex: index`；其余同对照请求。
3. 一手需要比较（`position.compare`）且一级的两边都就位之后，**判一次**要不要续搜。「判过没有」用一个**显式的标记**记（挂起结论上的 `follow` 对象：不存在 = 还没判；存在 = 判过了），**不能**拿续搜字段是不是 `undefined` 来推——那和「已经发出、还没回来」分不开，`tryEmit` 每被调用一次就会再排一对续搜（终审发现）。判定只发生在 `tryEmit` 里、且只在标记不存在时：
   - `linesToFollow` 说两边都不续 → `follow = { played: null, engine: null }`；
   - 否则先算出每一边需要的续搜局面（实际着法一边：`replay(前 i+1 手)` + `reply.move`；引擎首选一边：对照局面 + 对照响应的 `move`）。**只要有一边算不出**（`move` 为空、落不下去、走完不再是 `playing`），两边都记 `null`、一个请求都不发（P5）；
   - 都算得出：需要续的那一边记 `undefined`（等响应），不需要的记 `null`；把续搜任务插到队首，**先插引擎首选一边、后插实际着法一边**，于是实际着法一边先发。
4. 出结论的条件在阶段 A 的基础上加一条：需要比较的手，`follow` 已存在，且其中没有 `undefined`。
5. 响应分发由两支改成**三支**（按 `job.kind`：`position` / `alternative` / `follow`）。阶段 A 的分发是 `position ? … : onAlternativeResponse(…)`，漏改的话续搜响应会静默写进对照字段，结论错而管线不报错（终审发现）。续搜响应：记下 `{ score, reason }` 到 `follow[side]`，重试出结论。其余（三重闸门、每条响应后判收尾、失败以错误收尾、缓存）不变。
