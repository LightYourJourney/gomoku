# 阶段 D 实施计划：棋谱库可以长期使用

> 出处：评估报告 §4.6、§5.6 第 1 条、§10「阶段 D」；裁定见 §14 第 2 条（`createdAt` 作可选字段、**不递增** `schemaVersion`；
> `SCHEMA_MIGRATION.md` §4 第 3 条改写为「改变已有字段含义才走版本 + 迁移，纯新增可选字段不在其列」）。

## 目标

1. 每局棋谱带入库时间；旧记录、旧备份显示「时间未知」，不编造。
2. 列表能删除（二次确认），长列表分批显示，首屏 DOM 有上限。
3. 「同一局只留一条」的替换收成存储上的一个事务，现有的补偿逻辑（删旧失败再撤新）整段消失。
4. 新旧版本交叉读写安全：旧版本读得了新数据、新版本读得了旧数据，回滚不丢棋谱。

## 设计决定

| # | 决定 | 理由 |
| --- | --- | --- |
| D1 | `GameRecord.createdAt: number \| null`（毫秒时间戳）。`schemaVersion` 仍是 1。`parseRecord`：有限且非负的数取用，缺失或不合法记为 null——**不因为时间坏了丢整条棋谱** | 裁定 2。旧代码的 `parseRecord` 只取认识的字段、只核对 `schemaVersion === 1`，新字段对它透明；新代码把缺失当「时间未知」。时间是附属信息，坏了不该连累手顺 |
| D2 | `GameRecordInput` 加可选 `createdAt`；**时钟注入**：入库路径（`useGameStore` 的 `onGameEnd`）传 `Date.now` 的引用，存储层不读时钟（`AGENTS.md`「时钟一律可注入」）。内存兜底补写进库、导入、恢复备份都保留原值 | 入库时间是「这局下完的时间」，不是「这条进库的时间」 |
| D3 | 内容身份 `recordContentKey` **不含**时间（已经如此，补用例钉住）；导入去重照旧 | 同一局不因时间不同变成两局 |
| D4 | 外部格式：棋谱文件与备份里的棋谱加可选 `createdAt`，写 ISO 8601 字符串（文件给人看，库里存毫秒数），不升 `formatVersion`；读入时解析不出有限时间就当没有。`FILE_FORMAT.md` 补一行。导入与库里已有的同一局重复时照旧跳过，不拿导入的时间覆盖库里的 | `SCHEMA_MIGRATION.md` §4 第 7 条：外部格式新增可选字段不升版本 |
| D5 | 存储接口新增 `putReplacing(input, { replacesSeq, allowContentMatch })`：IndexedDB 实现是**一个读写事务**——（必要时）读全表找同一局 → 写新 → 删旧，`oncomplete` 才算成功。库打不开、或事务失败（整笔回滚，新旧都没动）都退内存兜底（`persisted: false`），与现在 `put` 失败的路径一致——界面照旧说「没能保存这局」。`saveGameReplacing` 改为调它，补偿逻辑删除。`replacesSeq` 指向不存在的记录时退回内容身份匹配（现有语义）放进事务里 | 评估报告 §4.6 ④。四个独立事务之间的窗口与补偿分支一起消失 |
| D6 | 列表：每项显示时间（`YYYY-MM-DD HH:mm`，与局面库同一个格式函数，抽到 `lib/` 共用）；默认显示最近 50 条，「再显示 50 条」按钮追加；**首屏 DOM 随 N 不再线性增长** | 评估报告：5,000 条时 30,073 个元素、首屏 433 ms。不上虚拟列表，分批够用 |
| D7 | 删除：每项一个「删除」按钮，点一次变「确认删除」（危险色）+「取消」，与局面库同一套交互；删除成功后从列表移除并说一句「已删除」；失败如实报错、列表不动。删除的是本机记录，不可撤销（文案写明） | 局面库已有的模式 |
| D8 | 注释与文档：`gameRecords.ts` / `storage.ts` 顶部「字段形状一变就递增，旧数据被安全丢弃」改为与 `SCHEMA_MIGRATION.md` 一致的说法；`gameRecords.ts`、`GameLibrary.tsx` 里「不存时间戳」的理由删掉；`SCHEMA_MIGRATION.md` §4 第 3 条按裁定 2 改写；`DEPLOYMENT_RECORD.md` 写明回滚行为 | 评估报告 §5.6、裁定 2 |

2. 交叉版本读写：改造前的构建（`3c632f0`）与生产回滚目标（`6301201`）读新数据、新构建读旧数据都正常（实测记录）。

## 自审

**第一轮（与裁定、报告对照）**
1. 裁定 2：可选字段、不递增版本、内容身份不含时间、`SCHEMA_MIGRATION.md` §4 第 3 条改写——D1、D3、D8 覆盖。
2. 评估报告 §4.6 的四项改进（时间、分批、删除、单事务替换）与「如何证明有效」的四条（旧夹具、交叉读写、删后刷新、5,000 条 DOM 上限）一一对应到 Task 与验收。
3. §5.6 第 1 条（注释与迁移规则矛盾）随 D8 改；第 2 条（`isPlayer` 等小重复）留给阶段 E 第 5 项，本阶段不扩大。

**第二轮（时序与边界）**
4. 事务失败的语义：旧路径里 `put` 失败退内存（`persisted: false`），`delete` 失败抛「本次保存已撤回」。单事务后只剩一种失败——整笔回滚、库里什么都没变——统一退内存兜底，界面结果与旧的 `put` 失败相同。内存里的这条会在下次 `list()` 时按内容身份补写进库：与旧路径完全相同的行为，不新增分支。
5. 旧 `saveGameReplacing` 的内容匹配走的是 `list()`，会顺带把内存兜底补写进库；事务版只读全表、不补写。补写仍由下一次 `list()` 做，结果相同。
6. 列表按 `seq` 降序（入库先后），不按 `createdAt`：导入的旧棋谱 `seq` 新、时间可能早，按时间排会让「刚导入的」散落在中间；显示时间、不改排序。
7. 删除时回放页 / `gameStore` 手里可能还握着这条的 `seq`（`recordedSeq`）：之后再替换时按号找不到，退回内容身份匹配——现有逻辑已覆盖。
8. 分批显示与删除并存：删掉一条后已显示的条数不回退。

**第三轮（测试与门禁）**
9. `GameRecordsStorage` 加方法后，测试里的假存储大多是 `{ ...memoryGameRecords(), list: … }`，自动继承；typecheck 会抓漏的。
10. 删除的二次确认与局面库同形：若 jscpd 报克隆，抽共用组件，不加豁免。
11. 依赖方向：时间格式函数放 `lib/`（`features` 两处用），`lib` 不依赖任何层，门禁自动查。
12. 条数棘轮只增；交叉版本的验证是一次性的实测脚本（`/tmp`），不进 CI——它要两份构建与持久化浏览器配置，进 CI 的成本与收益不相称，结果记入测试报告。

## 独立终审

终审者只读源码与计划，八条意见逐条核实，全部成立，处理如下。

| # | 意见 | 处理 |
| --- | --- | --- |
| 1 | `createdAt` 只查有限非负、没上限：大于 8.64e15 的值 `toISOString` 会抛，导出时整条被当成损坏，与 D1「时间坏了不丢整条」矛盾 | 库层与文件层都要求它是一个有效的 `Date`（≤ 8.64e15）；文件里读 ISO 用严格正则，不用宽松的 `Date.parse` |
| 2 | 分享链接走 `toGameFile`，加了时间就会进链接，违反 `SECURITY_MODEL.md`「分享不带本机信息」 | 只在文件导出与备份里写时间，分享路径剥掉；用例钉住 |
| 3 | `delete` 返回 void，库打不开时静默删内存，界面会说「已删除」而刷新后又回来 | 照局面库改为返回 `{ persisted }`，界面如实说「库不可用，记录可能仍在」 |
| 4 | 分批后 `bench/library.probe.mjs` 核对行数 = N+1 会报错；新增 testid 不能以 `record-` 开头（多处 `toHaveCount` 按这个前缀数） | 探针按 `min(N, 50)` 核对；新 testid 用别的前缀 |
| 5 | 交叉版本的基线：应用改造前的代码（`3c632f0`，与 `5616b4d` 同码）**并加上生产回滚目标 `6301201`**；验收写明 `DB_VERSION` 保持 4；旧构建导入新文件时每局一条未知字段告警，所以时间为 null 时省略这个键 | 照改：两个旧构建都测；`DB_VERSION` 不动并写进验收；文件里无时间就不写键 |
| 6 | 回滚的权威文档是 `ROLLBACK_PLAN.md` 那张表 | 一起改，写明回滚期间新入库的棋谱与导出的备份都不带时间 |
| 7 | 测试：补偿用例删掉会让条数少 1；`createdAt` 必填要改约 30 处字面量；旧夹具的断言在 `e2e/fixtures.spec.ts`；时间显示的断言要用正则（时区） | 补偿用例由「事务中途失败整笔回滚」取代（写进测试报告）；字面量逐处补 `createdAt: null`；`fixtures.spec.ts` 补「时间未知」；时间断言用正则 |
| 8 | `putReplacing` 在读写事务里全表严格回放；验收只比首屏 | 把探针的「终局入库耗时」也列为不退化，前后同机紧挨着各跑一次 |
