# Gomoku Lab 全仓深度审查与重构评估

> **性质**：只读研究。研究阶段没有修改任何生产代码、测试、配置、基线或门禁。
> **对象**：HEAD `d197444`（应用 `0.6.0` / 引擎 `search-1`），2026-11-17。
> **实验可复跑**：研究时的临时脚本已按裁定整理成 `bench/` 下的五条 `yarn bench:*` 命令
> （§13 列出命令、首次数字与复跑数字）。这一步新增了测量脚本与 `package.json` 的脚本项，仍未动任何生产代码。
> **本报告提出的未决事项已于 2026-11-17 裁定，见 §14**；正文保留研究当时的原貌，与 §14 不一致处以 §14 为准。

## 0. 结论先行

**整体判断：架构是健康的，不需要大规模重构。** `core` 的纯净、`replay()` 作为唯一构造路径、
注入式的 store 工厂、全仓零 `vi.mock`、把导入与分享当不可信输入、以及「如实报告失败」这条贯穿
存储层的纪律，都是真功夫，应当原样保留。此前几轮审计（`docs/audit/`）对代码整洁性的清理已经很彻底，
本报告**不重复**那些结论。

但这次独立研究找到了此前审计没有覆盖到的几类问题——它们的共同点是：**不是「代码写得乱」，
而是「某个语义或某个缺失的能力，被周围写得很认真的代码稳稳地固定住了」**。按我的优先级：

| # | 问题 | 性质 | 证据 |
| --- | --- | --- | --- |
| 1 | **复盘「分差」的计算口径有系统性偏差**，会把大多数真实亏损钳成 0 | 已证实（实验） | 随机着法 124 手里 108 手被报成零亏损；同视界口径下 110 手有亏损（§4.1） |
| 2 | **「精确 / 启发式」的语义是倒挂的**：入门档 1 层搜索标「精确」，专家档搜完 6–7 层标「启发式兜底、不保证最优」 | 已证实（读码 + 项目自己的发布记录） | §4.2 |
| 3 | **引擎没有取消**：被作废的搜索照样在唯一的 Worker 上跑完，新请求排队 | 已证实（实验） | 思考中悔棋再落子，新请求排队 1.27–1.42 s；连续 6 次后排队 10.4 s，距 15 s 超时只差 2.8 s（§4.3） |
| 4 | **入口包离预算只剩 3.4%**，下一个功能就会撞上「不许调松」的门禁 | 已证实（实测） | 130,417 B / 135,000 B（§4.4） |
| 5 | **应用内导航不进浏览器历史**：按后退键直接离开应用；页面位置寄存在学习进度里 | 已证实（实验） | §4.5 |
| 6 | **棋谱库只增不减、没有时间、不能删、全量渲染** | 已证实（读码）；性能影响实测为轻微 | §4.6 |

其余是结构性风险与长期机会（§5–§8），多数**建议保留现状**或顺手处理。

我推荐的路线是**五个小阶段**，前两项（1、2）各自独立、改动很小、收益直接，应当最先做；
第 3 项是唯一称得上「架构改造」的，它同时解开四处重复的请求生命周期代码。详见 §10。

## 1. 项目理解与技术画像

**是什么**：纯前端、无后端的五子棋（自由规则）人机对战与学习应用。四个模块——对战、互动教学、
残局挑战、棋谱复盘——外加局面编辑器、数据备份/恢复、Fragment 分享链接。部署在 Cloudflare Pages，
手动发布，CSP 全 `'self'`。

**规模**（本轮实数）：

| 项 | 数值 |
| --- | --- |
| 生产代码 `src/**`（不含测试） | 19,114 行 |
| 单元/组件测试 | 20,643 行，90 个文件，**1,475 条**，`yarn test` 31.4 s |
| e2e | 5,321 行，193 条（另有 prod 7、Firefox/WebKit 全量 307） |
| `bench/`（基准、剖析、棋力评测、UI 探针） | 9,057 行 |
| `docs/**/*.md` | 104 个文件，24,761 行 |
| 运行时依赖 | 3 个（react / react-dom / zustand） |
| 历史 | 245 次提交，2026-10-10 → 2026-11-15（5 周） |

按层的生产代码量：`features` 5,467 · `persist` 3,149 · `ai` 2,623 · `components` 2,595 ·
`store` 2,212 · `learn` 1,203 · `core` 563 · `lib` 401 · `sharing` 256 · `analysis` 167。

**三个值得先说的画像特征**：

1. **文档与测量基础设施的体量超过了产品代码**（文档 24.8k 行 + bench 9k 行 + 测试 26k 行，对 19k 行产品代码）。
   这不是坏事——它是这个项目「每个数字都能重跑」的来源——但它决定了**改动的真实成本主要在同步文档与门禁，
   不在写代码**。评估任何重构都要把这部分算进去。
2. **项目只有 5 周历史，却已经走完 30 多个「阶段」和至少 4 轮独立审计。** 清理类的低垂果实已经摘完；
   剩下的问题大多是语义层与能力层的。
3. **工程文化是「把教训写进注释」。** 好处是每个奇怪的写法都能查到来由；代价是注释里夹着历史叙事，
   并且会漂移（§5.7）。

**研究范围的诚实说明**：`core/*`、`store/*`、`analysis/*`、`ai/` 除 `patterns.ts` 外的全部模块、
`persist/` 的 `schema` / `idb` / `storage` / `recordIdentity` / `gameRecords`、`App.tsx` / `main.tsx`
是**逐行读完**的；`patterns.ts`、`positions.ts`、`progress.ts`、`transfer/validate.ts`、`Board.tsx`
与各 feature 容器是**结构级阅读加定点精读**；e2e 与 bench 只看了组织方式与门禁脚本。
凡是只在结构级读过的地方，本报告不下细节结论。

## 2. 当前架构评价

### 2.1 实际的依赖方向（自己算的，不采信文档）

```
core        → （无）
ai          → core
analysis    → ai, core
learn       → ai, core, lib
persist     → core, ai(类型与 isDifficulty), lib
sharing     → persist/transfer, core
store       → core, persist, ai, analysis, lib
lib         → core, react；另有 shape-labels 取 ai / learn 的类型
components  → lib, core, ai；另有 7 处取 store / features 的类型或常量
features    → components, store, persist, core, learn, ai, sharing, lib, analysis
```

- `yarn check:cycles`（madge）**零环**，实跑确认。
- `core` / `ai` / `analysis` / `learn` 的生产代码里没有任何浏览器 API——唯一命中的是
  `ai/browserEngine.ts` 的 `new Worker`，正是 `AGENTS.md` 明文豁免的那一处。
- **主干方向是对的，且与业务结构吻合**：规则 → 引擎 → 两条互不依赖的纯逻辑支线（分析 / 教学）→ 状态编排 → 展示。

### 2.2 评价

**做对了的部分远多于做错的。** 架构真正反映了业务结构，注入点找得准（引擎、存储、时钟），
`persist` 的三个 IndexedDB 存储层共用 `idb.ts` 的连接样板也收得干净。

**不足集中在三处**，都不是「分层错了」：

1. **`store` 与 Worker 之间缺一层「请求调度」**。四个调用方各自实现请求生命周期，谁也管不了 Worker
   的队列（§4.3、§5.1）。这是全仓唯一一处我认为「缺了一个本该存在的模块」。
2. **应用级状态没有自己的家**：当前在哪一页住在 `learnStore`、持久化在学习进度里；
   子页面（打开的棋谱、编辑器、课程）是各组件的 `useState`（§4.5）。
3. **分层规则只靠人守**。循环依赖、死代码、重复代码、包体积都有门禁，唯独被强调最多的
   「依赖方向」没有（§5.2）。

## 3. 值得保留的优秀设计

这一节不是客套。下面每一条我都认为**未来两年不该动**，并且新代码应该照着它写。

| 设计 | 位置 | 为什么好 |
| --- | --- | --- |
| `replay()` 是 `GameState` 的唯一构造路径 | `core/game.ts` | 棋盘与手顺不同步这类 bug 在结构上不存在；每手多付的那次重放可以忽略 |
| `Position` 与 `GameState` 分成两个类型 | `core/position.ts` | 编辑器不必编造假手顺；「静态合法」与「可重放」分级清楚 |
| store 全部是注入依赖的工厂 | `createGameStore(engine, options)` 等 | 全仓 **0 处 `vi.mock`**，时序类缺陷可以用假引擎确定性复现 |
| 时钟一律注入 | `searchBoard(…, now)`、`findForcedWin`、`judgeMove` | 超时行为可测、不 flaky |
| 「如实报告」的存储语义 | `persisted` / `degraded` / `skipped` / `storage: 'failed'` | 把「没存上」与「没数据」分开，界面不必撒谎。这是本项目最有价值的一条产品纪律 |
| 以事务提交为准判定成功 | `idb.ts` 的 `withObjectStore` | 堵住了「`request.onsuccess` 之后提交失败」这类欺骗性成功 |
| 导入与分享当不可信输入 | `persist/transfer/validate.ts`、`sharing/link.ts` | 大小 / 深度 / 单次重放的严格校验；外部格式版本与内部版本解耦 |
| 题目只声明目标、答案由引擎算 | `learn/verify.ts` + `content.test.ts` | 出题人没有机会把答案写错；多解自然成立 |
| 增量评估与全量评估逐位等价，并有三重钉子 | `incrementalEvaluate.ts` + 等价测试 + A/B | 性能优化没有以行为漂移为代价 |
| 用实验否决优化 | 候选预筛（慢 48.8%、棋力告负）被如实否决 | 比「做成了」更说明评测体系是真的在工作 |
| 入库链的「局号」闸门 | `gameStore` 的 `makeNotifier` | 「终局 → 立刻重开」这类竞态被认真对待过 |
| 门禁失败关闭 | `.githooks/pre-push` | 跑不起来就拒绝推送，而不是静默放行 |
| 整张棋盘一张 SVG、容器查询定尺寸 | `Board.tsx` | 坐标系统一，无 JS 测量；实测落子一手 0.10 ms（项目记录） |

## 4. 已证实的问题

每条按同一结构写：**现状 → 为什么值得关注 → 涉及模块 → 现设计的优缺点 → 不处理的后果 →
改进方向 → 更简单的替代 → 复杂度/风险/收益 → 如何证明有效**。

### 4.1 复盘「分差」的口径有系统性偏差 —— 优先级 1

**现状。** `analysisStore` 为每一手发两次搜索：局面 *i*（落子前，行棋方视角）与局面 *i+1*
（落子后，对手视角）。`emit()` 把 `engineScore = score(i)`、`playedScore = −score(i+1)` 交给
`analysis/analyze.ts` 的 `buildVerdict`，后者算 `loss = max(0, engineScore − playedScore)`；
着法与引擎首选相同时强制为 0。

**问题。** 这两个分数**不在同一个搜索视界上**。局面 *i* 搜 *d* 层，最后一手是对手下的；
局面 *i+1* 搜 *d* 层，等于从 *i* 看了 *d+1* 层，最后一手是自己下的。而 `evaluateBoard`
是刻意不含「轮到谁」的纯局面评估（`AI_ENGINE.md` 写明），于是「谁下最后一手谁占便宜」的
奇偶层效应原封不动地进了分差——并且方向固定：**`playedScore` 被系统性高估，`loss` 被系统性低估，
然后被 `max(0, …)` 钳成 0。**

**实验一（自洽性）。** 让引擎自己走（走的就是它的首选，按定义分差应为 0），用上面的口径算
`score(i) − (−score(i+1))`，只统计两次都是常规搜索（`reason === 'search'`）的手：

| 样本 | 为负 | 为零 | 为正 | \|偏差\| 中位数 | P90 |
| --- | --- | --- | --- | --- | --- |
| 135 手（6 个开局，初级档，预算给足恒搜满 2 层） | **134** | 1 | 0 | **14,200** | 17,200 |

偏差中位数比一个活三的评估分（`SHAPE_VALUES.openThree = 12,000`）还大，按界面「分差约 N 子」
的换算是 1.4 子。项目当初观察到「同一手算出亏 98 万」时把原因归为捷径分的量纲不同，
并用「着法相同则强制为 0」绕开了——那个特判同时也把这个**符号恒定的偏差**盖住了。

**实验二（后果）。** 同样的局面上，让「玩家」随机走一个邻域内的其它空点，比较两种口径：

| | 现行口径 | 同视界口径（都取落子后的局面来比） |
| --- | --- | --- |
| 报告为零亏损 | **108 / 124** | 14 / 124 |
| 报告有亏损 | 16 | 110（其中 ≥ 5,000 的 70 手） |

**现行口径把 94 手真实亏损报成了「与引擎首选相当」，其中 57 手的亏损在半子以上。**
随机着法里有 87% 被判成不亏——这个功能在它最该起作用的地方基本是哑的。

**涉及模块。** `store/analysisStore.ts`（`emit`、队列构造）、`analysis/analyze.ts`（`buildVerdict`、`cacheKey`）。
不涉及引擎。

**现设计的优点。** 每手只要 1 个请求（相邻手共享局面），便宜；没有固定档位标签，克制。
**缺点**就是上面这条：比较的两个量不可比。

**不处理的后果。** 「引擎帮你找亏损的手」是复盘页的卖点。它现在大面积漏报，而且漏报是静默的
（显示成「相当」而不是「不知道」），用户无从察觉。这与项目「不把有限预算的分析称为绝对正确」
的自我要求方向相反——不是说得太满，而是**说错了**。

**改进方向。** 着法不同时，再发一次请求：局面 *i* 走完**引擎首选**之后的局面。
`loss = score_after_played − score_after_engine`（都是对手视角、同一视界、同一量纲）。
代价是每个「与引擎不同」的手多 1 个请求（400 ms 上限）。量纲随 `reason` 变的问题仍要按
`AI_ENGINE.md` 的表做一次显式处理（两边之一是捷径分时不相减，如实标「无法比较」）。
缓存键的 `v2` 要递增——结论的含义变了。

**更简单的替代。** 不加请求，只把偏差当常数修正掉——**不建议**：偏差随局面变（P90 比中位数高 21%），
减一个常数只是把错误从「系统性」变成「随机性」。
另一条路是给引擎加「根节点只搜指定着法」的选项，让两个分数出自同一次搜索口径；更干净，
但要动 `ai/search.ts`，按约定得走基准与 A/B。**先做 store 层的版本。**

**复杂度 / 风险 / 收益。** 小（一个 store + 一个纯函数 + 测试）；风险低（只读功能，不碰棋局）；
收益高（修复一个已发布功能的核心指标）。分析总时长会上升，上限是手数 × 400 ms。

**如何证明有效。** 把实验一做成自测：**引擎走自己的首选时，新口径的分差中位数应为 0，
且不依赖「着法相同」特判**；实验二的检出率作为回归基线写进文档。按项目惯例，
用例写完后把修复撤掉确认它会红。

**不确定性。** 实验用的是引擎自对弈与随机着法、初级档、6 个开局、共 259 个样本；
「同视界口径」本身仍是 2 层初级引擎的看法，不是真理。结论限定为：**现行口径相对同一引擎的
自洽口径有方向固定、量级显著的偏差**——这一点样本足够说明。

### 4.2 「精确 / 启发式」的语义倒挂 —— 优先级 2

**现状。** `chooseMove` 里 `confidence = reason === 'timeout' ? 'heuristic' : 'exact'`。
而 `runSearch` 在迭代加深的某一层超时后，返回的是**上一层完整搜完的结果**，同时把
`reason` 记成 `'timeout'`。界面于是这样说话：

| 档位 | 实际发生的事 | 界面文案 |
| --- | --- | --- |
| 入门 | 搜满 1 层 | 「AI 完整搜索后选了这一手」，结论「精确」 |
| 专家 | 搜满 6–7 层，第 7–8 层没搜完 | 「时间到了还没搜完，这一手是**启发式兜底**」＋警示条「不保证最优」 |

**这不是推测。** 项目自己的发布记录里写着：生产环境五档深度 1 / 2 / 4 / 5 / 6，
「高级与专家均超时回退」（`DEPLOYMENT_RECORD.md`）；10E 审计记「专家连续三手：深度 6/7、
reason 超时回退、confidence 启发式、界面警示可见」并判为正常；Phase 10D 的标定数据是
**专家档 43% 的着法超时**（其余档 0%；更早的优化前基线里高级是 24/87 手）。
本轮实测里，一次 800 ms 的专家档提示搜到第 7 层，同样标成启发式。

**为什么值得关注。** 两个方向都不对：

- **最强的分析被说成最不可靠的。** 「启发式兜底」这四个字只在 `depth === 0`（一步贪心）时成立；
  深度 ≥ 1 时返回的是一次完整的浅一层搜索。
- **「精确」是过度声明。** 一次宽度 6、深度 1、不算杀的搜索不是精确结论。全引擎里称得上「证明过」
  的只有三类：直接成五、唯一必防、VCF 算杀链。

`AGENTS.md` 那条「不要把未经搜索验证的随机着法包装成高难度 AI」的精神是**如实**。现在的二值标签
在高档位过度保守、在低档位过度自信，两头都不如实。

**涉及模块。** `ai/types.ts`（`Confidence`）、`ai/search.ts`（`chooseMove`）、
`components/panels/AiPanel.tsx`（`REASON_TEXT`、警示条）、`HintPanel.tsx`、
`analysis/analyze.ts`（`pathLabel` / `pathSummary`）、`PositionEditor.tsx`、以及 `AI_ENGINE.md`。

**现设计的优点。** 简单，且永远不会把没搜完的东西说成搜完了。
**缺点。** 一个布尔量承担了三件事（有没有证明 / 有没有搜到上限 / 是不是贪心兜底）。

**不处理的后果。** 用户在专家档有近一半的手看到黄色警示，在入门档看到「精确」。
对一个把「如实告知」当核心卖点的产品，这是在消耗自己的信用。

**改进方向。** 把可靠度从二值改成按事实分的四类：**已证明**（成五 / 必防 / 算杀）、
**搜到上限**（N 层）、**限时内搜到第 N 层**（原 `timeout` 且 `depth ≥ 1`）、**贪心兜底**（`depth === 0`）。
只有最后一类配警示。`SearchReason` 不用动，新分类由 `reason` 与 `depth` 推导，放在 `searchPathOf` 旁边。

**更简单的替代（建议先做这个）。** 类型不动，只改两处：`heuristic` 仅在 `depth === 0` 时给；
把「精确」改叫「搜索完成」，超时那句改成「限时内搜到第 N 层，用的是这一层的结果」。
三五行逻辑加文案与测试。

**复杂度 / 风险 / 收益。** 很小；风险在于有若干断言文案的测试与一条覆盖棘轮要同步；
收益是界面终于与引擎的真实行为一致。这是**语义变更**，按约定要同步 `AI_ENGINE.md`。

**如何证明有效。** 单测钉住映射表（`reason × depth → 分类`）；浏览器里专家档连下三手，
确认不再出现「启发式兜底」而是「搜到第 N 层」。

### 4.3 引擎没有取消，过期搜索占着唯一的 Worker —— 优先级 3

**现状。** `ai/worker.ts` 的 `onmessage` 同步跑完 `chooseMove` 再回消息；`AiEngine` 只有
`search` 与 `dispose`，没有 `cancel`。悔棋、重开、认输、换页、编辑局面时，store 把
`pendingRequestId` 置空（或递增 `version` / `runId`）——**响应会被丢弃，但那次搜索仍然跑完**，
后面的请求在 Worker 的消息队列里等。代码注释自己也承认这一点（`ReviewScreen` 卸载处：
「`stop()` 只能丢弃结果——引擎没有取消接口」）。

**实测**（生产构建、真实 Chrome、专家档；给 Worker 的收发打时间戳，
`排队 = 往返时间 − 引擎自报耗时`，两轮独立运行）：

| 场景 | 新请求的排队时间 |
| --- | --- |
| 落子 → 300 ms 后悔棋 → 立刻换点落子 | **1,270 / 1,414 / 1,424 ms**（三次） |
| 求提示后立刻落子 | **717 / 719 ms** |
| 连续 6 次「落子 → 悔棋」后正常落子 | **10,213 / 10,431 ms**，往返 11.9 / 12.2 s |

最后一行离 `AI_RESPONSE_TIMEOUT_MS = 15,000` 只差 2.8 s。那个常量的注释写着「正常机器不可能触发」
——在有排队的情况下这句话不成立（**本轮没有实际触发超时**，只量到了余量；再多两三次悔棋，
或机器慢一些，就会出现一条误报的「AI 超过 15 秒没有响应」）。

**为什么值得关注。** 这不只是一个延迟问题，它是**一条被整个产品绕着走的约束**：

- 复盘分析被限制在初级档 + 400 ms，理由是「不会长时间占住 Worker」。也就是说，
  **用户刚输给专家档，回头帮他复盘的是 2 层深度、不算杀的初级引擎**——这个产品上限是架构给的。
- 编辑器分析用的是所选档位的全额预算（专家 2,600 ms），没有超时兜底，也不可取消；
  连续「改一格、点分析」会把过期搜索一个个堆进同一个队列，随后切回对战页落子，
  AI 的那一手要排在它们后面。（这条是读码推断，没有单独实测；机制与上表相同。）
- 四个调用方的作废闸门各写各的，两个有超时、两个没有（§5.1）。

**涉及模块。** `ai/engine.ts`、`ai/browserEngine.ts`、`ai/worker.ts`、
`store/gameStore.ts`（落子、提示）、`store/analysisStore.ts`、`store/editorStore.ts`、`store/useGameStore.ts`。

**现设计的优点。** 极其简单；`engine.ts` 是可单测的纯状态机；「过期响应不改变棋局」这条**安全性**是成立的，
本轮没有发现任何能让过期响应落子的路径。
**缺点。** 只保证了安全，没有管**资源**。

**不处理的后果。** 高档位下「思考中悔棋」的体验变差；误报超时的概率随功能增加而上升；
复盘分析的质量被锁死在最弱的一档附近。

**改进方向。** 给引擎一个真正的取消，并把四处生命周期收成一处。同步搜索无法协作式取消
（除非上 `SharedArrayBuffer`，那要改响应头，不值得），但**终止并重建 Worker 很便宜**：
实测「新建 Worker + 首个请求往返」中位 **4 ms**、最大 9 ms（12 次）；置换表本来就是每次搜索新建的，
重建不丢任何东西。两种做法：

- **A（推荐先评估）：两个 Worker。** 一个只跑落子（同一时刻至多一个请求，取消 = `terminate` + 重建），
  一个跑只读请求（提示 / 复盘分析 / 编辑器分析，串行）。不需要优先级队列；
  分析再也不会挡住落子，于是分析预算可以放开。
- **B：一个 Worker + 引擎侧队列。** 队列从 Worker 的消息队列挪到 `engine.ts` 手里
  （一次只发一个），取消在飞的 = 终止重建后发下一个，取消排队的 = 直接摘掉；可加优先级。

两者都要配一个 store 侧的小工具（暂称「请求槽」）：发起即取代上一个、统一超时、统一作废判定。
`gameStore` 现有的 `requestId` + `gameVersion` 两道闸门**原样保留**——它们是纯 action 里的安全判断，
有测试钉着，取消只是在它们之外再加一层资源回收。顺带把 Worker 改成首次请求时才创建，
`BattleScreen.test.tsx` 里那个全局 `FakeWorker` 垫片就不再需要。

**更简单的替代。** 只在 `gameStore` 的几条作废路径上 `terminate` 重建——**不行**：
Worker 是共用的，这会把无辜的在飞请求（一手复盘分析）一起杀掉并报成引擎错误。
要么分 Worker（A），要么引擎自己管队列（B）。

**复杂度 / 风险 / 收益。** 中等。风险点：Worker 重建时脚本若不在 HTTP 缓存里且断网会失败
（走现有的 `aiError` + 重试路径即可，但要有用例）；Firefox / WebKit 的模块 Worker 行为要走
`e2e:browsers`；`engine.test.ts` 与三个 store 的假引擎要跟着扩。收益：延迟问题消失、
误报超时的根因消失、四份重复逻辑合一、并且为「更深的复盘分析」解锁。

**如何证明有效。** 把本轮的时间戳探针做成 `bench/` 下的正式探针（它不改产品代码，
只在页面里包一层 `Worker`）：悔棋后排队时间应从 1.3 s 降到与重建代价同量级；
连续 6 次悔棋后不再累积。既有的过期响应用例必须一条不改地全绿。

### 4.4 入口包离预算只剩 3.4% —— 优先级 4（与 4.5 同做）

**现状。** 没有任何代码分割：四个页面、编辑器、导入校验器、分享、全部课程与题库都在一个入口块里。
`quality/bundle-budget.mjs` 的上限是 135,000 B（gzip）。

**实测。** 本轮 `yarn build` + `yarn check:bundle`：**130,417 B**，余量 4,583 B。
历史轨迹（`TEST_REPORT.md`）：81.68 kB → 128.15 kB → 130.4 kB；预算是 10 月 29 日在 128 kB 时立的，
之后两周只做修复类改动就涨了约 2.3 kB。

**为什么值得关注。** `AGENTS.md` 把调松门禁定为违规。也就是说**下一个像样的功能一定会撞线**，
而到那时可选的动作只有「拆包」或「违规」——拆包应当在不慌的时候做。

**可拆出多少**（估算，`yarn bench:split`：以页面组件为入口用 Vite 打包压缩、剔除 React 与 zustand 后相减；
**不是** Vite 实际拆分的结果，以实做为准）：

| 部分 | gzip 约 |
| --- | --- |
| 全部应用代码（不含 React / zustand） | 59.3 kB |
| 只有对战页 | 20.6 kB |
| 复盘 + 编辑器 + 数据管理 + 分享（独占部分） | ≈ 24.8 kB |
| 教学 + 残局（独占部分） | ≈ 14.3 kB |

按需加载复盘与教学两组，入口大约能从 130 kB 降到 91 kB 上下。

**涉及模块。** `App.tsx`（四个页面的挂载点）、`vite.config.ts`、`quality/bundle-budget.mjs`、
`e2e/prod.spec.ts`。

**现设计的优点。** 一个入口最简单，没有加载态，没有分块加载失败这类故障。本机 FCP 112 ms（项目记录），
**今天没有性能问题**——这一条的理由是预算，不是速度。

**改进方向。** `React.lazy` 拆「复盘组」与「教学组」；门禁同时改成「入口上限下调 + 总量上限」
（**收紧**而不是放宽，且门禁文件是 review 必看项，须由你明确批准）。分块加载失败（断网、发布后旧页面
请求已不存在的旧块）要落到错误边界并给出刷新提示——项目没有 Service Worker，这条路径是真实存在的。

**更简单的替代。** 只把 `persist/transfer/validate.ts` 与编辑器这类「点了才用」的东西做动态 `import()`，
不动页面级结构。改动更小，但省得也少，且导航结构（4.5）迟早要动 `App.tsx`，不如一起。

**复杂度 / 风险 / 收益。** 小到中；风险是引入加载态与一个新的失败模式；收益是把预算余量从 3% 拉回 30% 左右。

**如何证明有效。** `yarn check:bundle` 的实数；`e2e:prod` 加一条「冷启动直达复盘页」；
一条「分块加载失败时的界面」用例。

### 4.5 应用内导航不进浏览器历史 —— 优先级 4

**现状。** 「当前在哪一页」是 `learnStore.view`，随学习进度存进 IndexedDB（`progress.lastView`）。
子页面状态各管各的：复盘页的 `open` / `editorOpen` 是 `ReviewScreen` 的 `useState`，
课程与题目靠 `progress.lastVisited`。URL 只在分享预览时用（`#share=`）。全仓没有 `pushState` / `popstate`。

**实测。**

- 打开应用 → 点「教学」→ 按浏览器后退：`history.length` 为 2，后退后的地址是 **`about:blank`**——
  **直接离开了应用**。在手机上，从一节课里按返回键就是退出网站。
- 上次停在复盘页时刷新：**先挂载对战页**（7–9 ms），再切到复盘页（16–19 ms），三次一致。
  桌面上只是一帧之内的事；它说明的是「页面位置要等异步的 IndexedDB 读回来才知道」这个结构。

**为什么值得关注。** `TECH_DEBT.md` §1.3 把「无 router」列为明确不偿还，理由是单页工具不需要路由库。
**我同意不需要路由库，但不同意不需要历史。** 这两件事被绑在一起裁定了。应用现在的页面层级是
三层深（模块 → 列表 → 详情 → 编辑器 / 分支弹窗），后退键是移动端用户最本能的操作；
而分享功能已经引入了**第二套**导航机制（hash），两套互不知情。
另外，把页面位置放在学习进度里有实际的副作用：每次切页都要写一次 IndexedDB；
页面位置的可用性取决于一个与它无关的存储。

**涉及模块。** `App.tsx`、`store/learnStore.ts`（`view` / `setView`）、`features/shell/AppHeader.tsx`、
`ReviewScreen` / `LearnScreen` / `PuzzleScreen` 的子页面状态、`sharing/link.ts` 的 hash 识别。

**现设计的优点。** 零依赖；页面位置能跨会话恢复。
**缺点。** 后退键、前进键、子页面恢复都没有；状态的归属是历史原因而不是设计。

**改进方向。** 一个一百行量级的 `navigation` 模块（不引入路由库）：页面与子页面状态放进
`history.state`，切换时 `pushState`，监听 `popstate`。**URL 可以完全不变**——这样既不用设计 URL 方案，
也不碰 `#share=` 协议与部署配置，只换来后退 / 前进。`view` 从 `learnStore` 搬出去；
`progress.lastView` 字段保留并继续写（备份格式里有它，不动 schema）。
深链接（把页面编码进 URL）留作以后的可选项，这一步不做。

**更简单的替代。** 只拦后退键、弹「确定离开吗」——治标，且浏览器对 `beforeunload` 的支持越来越弱。不建议。

**复杂度 / 风险 / 收益。** 中等，主要成本在焦点管理与 e2e（a11y 用例对换页时的焦点落点有断言）。
收益是一个移动端用户每次使用都会碰到的行为变正确。

**如何证明有效。** e2e：三层进入后连按三次后退逐层返回、第四次才离开；分享预览进出不受影响；
换页焦点用例全绿。

### 4.6 棋谱库只增不减、没有时间、不能删 —— 优先级 5

**现状。**

- 每一局结束都自动入库（含空盘认输）。
- `GameRecord` **没有时间字段**；列表项只有「黑方胜 · 人机 · 初级 · 37 手」。
- **界面上没有删除棋谱的入口**（局面库有；棋谱库的 `delete` 只被「替换同一局」的内部路径调用）。
- `GameLibrary` 把 `list()` 的结果**全量渲染**；`list()` 每次 `getAll` 并对每条记录做一次 `replay` 校验。
- `saveGameReplacing` 与 `findSavedGame` 判重靠全表扫描 + 每条算一次内容键；`records` 表没有索引。

**关于「不存时间戳」的理由。** `gameRecords.ts` 与 `GameLibrary.tsx` 的注释把它归因于
「`Date.now()` 只允许出现在 `ai/search.ts`」。但 `AGENTS.md` 当前版本已经自己更正了这条规则
（「这条原先写的……比事实更绝对」，并且**点名**这两处注释「还按旧措辞引用了它」）；
而局面库的 v2 已经用注入时钟存了 `createdAt` / `updatedAt`。**这个产品决定赖以成立的理由已经被项目自己撤回了**，
决定本身却留了下来。

**实测（性能）。** 往一个隔离的浏览器环境里灌 N 条 40–120 手的合法棋谱：

| N | 打开复盘页 → 首条可见 | DOM 元素 | 长任务 |
| --- | --- | --- | --- |
| 0 | 66 ms | 73 | — |
| 200 | 63 ms | 1,273 | — |
| 1,000 | 118 ms | 6,073 | — |
| 5,000 | 433 ms | 30,073 | 138 ms（打开）、162 ms（终局入库） |

终局入库到「已存入」的耗时在 96–375 ms 之间波动，**没有随 N 单调上升的趋势**。
**结论：在桌面机上，性能不是问题**；5,000 条才出现一次百毫秒级长任务。低端手机上会放大若干倍，
但那是没有测过的假设（§7）。

**所以这一条的性质是产品与数据模型，不是性能。** 一个每天下几局的用户，几个月后面对的是
几百条无法区分、无法删除、无法筛选的条目。

**涉及模块。** `persist/gameRecords.ts`、`features/review/GameLibrary.tsx`、
`persist/transfer/format.ts`（导出文件）、`docs/data/*`。

**改进方向。** ① 入库时用注入时钟写 `createdAt`；② 列表显示时间并分批渲染（「显示更多」即可，
不必上虚拟列表）；③ 删除入口（二次确认，沿用局面库的模式）；④ 把 `saveGameReplacing` 的
「写新 → 查旧 → 列全表 → 删旧」四个独立事务收成存储接口上的一个原子操作，
现在那段补偿逻辑（「旧条删不掉就把新条撤回」）可以整段消失。

**更简单的替代（关于 schema，推荐）。** `parseRecord` 只取它认识的字段、只核对 `schemaVersion === 1`。
所以**把 `createdAt` 作为可选字段加进去而不递增版本号**，旧代码读得了（忽略它）、新代码把缺失当「时间未知」
——**向前向后都兼容，回滚安全，不需要迁移**。相反，照局面库的做法升到 v2，
回滚后的旧代码会把所有新棋谱报成「读不出来」。这与 `SCHEMA_MIGRATION.md` §4 第 3 条的字面
（「改对象字段形状用 schemaVersion + 迁移」）有出入，需要你裁定；我的看法是那条规则针对的是
「改变已有字段含义」，纯新增可选字段不在其列（同一份文档对外部格式就是这么规定的）。
内容身份 `recordContentKey` **不得**包含时间。

**复杂度 / 风险 / 收益。** 中等；风险集中在数据兼容（用 `docs/audit/fixtures/phase11e/` 的旧夹具守）；
收益是棋谱库从「日志」变成「库」。

**如何证明有效。** 旧夹具读入后显示「时间未知」；新旧版本交叉读写的 e2e；删除后刷新不复现；
5,000 条下首屏 DOM 数量有上限。

## 5. 深层次架构与工程风险

这些不是今天的缺陷，是**会随规模变贵**的结构。

### 5.1 四份请求生命周期实现

| 调用方 | 作废判据 | 超时兜底 | 取消 |
| --- | --- | --- | --- |
| `gameStore.requestAiMove` | `pendingRequestId` + `gameVersion` | 有（15 s） | 无 |
| `gameStore.requestHint` | `pendingHintRequestId` + `gameVersion` | 有（15 s） | 无 |
| `analysisStore.pump` | `runId` + `inflightIndex` + `moveIndex` | **无** | 无 |
| `editorStore.analyze` | `version` + `requestId` | **无** | 无 |

同一件事写了四遍，两两不一致（后两处缺超时已登记在 `TECH_DEBT.md` §1.4）。
项目自己的原则是「没有第二个消费者就不抽象」——这里已经有四个了。它与 4.3 是同一件事的两面，一起解决。

顺带一个观察：`SearchRequest` 里的 `gameVersion` 在三处承载了三种不同含义（手数 / 编辑计数器 / 恒为 0），
`moveIndex` 与它一样只是穿过 Worker 再原样带回，而四个调用方实际都靠**闭包里捕获的值**做判定
（`analysisStore` 对回显字段的那道检查，注释自己写着「真实引擎下不可达」）。
这说明回显字段更多是历史形状而不是必需品。**不建议现在删**——`AGENTS.md` 的「两道闸门」是明文约定——
但做「请求槽」时值得把「局面身份」这道闸门的实现想清楚（见 §7 的 H-4）。

### 5.2 分层规则没有机械化门禁，且已经有漂移

`core` / `ai` 不得依赖 React、`store` 不依赖 `features`……这些规则在 `AGENTS.md`、`CLAUDE.md`、
`ARCHITECTURE.md` 里写了三遍，每轮审计靠手工 grep 复核。`yarn gates` 管了环、死代码、重复、条数、体积，
**唯独不管依赖方向**。本轮自己算了一遍，主干干净，但有这些：

- `components/panels/` 有 7 处 import 指向上层：`StatusPill`、`ResultDialog` 从 `features/battle/status`
  取类型；`AiPanel`、`SettingsPanel`、`ResultDialog` 从 `store/gameStore` 取类型；
  `HintPanel` 取 `HINT_BUDGET_MS`、`MoveList` 取 `moverAt`（这两处是**值**）。
  `ARCHITECTURE.md` 解释 `PageShell` 为什么不能放进 `components/` 时用的理由正是
  「那会变成 `components → features`」——同一条规则在别处已经被悄悄越过了。
- `lib/shape-labels.ts` 取 `learn` 的类型，而 `learn` 又 import `lib`——类型层面的互相引用。
- `ARCHITECTURE.md` 的箭头记法自相矛盾：「`components → features → store`」里的箭头若读作「依赖」，
  就与紧接着的 `PageShell` 段落相反。

这些都很小。值得说的是**成因**：`GameMode`、`moverAt`、`GameStatusDescriptor` 是领域概念，
却没有一个下层的家，只好住在 `store` / `features` 里，于是下层要用就只能往上够
（`persist` 为了不依赖 `store` 把 `'pve' | 'pvp'` 又手写了一遍，并留了注释解释）。
**给它们在 `core` 里安个家，再加一道门禁，这类漂移就停了。**

### 5.3 `replay()` 的静默截断，与 6 处手工补的严格检查

`replay` 遇到非法手就停并丢掉其余——对恢复本地存档是对的。但其余调用方几乎都要相反的语义，
于是 `state.moves.length !== moves.length` 这句检查出现在 6 个地方
（`core/branch.ts` ×2、`core/position.ts` ×2、`persist/gameRecords.ts`、`persist/transfer/validate.ts`）；
「重放之后若有认输方就再套一层 `resign`」写了 2 处（`gameStore.restore`、`replayStore.derivePosition`），
`gameRecords.deriveWinner` 是同一条规则的第三种写法。
`TECH_DEBT.md` 做禁手推演时已经指出过截断策略在新语义下会变危险。
**缺的是一个原语**：`replayStrict(moves, firstPlayer)` 返回「成功的状态」或「在第几手、因为什么失败」，
以及一个「按棋谱记录重建终局」的函数。宽松版留给存档恢复。纯 `core` 改动，6 处调用点各少两行，
漏写检查这类错误从此不可能。

### 5.4 `gameStore` 的增长轨迹

5 周内 420 → 607 → 714 → **843** 行。它现在同时是：对局状态机、AI 落子编排、提示编排、
棋谱入库链（`makeNotifier`）、会话读写状态旗标、分支来源。此前的审计判断「合在一起合理，
等有第二个着法来源再拆」——**我同意不整体拆**：这些职责共享 `game` 与几个 pending 字段，
拆成多个 store 只会把同步问题从文件内挪到文件间。

但有两块是**自成一体、今天就能平移**的：请求生命周期（随 4.3 抽走，落子与提示各少约 40 行）
与 `makeNotifier`（它已经是闭包里的独立状态机，只通过 `set` 写三个字段）。
做完这两件，文件回到 600 行上下，剩下的才是真正的「对局状态机」。**除此之外不建议动。**

### 5.5 恢复备份的编排逻辑住在组件里

`DataManagementPanel.confirmImport` 是一段 130 多行的流程：棋谱整笔失败则其余各段不动、
进度 / 偏好 / 会话各自独立成败、局面逐条去重逐条写。这是**数据安全的核心逻辑**
（「不做半恢复」的策略就定义在这里），却只能通过渲染组件来测试，也没法被别处复用。
它违背的不是行数，而是架构文档那句「展示层只做渲染与事件转发」。
建议平移成一个注入依赖的纯函数（`计划 + 存储接口 → 分项结果`），组件只留预览与结果展示；
现有组件测试原样保留作为集成层。

### 5.6 持久化的几个小口径问题

- `gameRecords.ts` 顶部注释写「字段形状一变就递增，**旧数据被安全丢弃**」，`storage.ts` 也有同样一句；
  这与 `SCHEMA_MIGRATION.md` §4 的「迁移前不破坏旧数据」「不因单条无效清空全部」直接矛盾，
  也与 `storage.ts` 自己实现的 v1 → v3 只读迁移矛盾。棋谱表目前没有任何迁移路径——
  哪天真的递增版本号，按现有代码就是全部变成「读不出来」。改注释，并在动棋谱格式前先补迁移入口。
- `isPlayer` 写了 4 份、坐标点的解析写了 3 份（`storage` / `gameRecords` / `positions`，
  而 `transfer/guards.ts` 已经有导出的那一份）。jscpd 抓不到这种 5 行以内的重复。小事，顺手收。
- 每个存储操作各开各关一次数据库连接。实测没有性能问题，**不必动**；只是 4.6 里把替换做成单事务后，
  多连接带来的补偿逻辑会自然消失。

### 5.7 文档与注释的漂移

量不大，但说明「写得多」本身不能防漂移：

### 5.8 测试条数棘轮的副作用

## 6. 性能与可靠性观察

严格区分三类。

**已实测、没有问题（不必投入）：**

- 首屏与落子成本（项目记录：FCP 112 ms、落子 0.10 ms 中位）。`Board.tsx` 不需要 `memo`、不需要拆。
- 教学判题在主线程同步跑算杀（预算上限 2 s / 3 s）——项目已量过，现有内容最慢 5.15 ms。
  只要出题时继续过 `content.test.ts` 与 `bench:learn`，就不必搬进 Worker。
- 棋谱库到 1,000 条没有可感知成本（4.6 的表）。
- Worker 终止重建：中位 4 ms。

**已实测、有问题：**

- 过期搜索排队（4.3）。
- 入口包余量（4.4）。
- `yarn test` 的 31.4 s 里，vitest 自己报告 **jsdom 环境创建了 90 次、合计 79.86 s、占被跟踪时间的 40%**。
  `core` / `ai` / `analysis` / `learn` / `sharing` 与 `bench/strength` 的测试是纯逻辑，本不需要 jsdom。

**没有测过、只是理论可能（不要据此动手）：**

- 低端手机上数千条棋谱的长任务会不会到秒级。
- Worker 的长时间内存表现（`KNOWN_LIMITATIONS.md` 已如实登记）。
- 迭代加深在超时那一层丢掉的计算（平均接近半个预算）能不能安全地利用起来——见 §7 的 H-1。

**可靠性方面，本轮没有发现新的数据安全问题。** 导入校验、事务口径、降级语义、分享预览不写库，
读下来都站得住。多标签页最后写入者胜、回滚时会话被当作未来版本丢弃，都是文档里已经如实登记并接受的边界。

## 9. 总体演进战略

**一句话：先修语义，再补能力，最后才动结构；每一步都能单独上线、单独回滚。**

三条原则：

1. **按「会不会说错话」排序，而不是按代码的难看程度。** 4.1 与 4.2 的代码都很整洁，
   它们的问题是界面在向用户陈述不成立的事。这类问题在一个以「如实」为卖点的产品里应当排在所有结构性工作之前。
2. **只补一个缺失的模块。** 全仓真正「缺东西」的地方只有请求调度这一处；其余都是平移、下沉与收口，
   不新增抽象层。
3. **不改已冻结的约定，除非给出证据并由你裁定。** 本报告对四条既有决定提出了异议，逐条列在这里，
   **在你表态之前都按现状执行**（已于 2026-11-17 裁定，结果见 §14）：

| 既有决定 | 我的异议 | 证据 |
| --- | --- | --- |
| 无 router（`TECH_DEBT` §1.3） | 不要路由库，但要进浏览器历史 | 后退键直接离开应用（4.5） |
| 棋谱不存时间戳 | 该存 | 理由已被 `AGENTS.md` 自己更正；局面库已有先例（4.6） |
| `confidence` 二值 | 语义倒挂 | 项目自己的发布记录（4.2） |
| 对象字段变化一律走 `schemaVersion` + 迁移 | 纯新增可选字段可以不递增 | `parseRecord` 的实际读取方式；回滚安全性（4.6） |

对「`requestId` + `gameVersion` 两道闸门」「`core` 是唯一真相」「状态不可变」「时钟注入」
「题目答案不许写死」「门禁不许调松」这些约定，本报告**没有异议**，所有建议都在它们之内。

## 10. 分阶段实施路线

五个阶段。A 与 E 的各项互相独立；B、C、D 之间没有硬依赖，顺序是按价值排的。

### 阶段 A · 让界面说对话

- **目标**：修复两处语义错误。不动架构。
- **解决的问题**：4.1、4.2、5.7。
- **模块**：`store/analysisStore.ts`、`analysis/analyze.ts`、`ai/search.ts`（仅 `chooseMove` 里那一行映射）、
  `AiPanel` / `HintPanel` / `PositionEditor` 的文案、`AI_ENGINE.md`、`ARCHITECTURE.md`。
- **设计思路**：分差改同视界比较（着法不同时补一次「走引擎首选之后」的请求），缓存键版本递增；
  可靠度先用最小改法（`heuristic` 仅限 `depth === 0`，改两句文案）。
- **改动范围**：约 6 个生产文件，各几十行以内；测试新增为主。
- **主要风险**：分析总耗时上升（上限 = 手数 × 400 ms）；文案断言与覆盖棘轮要同步。
- **验收**：① 引擎自对弈时新口径分差中位数为 0，且不依赖「着法相同」特判；
  ② 随机着法的亏损检出率有基线并写进文档；③ 专家档连下三手不再出现「启发式兜底」；
  ④ 五条命令全绿，`e2e:prod` 全绿。
- **依赖**：无。**可立即开始。**

### 阶段 B · AI 请求调度层

- **目标**：引擎有真正的取消；四份请求生命周期合一。
- **解决的问题**：4.3、5.1，以及 5.4 的一半。
- **模块**：`ai/engine.ts`、`ai/browserEngine.ts`、`store/` 下新增一个请求槽工具，
  `gameStore` / `analysisStore` / `editorStore` / `useGameStore` 改用它。
- **设计思路**：先用一次小实验在「双 Worker」与「单 Worker + 引擎侧队列」之间选型
  （倾向前者：更简单，且顺带解除分析对落子的阻塞）。取消 = 终止并重建 Worker。
  Worker 改为首次请求时创建。`applyAiResponse` / `applyHintResponse` 里的两道闸门**一行不动**。
- **改动范围**：`ai/` 两个文件重写（合计不到 100 行）、三个 store 各改请求发起处、新增一个小模块；
  `gameStore` 净减约 80 行。
- **主要风险**：Worker 重建失败的路径；Firefox / WebKit 的差异；假引擎接口扩展波及较多测试文件。
- **验收**：① 时间戳探针：悔棋后新请求排队 < 50 ms（现 1.3 s），连续 6 次悔棋后不累积（现 10.4 s）；
  ② 既有的过期响应用例不改断言全绿；③ 复盘与编辑器分析有超时兜底；④ `e2e:browsers` 全绿；
  ⑤ 每页 Worker 数量符合选型预期并有用例钉住。
- **依赖**：无硬依赖；做完后 H-7 才有意义。

### 阶段 C · 导航与按页加载

- **目标**：后退 / 前进可用；入口包回到有余量的状态。
- **解决的问题**：4.4、4.5。
- **模块**：`App.tsx`、新增 `navigation` 模块、`learnStore`（搬走 `view`）、`AppHeader`、
  三个页面的子页面状态、`vite.config.ts`、`quality/bundle-budget.mjs`（**收紧**，须你批准）。
- **设计思路**：页面与子页面状态进 `history.state`，URL 不变；`React.lazy` 拆复盘组与教学组；
  分块加载失败落到错误边界。`progress.lastView` 字段保留。

\|偏差\| 中位数 14,200、P75 15,000、P90 17,200、最大 200,000；≥ 10,000 的 112 个；另有 66 手因涉及捷径分被排除。
