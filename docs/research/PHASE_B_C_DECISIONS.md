> 出处：评估报告 §14 裁定 1（导航进历史并做深链接，先出 URL 方案）、裁定 4（调度层先做选型实验再定）、
> §14.1 裁定 11（两者一并提交，不各等一次）。本文只是实验记录与方案，**没有改主干的产品代码**。

## 一、阶段 B：请求调度层的选型实验

### 两个原型

都只改了 `src/ai/browserEngine.ts` 一个文件，各在一个本地实验分支上（`exp/b-dual-worker`、`exp/b-engine-queue`），
**不合入主干**。store、协议、`engine.ts` 一行没动——两个原型都靠「新的落子请求到来时，上一个落子请求必然已被 store
作废」这条事实做取消，不需要 store 显式调用取消。

| | 原型 A：双 Worker | 原型 B：单 Worker + 引擎侧队列 |
| --- | --- | --- |
| 做法 | 落子一个 Worker（同一时刻至多一个请求；新落子到来时终止并重建）；提示 / 复盘分析 / 编辑器分析另一个 Worker，串行 | 一个 Worker，队列挪到主线程、一次只发一个；新落子插队首，在飞的若是落子或提示就终止重建，在飞的是分析则等它回来 |
| 改动量 | +33 / −13 行 | +45 / −12 行 |
| 规则条数 | 1 条（按 `purpose` 分流） | 3 条（插队、哪些可以打断、出队） |

### 实测（`yarn bench:queue`，生产构建，本机 Chrome，专家档；三个构建依次各跑两轮、不并发，1 分钟负载 3–7）

「排队」= 往返时间 − 引擎自报耗时。

| 场景 | 主干现状（两轮） | 原型 A 双 Worker | 原型 B 引擎队列 |
| --- | --- | --- | --- |
| A. 思考中悔棋再落子（三轮的最后一个请求） | **908 / 897 / 1001**；**921 / 891 / 912 ms** | 15 / 15 / 15；14 / 13 / 13 ms | 15 / 15 / 16；14 / 14 / 15 ms |
| B. 连续 6 次「落子 → 悔棋」后落子 | 排队 **8,492 / 8,500 ms**，AI 9.9 s 后才应手 | 12 / 14 ms，AI 1.8 / 2.1 s 应手 | 13 / 54 ms，AI 2.8 / 2.6 s 应手 |
| C. 求提示后 50 ms 落子 | 落子排队 **717 / 717 ms** | 落子排队 0 / 0 ms；提示照常返回 | 落子排队 10–16 ms；**提示被打断、不再返回**（局面已变，它本来就过期了） |
| D. Worker 新建 + 首个请求往返 | 中位 4 ms（12 次，3–9 ms） | 同一个 Worker 脚本，代价相同 | 同左 |

两个原型都把排队从秒级降到十几毫秒（≈ 重建 Worker 的代价），且不再随悔棋次数累积。**延迟上分不出胜负。**
B 场景里两者「AI 多久应手」的差别来自那一手的引擎耗时（原型 B 那两轮落在 2.6 s 上限的超时档），不是排队。

### 分得出胜负的地方

1. **分析会不会挡住落子。** 原型 A 里分析与落子在两个 Worker，永不互相等待——复盘分析的档位与预算可以放开
   （评估报告 §4.3：现在复盘被锁在初级档 400 ms，理由就是「不长时间占住 Worker」）。原型 B 里，复盘页卸载后
   在飞的那一个分析请求仍会挡住对战页的落子；预算一放开，这段等待就跟着变长。要避免就得让落子也能打断分析，
   而引擎不知道分析是否还有人要——那得由 store 显式取消，规则随之变多。
2. **复杂度。** A 一条分流规则；B 要维护一个队列和「谁能打断谁」的表，以后加一种请求就要回答一次。
3. **代价。** A 多一个常驻 Worker：Worker 脚本 15.1 kB（gzip 5.9 kB，与主线程共享 HTTP 缓存，只下载一次），
   置换表每次搜索新建、不常驻，所以多出来的主要是一份 JS 引擎实例。原型里只读 Worker 是首次只读请求时才创建，
   从不求提示、不复盘的会话不会多出这一个。

### 原型暴露的、正式实现要补的

- 被取代的落子请求的 Promise 不再结算，`engine.ts` 的待决表里会留一条（原型可以接受；正式实现要加 `cancel`，
  从表里摘掉并以「已取消」结算，store 的闸门照旧丢弃它）。
- 原型靠「下一个落子请求」触发终止；悔棋之后若玩家不再落子，作废的那次搜索会跑完——资源上不理想但无害。
  正式实现由 store 在作废路径上显式 `cancel`。
- 编辑器分析也走 `purpose: 'hint'`。A 里它在只读 Worker 上；B 里它会被落子打断（不同页面，实际碰不到）。

### 建议：原型 A（双 Worker）

延迟收益相同，A 的规则更少，并且顺带解除「分析挡住落子」——这正是之后放开复盘分析档位的前提。
代价是多一个按需创建的 Worker。

## 二、阶段 C：URL 方案

### 要回答的问题

裁定 1：导航进浏览器历史，**并做深链接**（页面编码进 URL），不引入路由库。
现状：页面位置存在 `progress.lastView`（IndexedDB），子页面是各组件的 `useState`；
URL 只在分享预览时用（`#share=<token>`，`App.tsx` 监听 `hashchange`）；部署在 Cloudflare Pages，
`public/404.html` 写着「应用只有首页一个入口」，`public/_headers` 管缓存与 CSP。

### 两个方案

| | 方案一：hash 路由（建议） | 方案二：路径路由 |
| --- | --- | --- |
| 地址 | `/#/learn`、`/#/learn/<课程 id>`、`/#/puzzles/<题目 id>`、`/#/review`、`/#/review/<棋谱号>`、`/#/review/<棋谱号>/editor`；对战页是 `/`（或 `/#/`） | `/learn`、`/learn/<课程 id>`、`/review/<棋谱号>` …… |
| 与 `#share=` 共存 | 靠前缀区分：`#share=` 照旧，`#/` 开头是页面。分享预览关闭后回到原来的页面地址 | 不冲突（一个在路径、一个在 hash） |
| 部署 | **不用改**：所有地址的路径都是 `/` | 要在 `_redirects` 里为每个页面路径写改写规则（`/learn/* /index.html 200` …）。**不能**写成 `/* /index.html 200`：那会把发布后已不存在的旧分块也回成 `index.html`，分块加载失败变成「把 HTML 当 JS 解析」。`404.html` 的文案要改；`vite preview` 与 e2e 的服务器要有同样的回退 |
| 刷新 / 直达 | 都行 | 都行（规则写对的前提下） |
| 观感 | 地址里有 `#` | 更干净 |

### 两个方案共同的行为（与方案无关）

- 切页、进出子页面都 `pushState` 一条历史；后退 / 前进逐层返回，回到第一条之后再后退才离开应用。
- 冷启动：地址里有页面就以地址为准；没有（裸的 `/`）就照旧用 `progress.lastView` 恢复上次的页面。
  `progress.lastView` 继续写（备份格式里有它，不动 schema）。
- 地址里的 id 找不到（课程下线、棋谱删了、换了设备）：回到该页的列表，不报错页。
  **棋谱号是本机 IndexedDB 的自增号**，所以 `/review/<棋谱号>` 只在本机有意义——它是给刷新与后退用的，
  不是给别人分享用的；分享仍走 `#share=`。
- 对局中途切页、悔棋这些对局内的动作**不进历史**（后退键不是悔棋键）。
- 不引入路由库：一个百行量级的 `navigation` 模块，`TECH_DEBT.md` §1.3 的「无 router」改写成「不用路由库，但进历史」。

### 建议：方案一（hash 路由）

深链接的需求（刷新、后退、直达）两者都满足；方案一不碰部署配置、不碰缓存与旧分块那条风险，
与分享链接靠前缀就能分开。代价只是地址里多一个 `#`。
