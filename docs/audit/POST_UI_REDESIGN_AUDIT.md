## 7. 发现的问题及证据

### P0（严重功能 / 数据 / 安全）：**无**

### P1（明显影响主要用户流程）：**无**

### P2（值得改进，不阻止发布）：**无**

### P3（细节、审美或未来增强）：5 条 + 1 条环境伪影

#### P3-1 · 学习进度的写入没有落盘时机保证（同 tick 刷新会丢「上次停留位置」）

- **现象**：点「← 课程列表」后**立刻**刷新，会回到课程的讲解页，而不是课程列表。
- **证据**：`LearnScreen` 退出 → `visit(null)` → `learnStore.persist()` 里是 `void storage.save(progress)`
  （`learnStore.ts:50`），**不 await**；IndexedDB 提交还没完成，页面就被卸载了。
  受控实验（`/tmp/gomoku-audit/flaky.mjs`）：延迟 **0 ms 刷新 6/6 次复现**；
  延迟 **≥20 ms 全部正常**（20/60/200/800 ms 各一次，均落在列表页）。
- **影响范围**：只影响「上次停留位置」这一个字段。**完成记录不丢**——
  单独实验（`explore3.mjs` 的 L 组）显示：判对后 0/5/15/30 ms 刷新，
  IndexedDB 里始终是 `completedLessons: ["rules"]`。
- **根因**：异步写入 + 卸载之间没有同步点。任何未来的「写完再跳页」流程都会带上同一个窗口。
- **修复建议（不建议现在做）**：`pagehide` / `visibilitychange` 时 flush 一次，
  或把「离开课程」改成等待写入完成的最小异步流程。当前窗口 <20 ms，
  真人手速（>150 ms）够不到，所以定 P3。

#### P3-2 · 分析面板对「走捷径」的一手仍标「搜索完成」

- **现象**：复盘结论卡片里出现 `深度 0 · 节点 0 · 搜索完成`（本次实测的种子局第 8 手）。
- **证据**：`analysisStore` 的 `confidence` 只在 `reason === 'timeout'` 时为 `heuristic`
  （`search.ts:564`），而 `win` / `block` 捷径返回 `depth: 0, nodes: 0`；
  卡片按 confidence 渲染「搜索完成 / 预算内未搜完（启发式）」（`ReviewScreen.tsx:302`）。
- **影响范围**：读的人可能把「没搜索的捷径结论」当成「搜完了的结论」。
  两个原始数字（深度 0、节点 0）就显示在同一行，技术读者看得出来，所以是措辞问题而非数据问题。
- **修复建议（与 F-UI-23 同一处）**：`SearchResponse` 补 `plies` / `shortcut` 字段，
  卡片分三档说：直接成五 / 算杀链首手 / 搜索结论。

#### P3-3 · 判题与第三级求解同步跑在渲染路径上

- **现象**：练习/残局里点「第三级提示」或落子，主线程被同步占用一小段。
- **证据**：`PracticeBoard.tsx:50`（`useMemo` 里 `solveMove`）与 `:92`（`judgeMove`）都在渲染路径上；
  实测第 3 级提示 **114–132 ms**、判题 **60–79 ms**，16 ms 打点最长间隔 **26–49 ms**。
- **影响范围**：算杀题上一次约 2–3 帧的轻微顿挫，未观察到卡死；
  预算上限是 2 s（判题）/ 3 s（求解），本次所有局面都远未触及。
- **修复建议**：若日后加大算杀深度或题目变难，把求解挪进 Worker（`ai/engine.ts` 已是可注入的纯状态机，
  复用成本低）。
- **⚠️ Phase 09A 更正（2026-10-20）——上面的 60–132 ms 是测量口径错误**：
  当时计时块里含一个固定 `waitForTimeout(60)`，且从 Playwright 的 `click()` 调用点起算，
  把派发与读取开销都算了进去。Phase 09A 改用**页内同步点击 + MutationObserver**重测
  （`/tmp/gomoku-audit/phase09-blocking3.mjs`，dev 5190 与生产产物 5192 各一遍）：
  - 纯函数（`yarn bench:learn`，15 道题/课各 3 次取中位）：最慢 `solveMove` **5.15 ms**
    （lesson `defense`），最慢 `judgeMove` **2.97 ms**（puzzle `forced-counter`），判错 ≤0.45 ms；
  - 生产产物：点第 3 级提示 → DOM 出现标记 **1.3–4.3 ms**，其中求解本身占 0.7–5 ms；
    同步事件处理 0.1 ms，React 提交在微任务里完成；
  - dev 模式同口径 **10–14 ms**（React 开发版 + 未压缩代码），差异全部来自开发开销；
  - 全程**无 >50 ms 的 long task**（此前 dev 下偶见一次 52 ms，属开发模式渲染）。
  结论：**不存在 60–132 ms 的同步阻塞**，P3-3 的「顿挫」描述不成立；求解/判题无需挪进 Worker。
  已做的 `solutionCache` 保留，但它省的是「再做一次」重付的那几毫秒，**不是**对 130 ms 卡顿的修复。

#### P3-4 · 超宽屏（1920）下对战页信息密度偏稀

- **现象**：1920 下**对战页**棋盘 729px（占视口宽 **38%**，判据线 35%）；**复盘 / 教学详情** 758px（**39.5%**）。两侧留白明显（截图：`ci/battle-battle-midgame__1920-light.png`；`ci/` 被 gitignore，可用附录 A 的命令重生成）。
- **影响范围**：观感问题，判据内合规；不遮挡、不溢出。
- **修复建议**：给中列加一个上限（例如棋盘最大 760 px）并把省下的宽度给侧栏，或在 ≥1920 收成「更宽的棋盘 + 更宽的侧栏」。

#### P3-5 · 缺 `robots.txt` / `llms.txt`（Lighthouse SEO 80 / Agentic 50）

- **证据**：三次 Lighthouse 的失分项**只有**这两条。
- **影响范围**：纯静态离线应用，本机与自托管都不受影响；对外部署时才是小瑕疵。
- **修复建议**：部署前在 `public/` 各放一个文件（`robots.txt` + 一行 H1 的 `llms.txt`），成本几分钟。

#### ENV-1 · 一次无法复现的 `theme-color` 读数（**不作为缺陷**）

- **观测**：在用户本机 Chrome 里做过一次 Lighthouse 快照之后，读到
  `<html class="dark">` 而 `meta[theme-color]` 仍是浅色值 `#f6f4f0`。
- **无法复现**：随后两次受控测量都正确——
  (a) Playwright 上下文 `colorScheme: dark` 挂载 → `#0f1115`；
  (b) 在同一页面里把模拟色板在 light ↔ dark 之间来回切换 → 两次都跟着更新。
  用应用自己的主题按钮切三档（浅色 / 深色 / 跟随系统）时 class 与 meta 也始终一致。
- **判定**：测量环境伪影（CDP 媒体模拟 + 本机扩展注入）。**如实记录，不计入缺陷**，
  但建议日后若要再验 F-UI-17，用**干净上下文**而不是带扩展的真实 profile。

## 11. 建议的下一轮开发路线图

排序依据：**用户价值 × 实现难度 × 维护成本 × 依赖关系**。明确写出**哪些不做**。
每一阶段都可以独立实施、独立验收。

### Phase A · 发布后收尾（低成本、高确定性，1–2 天）

| # | 事项 | 为什么排在最前 | 依赖 |
| --- | --- | --- | --- |
| A1 | 部署基线：`robots.txt` / `llms.txt`；产物已自带内容哈希文件名（`index-<hash>.js`），无需额外指纹 | 三条 Lighthouse 失分全在这里，成本几分钟（P3-5） | 无 |
| A2 | 复盘页**手顺列表**（点击跳转、与时间轴同一游标） | M-2 的正解：既解决三位数密排的载体问题，又补上「看完整手顺」这个真缺口。游标已经是唯一真相（`replayStore`），加一个列表不新增状态 | 无 |
| A3 | 进度写入的落盘时机（P3-1）：`pagehide` flush 或离开课程时等待写入 | 一处 ~10 行的健壮性修复，消除 <20 ms 的丢写窗口 | 无 |
| A4 | 分析结论分档（P3-2 + F-UI-23 正解）：`SearchResponse` 补 `plies` / 捷径标记 | 把「深度 0 却写搜索完成」这句假话修掉；需要动 `ai/` 接口与基准（基准有门禁守着） | 无 |
| A5 | 超宽屏密度（P3-4）：给中列 / 棋盘一个上限，把宽度让给侧栏 | 判据内合规但偏稀；纯样式改动，风险低 | 无 |

**P3-3（判题/求解同步）不单列**：原测「60–132 ms」已被 Phase 09A 证伪（测量口径含固定等待），
纯函数最慢 5.15 ms、生产产物提交 1.3–4.3 ms，**当前无任何理由挪进 Worker**；
只有算杀深度上调或题目显著变难时才重新评估（`ai/engine.ts` 已是可注入的纯状态机，迁移成本可控）。

### Phase B · 引擎与难度可信度（1–2 周，且有先后依赖）

| # | 事项 | 为什么 | 依赖 |
| --- | --- | --- | --- |
| B1 | **评测体系**：难度矩阵（档位 × 局面）自对弈胜率 + 固定题集的解题率 | 当前「五档差异」的证据是参数与深度；有了胜率矩阵，「中级比初级强」才是可回归的断言 | 无（先做） |
| B2 | **增量局面评估**：只重算受落子影响的 4 条线段 | `evaluateBoard` 74 µs 是专家档的主要开销；这是唯一能把专家档真正推到 7–8 层的杠杆 | B1（否则改完无法判断变强还是变慢） |
| B3 | 算杀扩展：VCT 按预算自适应开启 | VCF-only 是有意的漏杀；先把 B1 建起来再评估代价 | B1 |

### Phase C · 内容与生态（2–4 周）

| # | 事项 | 说明 |
| --- | --- | --- |
| C1 | 棋谱**导入 / 导出**（自定义 JSON 或 SGF 子集） | 复盘库目前只进不出；导出是分享与备份的最小闭环。需要 `schema` 双端校验（与 `parseRecord` 同一套尺子） |
| C2 | 教学与残局的**内容扩展**（目标：12 课 / 30 题，新增「防守优先」「双威胁反制」两类） | 判定器与求解器已就位，加内容几乎零代码风险；`content.test.ts` 会自动守 |
| C3 | PWA：`manifest` + Service Worker 预缓存产物 | 应用本来就不联网，装到桌面/主屏是顺水推舟。**风险点：缓存版本管理必须跟着产物指纹走**，否则会出现「更新了但页面还是旧的」 |
| C4 | 复盘「深挖某一手」：把手顺列表 + 分析接起来，允许对任一局面单独重跑（可选档位/预算） | 目前固定初级 + 400 ms，是复用现成管线的增量功能 |
| C5 | 对弈体验与模式：**新局可撤销**、让子 / 计时 | §10 把「新局可撤销」列为体验缺口；但它是产品决策（会改变对局语义），先做取舍再动手，不默认要做 |

### Phase D · 需要产品决策，**建议先不做**

| # | 事项 | 我的判断 |
| --- | --- | --- |
| D1 | 禁手 / 规则变体（连珠式三三禁手等） | **不建议现在做**：要同时改 `core`（判定）、`ai`（搜索空间与评估）、`learn`（教学内容重写）与 `DESIGN_SYSTEM` 的说明，代价接近重写规则层。若要做，先出**独立的规则模式**而不是替换自由规则 |
| D2 | 在线对战 / 多人 | **不建议**：它会引入后端、账号与网络依赖，直接冲掉本项目「完全离线、无后端」这个已经兑现的产品身份。要做应当**单独立项**（另一个产品，而不是这个仓库的一个阶段） |
| D3 | 生产可观察性（错误上报 / 埋点） | **不建议接第三方**：与「零网络请求」这条已经写进 README 的性质冲突。若确需，只做本地诊断（例如把 `AppErrorBoundary` 的堆栈留在 localStorage 供用户自行导出） |
| D4 | 引入 UI 组件库 / 图标库统一图标（L-2） | **不建议**：当前 3 个运行时依赖、`dark:` 0 处、56 个令牌是一份资产；为了图标统一引入依赖是负收益 |

### 不建议做的（明确列出）

- 给低档 AI 人为削弱（约定明令禁止；难度必须来自参数与算法）。
- 为了分数好看而压缩现有功能（本次审计未发现任何「为数字好看而删功能」的痕迹，保持它）。
- 用固定阈值把每一手断言成「最佳 / 失误」（`analysis/analyze.ts` 已明确拒绝这条路，不要回退）。
